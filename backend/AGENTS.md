# Backend

Java 25 и Spring Boot. Текущая структура пакетов описана в
[архитектуре](../docs/architecture.md#границы-кода), слои и последовательность
квалификации — в [SI-09](../docs/decomposition.md#si-09-архитектура-и-оптимизация).
Следующие правила применяются к текущему и новому коду.

## Слои и модель

- domain — обычная Java-модель и предметные правила. Без Spring, Jackson,
  JDBC, UserDetails, HTTP-статусов и generated DTO. Сущность предметной области
  не обязана быть JPA Entity; сохраняем Spring JDBC.
- controller — тонкая реализация generated API, преобразование текущего
  пользователя в Actor и вызов service. mapper преобразует HTTP DTO через
  MapStruct; права, допустимые действия и переходы определяет domain/service.
- service — сценарии, права, координация и транзакции. Зависит от domain, dto,
  контрактов repository/client. Не импортирует controller, generated DTO,
  repository/jdbc или client/http. Интерфейс для каждого service не нужен.
- repository — действующие контракты хранения. repository/jdbc — единственный
  владелец SQL. TaskRepository хранит задания/историю; ExchangeRepository —
  состояние обмена, очередь, попытки и курсор. У каждого свой JDBC-адаптер,
  TaskRowMapper общий только для реальных проекций состояния задания.
- client/http — HTTP и строгая проверка внешнего протокола; scheduler — тонкие
  триггеры; security — Spring Security; config — конфигурация;
  exception — единый HTTP-формат ошибок. DTO команд и страниц находятся в dto.
  json владеет общей канонизацией/отпечатком JSON для квитанций и диагностики;
  не зависит от service/repository. IdempotencyService владеет lock/read/callback/save в service/idempotency;
  репозиторий квитанций не исполняет бизнес-callback и не кодирует JSON.
- Модель задания владеет инвариантами задания; проблема и сверка имеют
  отдельную модель, поскольку проблема ленты может не иметь задания.
  Очередь, история и квитанции не загружаются как неограниченные коллекции задания.
- Версии названия и обмена независимы. Хранимый формат квитанций,
  канонический отпечаток команд и JSON результатов сохраняют совместимость.
  Чтение использует внутренние проекции, не API DTO в JDBC.

## Spring и транзакции

- HTTP transport принадлежит ExchangeHttpConfiguration/ExchangeHttpProperties:
  один Spring-managed HttpClient, deadline всего тела и bounded чтение байтов.
  Ошибка размера — ошибка протокола; неопределённый исход PUT требует GET.
  Единственный SQL-владелец task_history, включая наблюдения, — JdbcTaskRepository;
  audit-log появляется только после commit реально вставленной записи.
- Generated MVC API используют useSpringBuiltInValidation. В backend external
  модели нужны только test source set; у эмулятора external server API остаётся в main.
- Constructor injection; штатная автоконфигурация Boot. Lombok
  @RequiredArgsConstructor/@Slf4j применяем для простого DI и логирования;
  конструкторы с валидацией/жизненным циклом остаются явными. Domain records
  не заменяем @Data. MapStruct использует общий для приложения MapStructConfig,
  Spring injection и unmappedTargetPolicy=ERROR; processors и версии заданы
  в root Gradle. Generated outputs только в build, не в Git и не в src.
- @Service/@Transactional на прикладных операциях, @Repository на JDBC-адаптерах. Не рассчитывайте на
  транзакционный proxy при вызове метода через this; проверяйте реальную границу.
- Короткая транзакция получает/сохраняет состояние; HTTP находится между
  транзакциями. Read-only операции помечаются явно, но readOnly не является
  заменой проверки прав. SecurityContext преобразуется в явного actor на границе.
- Создание + outbox + история + квитанция атомарны. Применение страницы ленты
  + курсор атомарны. Логи успешного коммита не должны утверждать успех отката.
- Для нескольких записей задавайте единый порядок блокировки; размер батча
  ограничен. Не захватывайте lease заранее для работы, ожидающей сетевой слот.
  batchUpdate не делает несколько транзакций атомарными автоматически.
- При изменении потоков/кэша сверяйтесь с
  [архитектурой](../docs/architecture.md#потоки-и-ограничение-параллелизма).
  Глобальный virtual flag меняет fixedDelay-планировщик; сохраняйте независимость
  фоновых задач и проверяйте TC-17/NF08. Пулы без измерений не увеличивать.

## Хранение и проверки

Эмулятор запускается отдельно, пишет в свою БД и следует тем же границам слоёв.
Flyway ведёт миграции каждого процесса с V1; применённые миграции сохраняются,
демоданные загружаются отдельной командой. Новая миграция нужна только для
реального изменения схемы; структурный рефакторинг сам по себе её не требует.

Чистые правила проверяются unit-тестами, SQL/транзакции — на PostgreSQL,
права/контракт — через API. Архитектурные тесты проверяют зависимости слоёв.
Unit-тесты адаптеров следуют пакетам владельцев; межслойные workflow-тесты
сгруппированы по сценарию в tasks и используют тег postgres.
Тесты размещаются в src/test/ соответствующего приложения, проверки запущенного
сервиса — в tests/. Команды — в [README](../README.md#сборка-и-проверки).
