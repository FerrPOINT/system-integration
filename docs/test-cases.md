# План приёмки

Сценарии TC-01–TC-15 проверяют исходное ТЗ; TC-16 — публикацию по поручению владельца. Результаты прогона указываются
отдельно с версией приложения, окружением и ссылкой на отчёт. Для интеграционных
проверок используются миграции и тестовый PostgreSQL, а внешний обмен
в сквозных проверках идёт через эмулятор.

Текущая автоматизация: `TaskWorkflowTest` проверяет HTTP-доступ, команды,
периоды и транзакционный откат; `ExchangeWorkflowTest` — очередь и входящие
снимки; `OperationsWorkflowTest` — сверки, передачу разбора и решения;
`ResultFeedTest` — остановку и восстановление чтения ленты через HTTP;
`EmulatorWorkflowTest` — независимый приём и четыре сбоя.
Браузерные сценарии находятся в `tests/e2e/{tasks,operations,themes,spacing,pagination}.spec.ts`,
перезапуски процессов — в `tests/e2e/recovery.mjs`.
Частичные проверки сценария не заменяют весь критерий из таблицы.

## Доставка и восстановление

Используйте тестовый PostgreSQL и отдельный эмулятор. Включайте режим по
свободному `reference` до создания задания. Для успеха задайте
`quantity: 40`, для бизнес-отказа — `quantity: 150`. В автоматических
проверках переходы контролируют тестовые фикстуры и часы. Переходите к
следующему шагу после наблюдаемой записи, события или ответа.
Режимы заданы в [аналитике](analysis.md#демонстрация).

| Проверка | Контрольные точки и доказательства |
| --- | --- |
| TC-01. Приём и исполнение | Удержите запуск исполнения в тесте. При недоступном эмуляторе POST возвращает ID, в БД уже есть задание, очередь и история. После первого валидного подтверждения снимите `ACKNOWLEDGED/PENDING` и независимый `GET` без итога. Разрешите исполнение и сопоставьте итог карточки с состоянием эмулятора. |
| TC-02. Повтор команды пользователя | Одновременно отпустите два POST с одинаковыми ключом и телом. Сравните ответы и проверьте одну запись задания и очереди. Изменённое тело с тем же ключом даёт `409`. Два разных ключа дают два ID операции. |
| TC-03. Потеря ответа и повтор отправки | Включите `DROP_RESPONSE_AFTER_EXECUTION`. Дождитесь `UNKNOWN`, затем уточняющего GET по тому же ID. При удержанном итоге проверьте `ACKNOWLEDGED/PENDING`. Снимите независимый GET с `executions: 1` и `result.completedAt`. После перезапуска эмулятора повторите PUT с исходными ID и телом. Сохраните HTTP 200 и GET с прежним итогом, снимите режим и дождитесь применения итога в карточке. В отдельном прогоне одновременно отправьте два PUT нового ID, затем два PUT уже исполненного ID. Проверьте одну операцию, одно исполнение и ответы 202/200 для первого принятия и 200/200 для повтора. |
| TC-04. Дубликат и позднее событие | После итога версии 2 обработайте его копию с новым курсором и позднюю версию 1. Сравните состояние и курсор. Подайте изменённую версию 2 через фикстуру. Прочитайте проблему через API, сравните сохранённый локальный и отклонённый снимки. Повторите конфликт с новым курсором до и после закрытия проблемы. Число проблем остаётся прежним, курсор продвигается. Иное конфликтное содержимое создаёт отдельную проблему. |
| TC-05. Перезапуск | Отдельно остановите backend после коммита очереди и после внешней фиксации до записи ответа. Проверьте GET перед новым PUT после истечения захвата. Перезапустите эмулятор после приёма до исполнения и после коммита итога до публикации. Проверьте продолжение и одно исполнение. Вызовите откат входящей транзакции после изменения задания до записи курсора. Ни изменение, ни курсор не должны сохраниться, после повторного чтения событие применяется один раз. Отдельно перезапустите PostgreSQL на том же томе и сравните записи. |
| TC-06. Расписание и захват | На управляемых часах проверьте интервалы 2/5/15/60 с и остановку после пятой неудачи без шестого вызова. При долгом простое и перезапуске срок и счётчик сохраняются. Удержите старый HTTP-ответ, дождитесь истечения захвата и завершения новой попытки, затем выпустите старый ответ. Он сохраняется только в диагностике и не меняет новое состояние или расписание. После восстановления связи проверьте тот же ID и одно исполнение. |

Дополнительно в TC-06 проверьте ручной повтор ожидающей записи. Команда
оператора с причиной и актуальной версией переносит срок на текущее время,
сохраняя ID и счётчик. При активном захвате запрос отклоняется.
Повтор успешного ключа возвращает тот же ответ без новой попытки.
Для `409 OPERATION_CONFLICT` и неверного тела ответа проверьте
приостановку в `NEEDS_REVIEW`. Запрос повтора без актуальной сверки
отклоняется. В отдельных прогонах исправьте источник и сверяйте отсутствие
операции либо тот же запрос с `executions: 0`, после чего возобновите
с GET по прежнему ID. Если итог уже готов, повтор отклоняется, а оператор
применяет его через `APPLY_EXTERNAL_RESULT` по свежей сверке.
При несовпадении внешнего запроса повтор запрещён. Явное подтверждение
разбора с причиной завершает отправку в `STOPPED`.
Поздний итог создаёт наблюдение для оператора. Он не меняет бизнес-результат
без отдельного решения. При несовпадающем запросе применение запрещено.
В отдельном прогоне с совпадающим запросом проверьте применение допустимого
итога через `APPLY_EXTERNAL_RESULT` после свежей сверки.
Для неверного курсора проверьте остановку на последней сохранённой
позиции, диагностику общей проблемы без локального снимка задания
и продолжение после исправления источника. При плохом снимке с
валидным курсором следующая запись ленты обрабатывается.

В TC-04 отдельно проверьте идентичность раннего события. Удержите отправку
задания, создайте в эмуляторе операцию с тем же ID и другим `quantity`.
Прочитайте её событие до получения ответа PUT внутреннего приложения.
Оно сохраняется как конфликт, доставка и бизнес-результат остаются прежними.
Событие с правильными ID и запросом в отдельном прогоне принимается до
подтверждения PUT. После запуска отправки при конфликтующем содержимом
ответ `409 OPERATION_CONFLICT` приостанавливает доставку.

Для обоих состояний `NEEDS_REVIEW` и `STOPPED` в TC-06 подайте новый
`RUNNING` версии 1 и конечный снимок версии 2 с правильным запросом.
Оба остаются наблюдениями до решения оператора. Отдельно подтвердите,
что повтор каждого наблюдения сохраняет количество проблем.
В отдельном прогоне с `ACKNOWLEDGED` проверьте дубликат принятого
снимка и старую версию. Они сохраняют состояния и количество проблем.

В SI-03.6 и SI-03.7 читайте историю и позицию ленты из PostgreSQL.
После SI-04.2 в итоговом прогоне дополнительно проверяйте доступную
историю через API. Сохраняйте обезличенные ответы, состояния и ID операций
в отчёте прогона.

## Передача разбора и права

Для TC-07 и TC-08 подготовьте двух инициаторов с разными заданиями и двух
операторов для автоматической проверки. В демонстрационном наборе достаточно
одного оператора.

1. Для TC-07 включите `DROP_RESPONSE_AFTER_EXECUTION`. Дождитесь
   подтверждения доставки через GET при удержанном итоге. Первый оператор
   сверяет задание. Сохраните `DIFFERENCE`, локальный снимок без итога,
   внешний итог из GET и открытую проблему. Первый оператор берёт разбор
   на себя, после чего сохраните текущую версию. До снятия режима фоновая
   лента оставляет исходное расхождение стабильным.
2. Второй оператор берёт тот же разбор с текущей версией. Проверьте нового
   ответственного, увеличение версии и событие с прежним и новым
   ответственными, автором, временем и ID проблемы. Повторите команду с
   исходным ключом. Число событий передачи остаётся прежним. Отправьте
   новый запрос с устаревшей версией и проверьте `409` и сохранение назначения.
3. Снимите режим и дождитесь применения итога из ленты. Отправьте решение
   с текущей версией проблемы и ID прежней сверки. Ожидайте
   `409 SNAPSHOT_STALE`. Выполните свежую сверку с `MATCH`, подтвердите
   разбор с причиной и повторите команду с прежним ключом. Проверьте одну
   запись решения с автором, временем и причиной. В отдельном прогоне
   примите внешний итог по актуальной сверке до снятия режима. После
   снятия режима тот же итог из ленты не создаёт нового эффекта. Для `UNAVAILABLE`
   проведите отдельную сверку при остановленном эмуляторе и сравните
   состояние задания до и после.
   После следующей сверки и перезапуска прочитайте обе прежние сверки по
   ID из истории и решения. Оба снимка и автор сохраняются. Чтение сверки
   с ID другого задания возвращает `404`.
4. В TC-08 запросите карточку, историю и изменение названия у владельца
   и второго инициатора с действительными сессиями и токенами CSRF.
   Для второго инициатора все три запроса дают `404`. Его запрос
   операторской сверки даёт `403`. Оператор читает карточку и историю
   и может выполнить сверку. Запрос без сессии даёт `401`, изменение
   владельцем с неверным CSRF-токеном — `403 CSRF_INVALID`. После передачи разбора и перезапуска
   повторите проверки чтения и сравните прежние события и авторов.
   Сохраните статусы ответов и обезличенные события истории.
   Инициатор получает `403` при чтении операторской сверки и попытке
   взять разбор. Без сессии оба маршрута возвращают `401`.

## Интерфейс и клавиатура

В TC-09 повторите один маршрут при 390 и 1440 px. Инициатор входит,
создаёт задание и открывает его из реестра. Оператор открывает проблему,
запускает сверку и читает результат. Пройдите формы, список и действия
через Tab, Shift+Tab, Enter и Space. Проверьте видимый фокус, подписи полей
и отсутствие горизонтальной прокрутки всей страницы. При 390 px реестр
показывает карточки с доступом к тем же действиям.

В трёх отдельных прогонах используйте управляемую задержку API,
пустую выборку и ошибку с последующим успешным ответом. Проверьте
соответствующие состояния загрузки, пустого списка и ошибки, возможность
повторить запрос и восстановление списка. Сохраните скриншоты двух
ширин и результат браузерного прогона.
Отдельно повторите успешный ключ изменения после последующего обновления
задания. Подтвердите, что сохранённый ответ команды сменяется актуальной
карточкой после чтения. Ошибка этого чтения оставляет форму доступной
для повтора обновления без повторного изменения.

## Демо и проверка эмулятора

Для TC-10 используйте одну версию кандидата. Рабочие команды запуска,
миграций, начальной загрузки и демонстрации войдут в инструкцию на SI-05.1.
Включайте режимы на новых номерах заявок из тестовой сети и снимайте
после проверки. Для каждого шага приложите указанное подтверждение.
Для перезапуска до записи локального ответа используйте команду сквозного
теста с контрольной точкой из TC-05. Она подтверждает внешнюю запись до
остановки backend и сверяет историю после запуска. Удержанный итог
выпускается после сверки по шагу 1.

| Шаг | Что должен увидеть проверяющий | Подтверждение |
| --- | --- | --- |
| Подготовка | Чистая копия запускается с пустой БД. После миграций и загрузки доступны два инициатора, оператор и минимум шесть заданий с разными исходами. | Версия, команды, результаты запуска, список демоучёток без паролей в отчёте и снимок реестра. |
| 1. Потеря ответа и перезапуск | `DROP_RESPONSE_AFTER_EXECUTION` фиксирует итог до ответа. После перезапуска backend продолжает уточняющим GET по исходному ID, после перезапуска эмулятора повторный PUT возвращает 200. До выпуска итога оператор сверяет расхождение, затем выполняет свежую сверку и фиксирует решение. | История обмена, два независимых GET с одинаковым итогом, временем и `executions: 1`, обе сверки и решение. |
| 2. Временная недоступность | UNAVAILABLE сохраняет задание в очереди; после пяти вызовов доставка приостановлена. Снять сбой, выполнить сверку и разрешить новую серию оператором. Приём и исполнение проходят под тем же ID. | Снимки карточки до и после, журнал попыток, GET эмулятора до и после снятия режима. |

## Проверка кэша при нагрузке

Правила — в [архитектуре](architecture.md#чтение-кэш-и-повтор-команд).

## TC-18. Расширенная нагрузка и восстановление после пика

Профиль capacity выполнен на 20/40/80 клиентах для чтения и смеси;
отчёт и границы применимости — в [текущей стадии](current-stage.md).
Используется существующий tests/load runner с явным выбором профиля:
NF08 остаётся неизменным. Отдельный профиль capacity и его отчёт не заменяют NF08.
Данные — ровно 10 000 завершённых исходных заданий в выделенных тестовых БД;
подготовка через штатный API, роли разделены, записи для изменений не пересекаются.
Лимит четырёх контейнеров остаётся 2 CPU / 4 ГиБ.

1. На 20, 40 и 80 клиентах отдельно исследовать чтение и смесь операций NF08.
   На ступень — 15 с прогрева и 60 с измерения; отчёт разделяет режимы/ступени.
   Число записей в начале каждой ступени фиксируется, COUNT и страницы проверяются.
2. До/после ступени и во время неё снимать CPU/память контейнеров, состояние БД,
   число ожидающих/принятых операций и возраст очереди. Зафиксировать p95,
   throughput, ошибки/тайм-ауты, скорость доставки/завершения и внешние итоги.
3. После прекращения записи наблюдать очередь до 180 с. Ожидание отдельно от p95
   API; записать сокращение, остаток и возраст. Следующая ступень записи начинается
   после опустошения очереди. Если она не опустела, эскалация останавливается,
   предел/остаток сохраняются в отчёте; состояние не обнуляется для видимости успеха.
4. Прекратить эскалацию при выходе p95 за 2/3 с, ошибках, OOM/перезапуске,
   очереди свыше 20 000 либо возрасте свыше 180 с. Отказы генератора из-за его
   данных/прав/ревизий исправляются отдельно. Перегрузка не разрешает потерю
   уже подтверждённых данных или повтор исполнения.
5. Независимо проверить результаты/счётчик исполнения, историю и доступ другого
   инициатора после нагрузки. Повторить успешную команду по прежнему ключу.
   Итог указывает максимальную пройденную ступень отдельно для чтения и записи;
   более высокая не объявляется поддерживаемой.

Холодное чтение означает новую вкладку/пользовательский кэш; кэш ОС и общей БД
не сбрасываем. Профиль не доказывает длительную суточную устойчивость,
несколько реплик или работу на миллионах записей. Если нужна такая гарантия,
сначала определяется отдельный профиль и бюджет, затем выполняется замер.

## Регрессия общего HTTP deadline

После исправления Java 25 клиента должны проверяться задержанные заголовки,
ранние заголовки с зависшим телом, нормальный полный JSON и работоспособность
клиента после отмены. Тайм-аут даёт неопределённый исход, connection refusal —
определённую недоступность соединения. Для зависшего ответа проверяются отмена
underlying future и освобождение клиента при close.
ExchangeClientTest реализует четыре сценария на настоящем loopback HTTP-сервере
без Spring и БД. Пройдены все четыре и остальные модульные тесты.
Регрессия падает на прежней реализации чтения тела и на варианте без cancel;
после восстановления текущего кода снова проходит. Отдельный отчёт —
tests/results/deadline-regression.json.

## UI-15. Desktop-пагинация и мобильная лента

- На desktop реестр заданий, история и разборы рассчитывают размер страницы из
  реальной области и элементов. При resize сохраняются фильтры и запись,
  с которой начиналась прежняя страница; текущий `page`/`size` отражается в URL.
- На 390/1440 px серверные страницы обходятся без потерь: новые сценарии
  создают 40 заданий, события истории и восемь проблем только в отдельном
  system-integration-load. Фикстуры проблем удаляются по собственным UUID.
- Desktop-навигация находится ниже содержимого у нижнего края области при заполненном,
  коротком и пустом списке. Если один элемент
  выше области, прокручивается содержимое, а навигация остаётся доступной.
- До 760 px следующие страницы по 20 записей добавляются при прокрутке документа.
  Отдельных скроллеров и номеров страниц нет; все записи и события доступны
  без повторов. Resize внутри мобильного диапазона сохраняет загруженную ленту.
- API принимает размеры 1–100; без параметра сохраняет страницу из 20 записей.
  Неверные размеры дают 400. Инициатор не видит чужих заданий/истории и не
  получает операторский список при любом размере страницы.
- Автоматизация: PaginationWorkflowTest, PageTest, frontend/tests/page-size.test.mjs,
  дополненные клиентские тесты, tests/e2e/adaptive-pagination.spec.ts и UI-09.
  Проверки используют настоящий API/БД; новый UI не публикуется этим прогоном.

## UI-19. Мобильная компоновка и ошибки подгрузки

- На 320 × 568, 348 × 672, 390 × 844 и 390 × 480 нет горизонтального
  переполнения и внутренних скроллеров списка. Компактные карточки сохраняют
  статусы, заявку/количество и дату; вся карточка — обычная ссылка.
- Тема и выход находятся в мобильном меню; фильтры открываются рядом
  с заголовком. Диалоги сохраняют доступность и возвращают фокус.
- Подгрузка имеет один запрос в работе. Ошибка сохраняет предыдущие карточки,
  останавливает автоповтор и даёт явный повтор. Конец ленты не запрашивается снова.
- Фильтры создают новую последовательность с первой страницы. Browser Back и
  стрелка карточки возвращают условия, загруженные страницы и положение списка.
- `mobile-feed.spec.ts` проверяет задержку/ошибку HTTP на контролируемой выдаче;
  UI-15 отдельно обходит реальные серверные страницы заданий, разборов и истории.

## UI-16. Создание задания в модальном окне

- `/tasks/new` открывает одну форму поверх реестра, включая прямую ссылку.
  Фильтры/страница остаются в URL; пустая форма закрывается по Escape, крестику
  и «Отмена», фокус возвращается на создание задания.
- Фокус остаётся внутри модалки; поля и действия доступны с клавиатуры.
  Заполненную форму защищает AlertDialog, включая закрытие кликом снаружи
  и browser Back. «Продолжить заполнение» сохраняет поля и возвращает фокус.
- При создании поля/закрытие заблокированы. Ошибка сохраняет поля и ключ
  команды; безопасный повтор и очистка приватного кэша проверяются UI-10–UI-12.
  Успех открывает карточку принятого задания.
- На 390 × 480 тело прокручивается, действия остаются в пределах экрана.
  Проверки: task-modal.spec.ts, обновлённые tasks/spacing/themes/pagination.

## Архитектурные регрессии frontend

FR-00–FR-12 [плана frontend](frontend-refactoring-plan.md) сохраняют исходные
UI-сценарии и добавляют проверки границ состояния и ошибок:

| Область | Проверка | Ожидаемый результат |
| --- | --- | --- |
| Form identity | Тёплые/холодные A/B, равные revision, refetch той же записи | Новый taskId создаёт новый form session; прежний ID сохраняет draft и expected revision. |
| Write/read outcomes | Receipt получен, follow-up GET отказал | Команда остаётся принятой; retry выполняет только чтение. Неизвестный исход сохраняет input/key. |
| Unknown create | Обрыв после записи, повторный отказ CSRF/400, новый сознательный create | Отправленные поля заблокированы; повтор сохраняет input/key. Уход предупреждает о возможном сохранении; только после явного discard новая команда получает новый key. |
| Create receipt | 201 с отсутствующим, числовым или неверным taskId | Результат остаётся неизвестным; нет GET по невалидному ID и ложного success. Валидный replay подтверждает ту же команду. |
| Session lifecycle | Initial/background 502, dirty/pending форма, настоящий 401 и смена роли | Background failure сохраняет форму/observer; initial retry выполняет чтение; 401/смена identity удаляют приватное состояние. |
| Guard | Cancel, route/Back, reload, pending, focus | Один guard управляет подтверждением, pending блокирует уход, discard возвращает правильный фокус. |
| Operator basis | Новая сверка/revision или внешнее закрытие во время ввода | Основа draft не обновляется молча, submit блокируется до явного обновления; причина сохраняется. |
| Router | Прямой URL, роль, not-found, render/chunk error | Один route tree, безопасный fallback и восстановление с доступной оболочкой. |
| Collection budget | 20/100/1000/5000 записей; refetch и polling | Не более 5 страниц/100 записей кэша/DOM и 5 GET; нет копии DTO в state/storage. |
| Collection access | Полный обход 5000, обратная загрузка, Back после Query GC | Нет пропусков в стабильном наборе, вытесненные записи доступны; ID/offset восстанавливаются. |
| History navigation | Глубокое warm-окно → сверка → Link к заданию; затем native Back | Новая entry открывает summary и page 0; старая entry восстанавливает прежние ID/offset. Кэш остаётся ограниченным. |
| Changed/error position | Вставка, удаление anchor, сокращение списка, отказ чтения/storage | Стабильный доступный anchor или явное состояние; нет скрытого API-успеха и autoretry цикла. |
| Architecture gates | Positive/negative lint fixtures, StrictMode, strict TS | Неверные imports/cycles/generated calls отклоняются; lifecycle исправлен без отключения правил. |

Component fixtures находятся в tests/components и frontend/tests, выполняются
без БД через перехват API; 74 интеграционных UI-сценария используют отдельный
локальный Compose. Их результаты и IAB-приёмка фиксируются раздельно в current-stage.
