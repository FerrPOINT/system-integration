# Производительность обмена: план и журнал решений

## Цель и исходная точка

Работа начинается от тега baseline/pre-batch-optimization-2026-11-15,
коммит 7860311; приложение квалифицировано на 3e9e6da.
Предыдущий [аудит](iterative-audit-2026-11-15.md) остаётся историческим
срезом. Это отдельная доработка, без слияния или публичного развёртывания.

Симптом: API принимает задания быстрее фоновой доставки. В предыдущем NF08
по выборкам за 120 с поступало 117,09 задания/с, эмулятор принимал 37,30/с;
очередь росла на 79,79/с. p95 до первой попытки 125,30 с, внешнего
исполнения 125,912 с. Пустая очередь подтверждена через 109,024 с после
окончания HTTP-окна. В 45 снимках не обнаружены блокирующие сессии;
это не исключает коротких ожиданий. Одиночный indexed claim занимает
0,05–0,07 мс в синтетическом SQL-прогоне, не под конкурентной нагрузкой.

## Критерии до начала экспериментов

- Сохранены исходные гарантии ТЗ, права, форматы квитанций и миграции;
  сеть вне транзакций, один порядок блокировок, постоянные ограниченные
  повторы, отсутствие потерь, повторных эффектов и пропущенных событий.
- Исходный NF08: 5000 исходных записей, 20 клиентов, 30 с прогрева,
  120 с измерения; p95 чтения ≤ 2 с, изменения ≤ 3 с, ошибок 0.
  Суммарно не больше 2 CPU / 4 ГиБ для четырёх контейнеров.
- Кандидат повторяемо улучшает внешнюю задержку и очередь на одинаковом
  профиле. Практическая цель — минимум 30% снижения p95 внешнего исполнения
  и времени от конца HTTP-окна до подтверждения пустой очереди относительно
  свежего контроля. Это критерий выбора эксперимента, не SQL-таймаут
  и не обещание произвольной скорости.
- Устойчивая скорость определяется существующим create-only steady,
  отдельно от смешанного NF08. После поиска границы выбирается ступень
  ниже неё и подтверждается тремя последовательными фазами по 300 с
  без сброса очереди между фазами. Для устойчивой ступени нет ошибок,
  пропусков arrivals, потерь или устойчивого роста количества/возраста
  очереди. Сравниваются первый и последний 60-секундные окна каждой фазы:
  рост среднего pending не больше max(2, 2% целевой частоты), рост p95
  возраста не больше 1 с; после прогрева max возраста ≤ 5 с.
  Числа относятся только к тестовой классификации устойчивости.
- Пределы подтверждаются метриками, а не увеличением общего ресурса.
  Прогон с растущей очередью может доказать корректность при перегрузке,
  но не устойчивую пропускную способность.
- Проверены изменения SQL через EXPLAIN ANALYZE/BUFFERS/WAL в тестовых БД,
  конкуренция и восстановление отдельно. Итоговый повторный аудит не
  оставляет подтверждённых устранимых замечаний в согласованном объёме.

Изменение схемы само по себе не требуется. Физические партиции, новая
очередь/брокер, Redis, JPA и Spring Batch не входят в выбранное решение.
SKIP LOCKED уже даёт независимую работу с заданиями. Общий курсор публикации
сохраняется: большие позиции не могут стать видимыми раньше меньших.
Приём результатов сохраняет атомарность страницы и курсора.
При подтверждённых ожиданиях рассматривается меньшая страница, а не
незаметное ослабление её транзакционного контракта.

Отвергнутые варианты удаляются из итогового кода; результаты остаются здесь.
Логи, JFR и JSON прогонов находятся в ignored tests/results/performance-cycle-2026-11-15,
не копируются в Git. Все команды работают только с system-integration-load,
si_test/si_emulator_test и loopback. Генератор на Firebat1 вне лимита четырёх
контейнеров; это не тест публичной сети. Соседние приложения не останавливаются.

## Источники и выбор механизма

Версии: Java 25, Spring Boot 4.1.2, Spring Framework 7.0.10,
pgJDBC 42.7.14, PostgreSQL 18.7.

- [Spring JDBC batch](https://docs.spring.io/spring-framework/reference/data-access/jdbc/advanced.html):
  уменьшает обращения к БД; транзакция и обработка результата задаются отдельно.
- [PostgreSQL SKIP LOCKED](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE):
  применим к очереди, не заменяет порядок блокировок и полную выборку реестра.
- [PostgreSQL partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html):
  нужен подходящий ключ pruning; ограничения уникальности включают ключ партиции.
  Текущий indexed claim и общий курсор не дают оснований вводить партиции.
- [Linux cgroup CPU](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files):
  cpu.stat показывает nr_throttled/throttled_usec; CPU% сам по себе причины не доказывает.
- [Java 25 virtual threads/JFR](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html):
  виртуальные потоки уменьшают стоимость ожидания, не увеличивают CPU.
- [PostgreSQL SQL statistics](https://www.postgresql.org/docs/18/pgstatstatements.html):
  агрегаты SQL полезны при необходимости; включение только на частной QA-БД,
  без перезапуска обычного PostgreSQL.

## Журнал

### E00 — начало, 15 ноября 2026

Проверены Firebat1, checkout, чистое дерево и tag→7860311.
main 223bc86 и PR #9/#10 сохранены. Активных QA/load/build процессов
и контейнеров system-integration-load нет; обычных контейнеров 11.
Создаётся отдельная ветка perf/bounded-batching.

Исходный вывод — гипотеза CPU/стоимости транзакций, не доказанная причина.
Первое изменение ограничено измерениями. Значения CPU, задержек и исходы
контроля будут внесены после фактического запуска.

### E01 — контроль и исследование причины

Кандидат 2893f1a: прикладные исходники совпадают с тегом.
NF08 PASS: 55 830 запросов, ошибок 0, read p95 98,47 мс / write 97,20 мс.
За 120,016 с выборок создавалось 116,25 задания/с, принималось 37,40/с.
Внешнее исполнение p95 126,071 с; до первой попытки 125,578 с;
подтверждение пустой очереди через 110,156 с после HTTP-окна.
Целостность и однократное исполнение подтверждены; blocking samples = 0.

Новые cgroup-дельты: backend в среднем 0,516 CPU, throttled в 49,0%
активных периодов; PostgreSQL 0,910 CPU и 68,2%; эмулятор 0,074 CPU
и 2,0%. За окно записано около 81,6 МБ WAL, wal_buffers_full не рос.
throttled_usec не трактуется как процент wall time: несколько runnable
потоков могут суммировать время ожидания. Наблюдение не доказывает, что
одного увеличения backend хватит: одновременно ограничена БД.

Исследование: проверены cpu.stat по документации ядра и pg_stat_wal по
PostgreSQL 18. За основу оставлены штатные счётчики вместо нового
мониторингового сервиса. Предыдущие цифры NF08 воспроизвелись; измерения
не внесли заметного изменения профиля. Receipts: control-summary.json
и control-nf08.json в каталоге результатов цикла.

Следующий E02 — только распределение CPU: backend 0,8, PostgreSQL 0,95,
эмулятор 0,2, frontend 0,05, суммарно 2,0. Память, исходники, пулы,
параллелизм и периоды прежние. Частично используется невостребованный
ресурс эмулятора/frontend; снижение доли БД небольшое, но его влияние
нужно проверить, не объявлять заранее улучшением.

### E02 — перераспределение CPU отвергнуто

Кандидат 7b24c5b, прикладной код прежний. NF08 PASS и целостность сохранена:
55 621 запрос, ошибок 0, p95 чтения 100,08 мс / изменения 97,87 мс.
Однако внешнее исполнение p95 176,376 с, end-to-empty 152,451 с;
приём эмулятора 35,61/с вместо 37,40/с контроля. Общее улучшение отсутствует.

Backend throttled periods снизились с 49,0% до 5,2%, но PostgreSQL вырос
с 68,2% до 99,5% и использовал 0,950 из доступных 0,95 CPU.
Просто передать ресурс API неправильно: узкое место сместилось/усилилось
на стороне БД. Возможное влияние размеров прогрева/числа новых записей
сохранено в исходном отчёте; один прогон не используется для точной
оценки процента регрессии. Этот вариант не входит в итоговый Compose.

Исследование: pg_stat_statements PostgreSQL 18 показывает вызовы, суммарное
время, строки, shared hits и WAL по нормализованному SQL; total_exec_time
не является чистым CPU-time. Следующий короткий диагностический прогон E03
с исходными CPU-долями использует этот штатный механизм только на частном
PostgreSQL. Данные текущего QA-набора сохраняются; это не NF08 и не оценка
приёмочной скорости, а поиск дорогих запросов на уже выросшей таблице.
Обычный PostgreSQL и публичное приложение не перезапускаются.

### E03 — дорогой claim подтверждён; выбран упорядоченный поиск

Диагностический mixed30 на выросшей QA-БД показал два дорогих SQL:
COUNT — 828 вызовов / 1,556 с суммарного исполнения / 1,854 млн shared hits;
claim — 460 / 1,528 с / 0,894 млн hits. Это диагностические агрегаты,
не p95 CPU и не полный NF08. Файл sql-statements.json содержит все запросы.

Во время второго короткого прогона EXPLAIN реального claim показал
79 task lookups перед сортировкой и LIMIT 1; оценка join — одна строка.
При редком активном статусе над большим принятым населением плоский join
недооценивает результат. Старый синтетический тест с проанализированной
заполненной очередью этот вариант не воспроизводил. Долгая очередь
усиливает лишнюю работу запроса, несмотря на существующий due-индекс.

Исследованы LATERAL и границы row locking в PostgreSQL 18, а также
is_simple_subquery в исходниках PostgreSQL. Выбор: сначала упорядоченная
очередь, затем lateral lookup и lock одного подходящего задания.
Сортировка очереди находится до блокировки задания. Более короткий
lateral без упорядоченного подзапроса отвергнут: при другом плане
верхняя сортировка может заблокировать лишние задания до LIMIT.
OFFSET 0 не нужен: ordered subquery уже сохраняет требуемую границу.

В rollback-фикстуре 500 due заданий над выросшей таблицей, прямой и обратный
порядок вариантов: исходный claim 3,985/4,023 мс; ordered-lateral
0,206/0,216 мс. В первом валидном проходе shared hits 2853 → 35.
Одиночные цифры подтверждают механизм, но ещё не общую пропускную способность.
Начальная проба claim-variants.json оказалась невалидной: clock_timestamp
создавал due_at позже statement_timestamp всего SQL-пакета и возвращалось 0.
Она исключена из доказательства; claim-variants-valid.json задаёт due_at
в прошлом и проверяет Actual Rows=1 для каждого плана.

Изменён только JdbcExchangeRepository.lockDueExchange: схема, очередь,
права, lease, число потоков, транзакционные границы и статусы прежние.
Никаких новых полей/кэшей/процессов. Это причинное исправление перед
экспериментом с батчами; группировка транзакций не должна маскировать
лишний обход population в каждом claim.

Регрессия RED на прежнем SQL воспроизвела обход завершённой population.
GREEN: DeliveryClaimPlanTest (2) и ExchangeWorkflowTest (18), без ошибок.
Проверены forced-sequential план, доступность соседней строки и SKIP LOCKED.
Проверка EXPLAIN — тест конкретного алгоритма; runtime SQL-бюджетов и
дополнительных отказов API не добавлено. Следующий E04 — полный NF08 с
новым claim, исходными CPU и без pg_stat_statements preload.

### E04 — SQL-план улучшен, но общий предел остался

Кандидат cb57ea6, исходные CPU и четыре отправителя. NF08 PASS:
53 308 запросов, ошибок 0, read/write p95 99,85/98,22 мс;
внешнее исполнение p95 124,782 с, end-to-empty 107,234 с.
Приём по выборкам 34,61/с при поступлении 110,99/с; целостность сохранена.
Это не существенный общий выигрыш относительно контроля 126,071/110,156 с.
Локальная лишняя работа claim устранена, но она не объясняла весь предел.

Исследование после результата: Java 25 virtual threads дают дешёвое ожидание,
а фактический параллелизм всё равно ограничен координатором. p95 попытки
98,85 мс; четыре занятых слота при такой длительности согласуются с
наблюдаемыми десятками доставок/с, но p95 не подставляется вместо среднего
в формулу пропускной способности. Увеличение Hikari не обосновано.

Следующий E05 меняет ровно один фактор: восемь вместо четырёх незавершённых
доставок. Лимит 32 за проход, individual virtual threads, независимый
refill слота, HTTP deadline, lease и отсутствие сети в транзакции прежние.
Пулы БД и 2 CPU / 4 ГиБ не меняются. Это ограниченный параллелизм существующего
владельца, не новая очередь/сервис. Пять адресных unit-тестов проходят,
включая одновременный старт восьми слотов без девятого lease и прогресс
быстрых ответов при одном медленном. Результат NF08 ещё не получен.

Попутно уточнено название plan-regression: её валидная population —
ACKNOWLEDGED/PENDING, то есть уже доставленные задания, не обязательно
получившие терминальный итог. Условия и assertions теста не менялись.

### E05 — восемь слотов: небольшой выигрыш, цель ещё не достигнута

Кандидат bdf4995. NF08 PASS, ошибок 0, 53 610 запросов;
read/write p95 99,32/98,24 мс. Внешнее исполнение p95 112,310 с,
до первой попытки 104,989 с, end-to-empty 102,095 с.
Приём 42,84/с против 34,61/с предыдущего среза; CPU/пулы прежние.
Целостность подтверждена, blocking samples 0. У эмулятора p95 ожидания
исполнения вырос до 12,21 с. Это полезный, но недостаточный результат,
не заявленный окончательный PASS оптимизации.

Исследование следующей границы: общий duration попытки включает HTTP
и транзакционный finish, а последовательный claim измерялся только SQL.
Задержки пула/JVM/commit не видны в одиночном EXPLAIN. До нового изменения
пулов или размера батча разделяем эти фазы по штатному логированию
существующего координатора: claim на DEBUG, httpMs/finishMs в существующей
записи доставки. Новых сервисов/зависимостей/таймерных хранилищ нет.
Пять unit-тестов координатора проходят. E06 — короткий диагностический
mixed30 на текущем выросшем QA-наборе с DEBUG только в частном backend;
это не нагрузочная квалификация и не сравнение скорости с NF08.

### E08 — устранена сериализация независимых захватов

Исследование Java 25 virtual threads и PostgreSQL Read Committed/SKIP LOCKED:
один зарезервированный слот может владеть всей операцией claim→HTTP→finish.
Выбран этот вариант вместо группового захвата нескольких task в одной
транзакции: он устраняет последовательное ожидание, сохраняя прежние
короткие транзакции и единственный task lock. Для batch claim потребовались
бы дополнительные правила общего порядка нескольких task и новая форма
результата; пока они не нужны для устранения подтверждённой причины.

Координатор делает одну начальную проверку, чтобы пустая очередь не
порождала восемь SQL-запросов каждый tick. После неё каждое свободное место
запускает отдельную virtual task, которая сама получает lease, вызывает
HTTP и сохраняет результат. Pending-list остаётся единственным владельцем
лимита восьми незавершённых работ; максимум 32 попытки захвата за проход.
Нет lease для работы, ожидающей свободного слота; ошибки и все запущенные
работы наблюдаются до выхода из прохода.

Дополнительно воспроизведены две гонки старого контракта: кандидат SELECT
может предшествовать уже зафиксированному lease или будущему due_at.
До исправления такой кандидат прерывал ещё действующий lease либо
обходил время следующего повтора. lockQueue теперь вычисляет актуальную
eligible под блокировкой, а service проверяет её до любого изменения
счётчика/попытки. Это временная проекция БД, не новое хранимое состояние.
Порядок task→queue и авторитет часов PostgreSQL сохранены.

RED: задержанный второй claim блокировал остальные; два сценария stale
candidate также падали. GREEN: шесть unit координатора; 22 PostgreSQL
проверки (новые гонки, план и прежний workflow), затем добавлен и пройден
стресс-сценарий с 32 операциями через реальный PostgreSQL и восемь слотов:
32 уникальные доставки, одна попытка на операцию, без INTERRUPTED.
Mock применяется только для фиксации устаревшего кандидата в двух
детерминированных регрессиях; очередь/lease/счётчики там реальные.

Источники: [Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED),
[virtual tasks](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html),
[Hikari sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing).
Следующий шаг — полный NF08 на этом кандидате, исходных ресурсах и без DEBUG.

### E09 — явный текущий контракт результата claim

Вместо null введён один внутренний ClaimResult: CLAIMED с попыткой,
SKIPPED без попытки и EMPTY без кандидата. Все реальные потребители,
включая SQL-профилировщик, переведены на этот контракт; старого метода
или fallback-адаптера нет. REST, сохранённые receipts и схема БД прежние.
Это необходимое различение подтверждённых исходов, не обёртка на будущее.

RED: удерживаем семь HTTP-ответов, второй candidate — SKIPPED. Старый
координатор заканчивает проход и не запускает девятый selection.
GREEN: пропущенный кандидат освобождает слот для следующей работы;
восемь реальных lease остаются пределом. EMPTY заканчивает проход.
В начальной проверке SKIPPED также не скрывает готовое задание;
обслуживание ограничено общим максимумом 32 selections за проход.
Действительно пустая очередь всё ещё стоит один SELECT.

Пройдены 9 unit координатора и 46 PostgreSQL-тестов: 3 concurrency,
2 plan, 18 exchange workflow, 2 historical review и 21 operations workflow.
Детерминированный RED сохранён; положительные, пустые и ограниченные
maintenance-сценарии проверены. Следующий шаг — свежий NF08 на полном
кандидате E09. Архитектура остаётся без новых процессов, пулов, миграций
и группового владения task locks; эксперименты с batching эмулятора
и устойчивая нагрузка ещё не завершены.
