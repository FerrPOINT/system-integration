Исходная квалификация: 15 ноября 2026 года.
Исследованы исходники `ca174e7`; прикладной кандидат — `fb532b0`.
Архитектурный проход и SQL-эксперименты обновлены 16 ноября 2026 года.
Сначала сокращаем работу текущей архитектуры при неизменных ресурсах.
Баланс CPU/памяти и перенос frontend в отдельную ресурсную группу отложены.
Цикл P0–P6 реализован и проверен на кандидате 6e66aa3 при прежних ресурсах.
Приняты только подтверждённые простые изменения; итог — раздел 11.5,
диагностические эксперименты и ограничения — раздел 10.
Текущий короткий список после обсуждения отставания UI — раздел 12.

Этот файл объединяет ресурсы Compose, варианты SQL/кэширования/батчей,

## 1. Отложенный баланс ресурсов и корневой Compose

Этот раздел сохранён для следующего ресурсного этапа. До завершения
архитектурных экспериментов Compose, CPU, память и формулу учёта ресурсов
не меняем: эффект архитектуры должен сравниваться на прежних условиях.
Целевое решение пользователя для позднего этапа:

- Основной файл запуска — существующий [compose.yml](../compose.yml).
  Новый `compose.local.yml` не создаём.
- Frontend/Nginx получает отдельные лимиты с запасом.
- Backend + PostgreSQL + эмулятор суммарно ограничены **2 CPU / 4 ГиБ**.
- Браузер, генератор и сборка не входят в эти runtime-лимиты.
- Новая Redis/реплика/служебный worker, если появится, не получает «бесплатные»
  ресурсы: его серверная работа тоже учитывается внутри общего бюджета.

В [NF08 исходного ТЗ](original-specification.md) явно исключён браузер.
Это не тождественно исключению любого сервера с названием frontend.
В выбранном API-профиле запросы идут напрямую в backend: Nginx не обслуживает
этот поток и учитывается отдельно по поручению пользователя. Для дополнительного
HTTPS-прогона через Nginx указываем его CPU, память и маршрут запросов отдельно;
не выдаём такой замер за прежний профиль с другой границей ресурсов.

React выполняется в браузере; контейнер frontend — production Nginx,
а не Node/Vite. CPU сборки и HMR нельзя смешивать с расходом этого контейнера.

### 1.1. Первый кандидат будущего ресурсного этапа

| Компонент | CPU | Память, МиБ | Учёт |
| --- | ---: | ---: | --- |
| PostgreSQL | 1,10 | 1536 | Внутри общего ограничения. |
| Backend | 0,60 | 1536 | Внутри общего ограничения. |
| Эмулятор | 0,30 | 1024 | Внутри общего ограничения. |
| **Сумма трёх серверных компонентов** | **2,00** | **4096** | **2 CPU / 4 ГиБ.** |
| Frontend/Nginx | 0,50 | 256 | Отдельно. Стартовый запас для static/proxy; ещё не квалифицирован. |
| **Весь Compose вместе с frontend** | **2,50** | **4352** | Эту сумму тоже показываем в отчёте. |

Это увеличение потолка PostgreSQL с 1,0 до 1,1 CPU без урезания эмулятора.
Свободное время CPU фронта не «занимало» базу: ограничения Docker являются
потолками, а не резервированием физического ядра. Меняем разрешённый потолок,
не обещаем пропорционального ускорения.
Основание: [Docker CPU constraints](https://docs.docker.com/engine/containers/resource_constraints/).

### 1.2. Матрица поиска баланса CPU

В будущих ресурсных сравнениях frontend одинаков: 0,50 CPU / 256 МиБ.
Память серверных компонентов сначала неизменна; меняется только CPU.

| Профиль | PostgreSQL | Backend | Эмулятор | Сумма | Очерёдность |
| --- | ---: | ---: | ---: | ---: | --- |
| C0: контроль прежнего серверного распределения | 1,00 | 0,60 | 0,30 | 1,90 | Новый контроль с одинаковым frontend; запас до потолка допустим. |
| C1: вернуть базе прежнюю долю frontend | 1,10 | 0,60 | 0,30 | 2,00 | Первый кандидат после архитектурного этапа. |
| C2: небольшой перенос из backend | 1,15 | 0,55 | 0,30 | 2,00 | Если у backend остаётся подтверждённый запас. |
| C3: больший перенос из backend | 1,20 | 0,50 | 0,30 | 2,00 | Только после C2: backend может стать новым ограничителем. |
| C4: небольшой перенос из эмулятора | 1,15 | 0,60 | 0,25 | 2,00 | Условный вариант: внимательно проверять исполнение после приёма. |

После архитектурного этапа не требуется перебирать все профили. Начать с C0/C1/C0.
Проверять следующий, если он отвечает на конкретный вопрос по предыдущему.
Средний CPU ниже квоты не доказывает достаточность квоты для коротких всплесков.

Прежняя попытка backend 0,6 / PG 1,15 / emulator 0,2 / frontend 0,05 уже отклонена:
API ускорился, но выросла очередь исполнения эмулятора. C4 отличается от
неё, однако остаётся рискованным направлением, а не готовой рекомендацией.

### 1.3. Память — отдельный эксперимент

| Профиль | PostgreSQL, МиБ | Backend, МиБ | Эмулятор, МиБ | Сумма, МиБ | Условие |
| --- | ---: | ---: | ---: | ---: | --- |
| M0 | 1536 | 1536 | 1024 | 4096 | Начальный вариант. |
| M1 | 1792 | 1280 | 1024 | 4096 | Только если measured heap/native memory backend допускают снижение. |
| M2 | 2048 | 1280 | 768 | 4096 | Более поздний вариант; отдельно проверить JVM и эмулятор. |

Нехватка памяти как причина текущего предела не доказана. Больше RAM
не превращает точный COUNT в операцию постоянной стоимости.
Проверять RSS, heap/GC, direct/native memory и файловый кэш cgroup;
не ориентироваться только на занятый Java heap.

### 1.4. Что потребуется согласованно изменить

Сейчас исходники ещё суммируют все четыре контейнера:

- `compose.yml` — фактические исходные cpus/mem_limit.
- `compose.load.yml` — отдельные БД, порты и сеть; ресурсы наследуются.
- `tests/load/environment.mjs:qualifiedLoadEnvironment` — проверка общей суммы.
- `tests/load/nf08.mjs:resourceTotal` — ещё один расчёт суммы для отчёта.

Согласованный implementation slice позднего ресурсного этапа:

1. В существующем Compose задать выбранные стартовые лимиты.
   В load override сохранить изоляцию; не добавлять второй локальный стек.
2. В общем load-helper определить одну явную классификацию ресурсов:
   ограниченная серверная группа, frontend отдельно, сумма всего стенда.
   NF08 использует тот же расчёт, а не вторую формулу.
3. Проверять наличие всех ожидаемых сервисов, положительные реальные лимиты,
   source labels и стабильность container IDs. Не исключать неизвестный
   дополнительный сервис молча.
4. Тесты расчёта: ровно 2 CPU/4 ГиБ допустимы; превышение CPU или памяти
   серверной группы отвергается; frontend не теряется из отчёта; неизвестный
   сервис и неполные/дублированные сведения дают явную ошибку.
5. Проверить rendered config для base, base+load и base+public+load.
   Пароли в вывод не печатать. Бюджет проверяется по реальным cgroup/container
   лимитам, а не только по YAML.
6. Обновить существующие инструкции и таблицы ресурсов после выбора победителя.
   Старые результаты 2CPU/4 ГиБ, включавшие маленький frontend, остаются историческими.

Применение новой границы потребует нового замера. Старый NF08 нельзя
переименовать в новый профиль, не запуская его заново.

## 2. Что установлено, а что остаётся гипотезой

| Факт завершённой квалификации | Значение |
| --- | --- |
| NF08: 5000 исходных, 20 клиентов, 30/120 с | 44 243 запроса; ошибок 0; read/write p95 102,53/102,17 мс. |
| Непрерывные создания 50/с, 3×300 с | 45 000 новых, 50 000 итоговых записей сверены; очередь устойчива; внешнее исполнение p95 299 мс. |
| Длительная полная смесь 90/с каждого из четырёх действий | FAIL: 9921 неотправленный цикл генератора, 184 HTTP503, рост очереди. |
| Принятые данные перегрузочного прогона | Все 71 939 созданных операций и 1000 rename-целей проверены; 76 939 итоговых записей, потерь/дублей нет. |
| PostgreSQL по трём окнам полной смеси | 0,946/1,000/1,000 CPU при потолке 1 CPU. |
| Наблюдения активных SQL | COUNT427 session-hits, COMMIT115, page SELECT89. Это не доли CPU. |
| COUNT после разгрузки | Index Only Scan, 38 476 записей индекса, 5,232–7,002 мс. |
| Блокировки строк | Были; 22 наблюдения. CPU насыщение не означает полного отсутствия блокировок. |

**50 созданий/с без постоянных чтений не означают 50 полной смеси/с.**
Нагрузки closed-loop NF08 и fixed-rate mixed тоже нельзя сравнивать по одному
числу принятых записей.

Установленная последовательность под тяжёлой смесью:
дорогие чтения и записи конкурируют за CPU PostgreSQL → SQL/транзакции
завершаются дольше → дольше заняты соединения → растут ожидания и очередь.
Это не доказательство, что весь CPU расходует только COUNT.
Увеличение Hikari не добавляет CPU PostgreSQL.

Текущий read-адаптер `SpringDataTaskReadRepository.page` всегда выполняет
отдельные page SELECT и COUNT. В нём уже есть плоская проекция, фильтры по
owner/status/createdAt и индекс owner/status/createdAt/id.
Точное количество страниц — существующее требование пользователя.
Rows и total читаются в согласованной транзакции.

## 3. Уже принятые и отклонённые решения

| Решение | Состояние | Следствие для следующего цикла |
| --- | --- | --- |
| Глобальный Semaphore для claim/HTTP/finish, не локальные futures прохода | Принято; соседняя задача при задержанном ответе принимается за 96–190 мс вместо≈2,1 с. | Сохранить глобальную ёмкость, ошибки/interrupt/close и отсутствие preclaim без слота. |
| Штатное определение CPU JVM вместо ActiveProcessorCount2 | Принято; backend CPU≈0,54–0,55→0,458–0,459 ядра в повторных сравнениях. | Не возвращать фиксированное число без нового измерения. |
| Execution batch5 / publication batch25 | Принято. Прежние 1/5/10/25 уже исследовались. | Не начинать тот же перебор заново без изменения гипотезы. |
| Ручной JDBC вместо Spring Data для page mapping | Отклонено: локальный выигрыш не повторился в приложении. | Сохранить один Spring Data read-путь. |
| Hikari4 вместо 8 | Отклонено: задержки выросли. | Не уменьшать/увеличивать автоматически. |
| Удаление повторной cleanup при подтверждённой доставке | Отклонено: меньше SQL без повторяемого выигрыша. | Не возвращать дополнительное состояние/guard ради счётчика SQL. |
| Autovacuum naptime10 вместо 60 | Отклонено по общему результату. | Не объявлять «чаще vacuum» готовым решением. |
| Generic/custom prepared COUNT | Самостоятельная проблема плана не подтверждена. | Новый prepared-plan эксперимент нужен лишь при новом запросе/индексе. |
| Перенос CPU из эмулятора до 0,2 | Отклонено: накопление принятого, но не исполненного. | Оценивать всю цепочку, не только API. |

Исходные команды, положительные и отрицательные результаты — в
[существующем журнале](exchange-performance-plan.md); здесь их не дублируем
помесячным дневником.

## 4. Каталог вариантов

Приоритеты: **P0** — подготовка/достоверность; **P1** — простые первые
эксперименты; **P2** — только после профиля; **P3** — условное изменение
модели/контракта. Все не помеченные «принято» варианты ниже — гипотезы.

| ID | Вариант | Что может дать | Цена и ограничение | Приоритет |
| --- | --- | --- | --- | --- |
| O01 | Отделить frontend и проверить C1 | Больше разрешённого CPU базе без урезания эмулятора. | Новая граница отчёта; старые цифры не подтверждают результат. | Отложено до завершения архитектурного этапа. |
| O02 | C2/C3/C4 вместо C1 | Подобрать распределение 2 CPU под реальную смесь. | Можно перенести очередь в backend/эмулятор. | Поздний ресурсный этап, после C1. |
| O03 | Общий cgroup для трёх серверов: 2CPU/4 ГиБ, веса внутри | Неиспользуемая доля соседа может быть доступна PostgreSQL при соблюдении общего потолка. | Host/cgroup-driver зависимость, другая проверка лимитов; не portable замена cpus одной строкой. | P3, если статическое деление доказанно мешает. |
| O04 | Не выполнять COUNT, когда total строго выводится из страницы | Убрать часть запросов для пустой первой/неполной последней страницы. | Полные первые страницы и пустая глубокая страница всё ещё требуют COUNT. | P1, небольшой безопасный выигрыш. |

| O23 | Изменить execution/publication batch эмулятора | Сократить commits на операцию при новых условиях. | Большие транзакции держат locks дольше; прежний перебор уже дал batch5/25. | P2 только при новой причине. |

| O25 | Настроить worker max-in-flight/cadence/Hikari вместе с профилем | Убрать подтверждённое ожидание ёмкости при свободном DB CPU. | При насыщенном PG больше параллелизма увеличивает конкуренцию; интервалы пустой очереди тоже имеют цену. | P2 после CPU/SQL. |
| O26 | Уменьшить mapping/JSON/allocations/логирование | Снизить backend CPU, если снова станет ограничителем. | Прежний ручной mapping не дал macro win; результат/историю/права не урезать. | P2 по JFR, не переписывать слой заранее. |
| O27 | Read replica для списков | Вынести тяжёлые чтения с primary. | Реплика также внутри бюджета, удваивает процессы/память, есть lag и read-after-write вопросы. | P3, сейчас не выбран. |
| O28 | Партиции tasks по дате/владельцу | Pruning подходящих запросов, обслуживание больших данных. | Без фильтра по ключу COUNT всё равно обходит подходящие части; уникальность operationId/FK/миграция сложнее. | P3, не лечение текущего CPU само по себе. |
| O29 | Отдельная очередь/sharding workers/брокер | Масштабировать доказанную горячую очередь или несколько серверов. | Нынешний предел чтений не добавляет CPU; новые компоненты учитываются в бюджете. | P3, не выбран. |
| O30 | Архивация/вертикальное разделение горячих данных | Уменьшить активный набор и влияние частых UPDATE на читаемые данные. | Новая модель хранения, чтения и FK; архив не должен исчезнуть из обещанного реестра/истории. | P3, только при таком жизненном цикле данных. |

### 4.1. Простой пропуск COUNT

В текущем адаптере COUNT вызывается безусловно. Проверить
[PageableExecutionUtils](https://docs.spring.io/spring-data/commons/docs/current/api/org/springframework/data/support/PageableExecutionUtils.html)
внутри Spring Data адаптера, не вынося framework-типы в service/domain.

Total можно вывести для неполной первой страницы и для непустой неполной
последующей страницы при том же snapshot. Пустая глубокая страница ничего
не говорит о реальном total: её нельзя объявлять offset записей.
Полная страница ровно size тоже не доказывает конец списка.
Главный mixed-запрос получает полные страницы, поэтому этот вариант сам
по себе не обещает устранить обнаруженный предел.

### 4.2. Индекс и обслуживание PostgreSQL

SQL-spike 16 ноября уже проверил узкий B-tree `(owner_id,business_status)`
для count без периода; результаты и ограничения — в разделе 10.
Следующий шаг — macro-проверка наиболее подходящего паттерна записи,
а не принятие индекса по одному быстрому EXPLAIN. Сравнивать с уже существующим owner/status/createdAt/id. Создание нового индекса
не является заранее принятым решением. Он может уменьшить размер сканируемой
структуры, но добавит стоимость записей; deduplication тоже не отменяет
проверку видимости. Не включать большой JSON результата ради covering index.

Проверять custom/generic планы при частичном индексе: параметризованный
предикат не всегда доказывает условие индекса.
Официальные основания:
[COUNT](https://www.postgresql.org/docs/18/functions-aggregate.html),
[index-only и visibility map](https://www.postgresql.org/docs/18/indexes-index-only-scans.html),
[B-tree deduplication](https://www.postgresql.org/docs/18/btree.html),
[partial index](https://www.postgresql.org/docs/18/indexes-partial.html).

Для O07–O10 сначала установить реальную причину: heap fetches, долю
all-visible страниц, dead tuples/HOT updates, промахи буферов, дельту temp
bytes, planning/JIT, WAL/IO waits. Накопительный счётчик за прошлые тесты
не является расходом текущего прогона. `effective_cache_size` — оценка для
планировщика, а не выделение RAM. `work_mem` действует на операции плана,
поэтому его нельзя умножать только на один backend connection.

Ссылки:
[ресурсы PG18](https://www.postgresql.org/docs/18/runtime-config-resource.html),
[autovacuum](https://www.postgresql.org/docs/18/routine-vacuuming.html).
`synchronous_commit=off`, отключение fsync/full_page_writes или history
не принимаются как оптимизация: [WAL](https://www.postgresql.org/docs/18/runtime-config-wal.html)
должен сохранять договорённость о принятых данных.

## 5. Точный count и кэш: сначала модель согласованности

### 5.1. Транзакционные счётчики

Если простых архитектурных изменений недостаточно, O12 — предметный вариант
с наибольшим потенциалом
изменить именно стоимость повторного count, но этот потенциал пока не измерен.

Возможная модель: производная таблица count по owner/status, обновляемая
атомарно с созданием/сменой статуса. Общие итоги можно получить суммированием
этих строк; отдельный глобальный горячий счётчик заранее не вводим.
Задачи остаются источником истины; редактировать счётчики через API нельзя.
Сводка без периода покрывает только свою форму запроса. Для произвольных
from/to требуется точный запрос либо другая отдельно обоснованная проекция;
один общий count не отвечает на любой диапазон дат.

До реализации решить:

- Один владелец обновления: БД-trigger либо один полный командный путь,
  включая importer/seed/служебные изменения. Не два конкурирующих механизма.
- Начальный backfill и переключение чтения одной миграцией/согласованной
  последовательностью без окна расхождения; применение только на своём стенде.
- Создание, переходы, повтор/равный/устаревший результат и rollback не должны
  повторно менять счётчик. Переименование не меняет membership списка.
- Горячие owner/status строки могут сериализовать запись. При батче нужен
  единый порядок блокировок счётчиков вместе с tasks, а не новое кольцо deadlock.
- Сводка и rows читаются в одном [RR snapshot](https://www.postgresql.org/docs/18/transaction-iso.html).
- Любая будущая операция удаления/смены владельца тоже входит в инвариант.
  Несуществующие сейчас CRUD-операции ради счётчика не добавляем.

Проверка: конкурентные create/result/rename, retry/replay, отказ транзакции,
двойная обработка страницы, миграция на непустой БД; сравнение с обычным COUNT
для обеих ролей, всех статусов и поддержанных форм фильтра. Затем измерить
CPU/WAL/locks и всю смесь. Если чтение ускорилось ценой остановки записи,
решение отклонить. Шардирование счётчика O13 рассматривать только после
наблюдаемой конкуренции за простую строку, не внедрять заранее.

### 5.2. Кэш в backend или Redis

В PostgreSQL есть кэш страниц и планов, но это не готовый точный кэш
результата нашего COUNT. Redis сам не знает, сколько задач доступно пользователю.

Для O14–O16 сначала определить:

1. Что кэшируется: целая согласованная страница или производный count.
2. Какая свежесть разрешена контрактом. Простая TTL и afterCommit eviction
   оставляют гонки между изменением, чтением и заполнением кэша.
3. Ключ: реальная область доступа/роль, owner, status, диапазон дат, page/size
   и другие фактические входы. Авторизация выполняется до выдачи.
4. Все инвалидации: create/result/rename и операторские изменения там,
   где они действительно меняют соответствующий ответ.
5. Ограничения числа/размера записей, изоляцию при смене сессии/прав,
   поведение нескольких экземпляров и отказа кэша. Frontend очищает private
   cache при logout; backend проверяет сессию до каждой выдачи и не обязан
   глобально сбрасывать серверный кэш при каждом выходе пользователя.
6. Как не смешать cached total с rows другого snapshot.

Частые create/status updates могут обесценить версионный кэш раньше
повторного чтения: полезность hit ratio нужно измерить.
Не вводим цепь «Redis → локальный кэш → старый ответ → пустой успех».
Временная недоступность кэша не должна скрывать реальную ошибку; актуальный
путь и источник истины задаются явно.

Для одного backend не начинаем с нового Redis-процесса.
Вариант с общей памятью нужен при доказанной потребности нескольких
экземпляров и принятой модели свежести, а не ради названия технологии.
[Документация Redis](https://redis.io/docs/latest/develop/get-started/data-store/).

### 5.3. Изменение контракта отображения

Slice/keyset, приблизительный total, count по запросу, отдельный endpoint
и materialized view — другие продуктовые соглашения.
ТЗ NF08 не предписывает точное число страниц, но оно требуется текущим UI
и пользователем. Оно не исчезает из-за решения оптимизировать backend.

Такие варианты можно сравнить в исследовании, но не внедрять без отдельного
решения об изменении поведения. Обновляются OpenAPI, generated controller
interfaces/client при билде, реальные frontend callers и тесты.
Сгенерированное не сохраняется в src/Git.
[Materialized views](https://www.postgresql.org/docs/18/sql-creatematerializedview.html)
и [read replica](https://www.postgresql.org/docs/18/hot-standby.html)
не дают автоматически текущий результат primary после записи.

## 6. Батчи и ограничение конкуренции

Следующая ступень батчей должна сокращать подтверждённую работу БД,
а не просто увеличивать число одновременно захваченных задач.

Для claim-batch O21:

- Получить свободные глобальные слоты до захвата leases.
- Захватить не больше разрешённого числа; неиспользованные слоты освободить.
- Атомарно сохранить claims/attempts/history, затем выполнить HTTP вне БД.
- Сбой после commit до HTTP восстанавливается существующим lease/GET путём.
- Не возвращать барьер ожидания всей группы после одной медленной отправки.

Для result-consume O22: bounded размер страницы, единый порядок task locks,
результаты/история/cursor в одной транзакции, полное восстановление после
rollback. JDBC batch может применяться внутри существующего repository;
новый Spring Batch framework или generic batch engine не требуется.

Увеличение execution batch5 проверять только если после read/CPU улучшения
эмулятор сам стал узким местом. Больший батч не обязан быть быстрее для API.
Формула увеличения Hikari не является самостоятельным планом:
[рекомендации владельцев HikariCP](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)
требуют учитывать доступную работу БД; нам уже известен отрицательный pool4.

### 7.1. Нужная диагностика

- API: p50/p95/p99 и ошибки каждого вида; offered/started/missed отдельно.
- БД: CPU/throttling, connection acquisition/holding, SQL calls и wall time,
  BUFFERS, строки, WAL, IO/temp delta, реальные waits/blockers.
- Конвейер: создание → начало попытки → внешнее принятие → исполнение →
  применение результата. Очередь/возраст на каждой границе, не один backlog.
- Память: cgroup RSS/cache, heap/native/GC, OOM и перезапуски.
- Генератор: CPU/RSS/отставание своего clock; исходный payload, фактические
  созданные ID, revisions и исходы сохранить до завершения сверки.
- После остановки потока: время drain, отсутствие потерь/дублей и совпадение
  обоих хранилищ и history.

Текущие sampled active-query hits не измеряют долю CPU SQL. Если их
недостаточно, использовать штатный
[pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html)
в изолированном QA, с контролем overhead и snapshot/delta статистики.
Это может требовать настройки/restart только QA PostgreSQL; отдельный
Prometheus/Grafana стек для этого не нужен.

У старого mixed-report finalIntegrity=false также получается из-за
completed != planned при missed arrivals. После E45 mixed-report различает:

- `finalIntegrity.acceptedDataCorrect`: все действительно принятые операции
  сверены с исходным запросом, результатом, историей и двумя БД.
- `finalIntegrity.passed`: дополнительно выполнены все planned arrivals.
- `passed`: также соблюдены SLA, ресурсы, неизменность исходников и runtime.
- `sustainable`: дополнительно пройдены прежние проверки очереди каждой фазы.
  Успех сверки принятых данных не подменяет ни capacity, ни устойчивость.

13 null outcome в старом pipeline названы IN_FLIGHT. Это не число реально
работающих HTTP-запросов; диагностика живых слотов остаётся у координатора.
Уточнение метрики не означает выдумывание успешного исхода попытки.

### 7.3. Правило повторяемого цикла

Один цикл отвечает на один вопрос; повторяется не полный аудит, а путь
нового измеренного ограничения.

1. **Зафиксировать вход.** Git SHA приложения и генератора, digest образов,
   схему/индексы, effective CPU/RAM, настройки, набор данных и расписание.
   Отдельно указать, менялся ли instrumentation. Сверить чистоту checkout.
2. **Сформулировать гипотезу.** Где расходуется работа, какой владелец её
   создаёт, чем заменить и какой результат опровергнет идею. Например:
   узкий индекс сокращает читаемые страницы COUNT, но увеличивает WAL записи.
3. **Измерить контроль A.** Воспроизводимый fixture, прогрев, короткий mixed;
   сохранить offered/started/missed, latency, ошибки, очередь и целостность.
   Не брать старое число из другого объёма вместо нового контроля.
4. **Один вариант B.** Адресный regression, планы затронутого SQL и сборка
   только изменённого приложения. Если меняется лишь индекс, те же образы
   приложения; отдельный hash DDL/схемы в receipt. Не переписывать V1–V7.
5. **Повторить контроль A.** Данные/прогрев восстановлены штатно. Для индекса
   условия его существования до вставки одинаковы; никакого скрытого VACUUM
   только кандидату. Отсутствие совпадения контролей означает неопределённый
   результат, а не победу B.
6. **Принять или удалить эксперимент.** Выигрыш должен превышать разброс A,
   сохранять скорость записи/исполнения и правила раздела 8. Отрицательный
   результат остаётся в журнале, альтернативный производственный путь удаляется.
7. **Переизмерить остаток.** Повторить профиль горячих SQL, ожиданий и этапов
   конвейера. Следующий вариант выбирается по новой причине, не по порядку
   модных технологий. Принятый B становится контролем следующего цикла.
8. **Общий gate — на интегрированном кандидате.** Полный набор сборок,
   UI/recovery/NF08 и длительных прогонов не запускается после каждой малой
   правки. Адресная сборка для сравнения изменённого алгоритма нужна;
   полный gate выполняется после совмещения выбранных улучшений.

В [существующем журнале](exchange-performance-plan.md) на цикл сохраняются:
гипотеза/владелец, изменённые файлы и причина, источник исследования,
source/artifact/schema hashes, одинаковые условия A/B/A, результат и ограничения,
решение/удалённый путь, новое узкое место. Сырые JSON/JFR/планы остаются
в ignored tests/results с адресным run-каталогом; в Git — компактный вывод.

Среднее время SQL из pg_stat_statements не равно CPU-времени; sampled
pg_stat_activity не равно числу исполнений. CPU контейнера, стоимость SQL,
row-lock wait и ожидание Hikari рассматриваются совместно. Медленное
получение соединения при занятом PostgreSQL может быть следствием, а не
причиной; увеличение пула не считается исправлением по одному этому симптому.

### 7.5. Критерии завершения, а не бесконечная оптимизация

- Обязательный NF08 проходит на неизменных ресурсах; continuous 50 create/s
  ×3×300с сохраняет целостность и устойчивость.
- Полная открытая смесь исследована ступенями 50/70/90 циклов/с.
  Сначала короткий screening, выбранная поддерживаемая ступень подтверждена
  полным 3×300с и повтором. Если первая ступень неустойчива, исследовать ниже,
  не скрывать FAIL и не переименовывать его в результат другой нагрузки.
- 90×4 — исследуемая верхняя ступень, а не обещание и не основание менять
  SLA/ресурсы. Если все три ступени успешны, заявляется проверенная 90,
  не выдуманный абсолютный максимум; выше текущая цель не требует идти.
- Если 90 не достигнуты, оставшиеся разумные P4/P5-гипотезы рассмотрены по
  фактам: выполнен подходящий эксперимент либо записана конкретная причина
  неприменимости/неприемлемой сложности. Не завершать после первого
  отрицательного индекса; не запускать бессодержательные повторы без новой
  гипотезы. При перекрывающемся разбросе результат считается неопределённым.
- Права, exact total/RR, идемпотентность, конечные повторы, leases/fencing,
  неизменный request, история, commit-order cursor и восстановление сохранены.
- Нет параллельных экспериментальных путей, мёртвых флагов, отключённой
  durability или молчаливого изменения контракта. Архитектура остаётся проще
  подтверждённой выгоды; новый framework/процесс требует отдельного обоснования.
- Финальный source/artifact manifest, планы и отчёт относятся к одному
  кандидату; полный gate не заменён прежними результатами раздела 2.
  Код, миграции и документы закоммичены/опубликованы в task-ветке, повторное
  ревью закрыто. Merge и публичный deploy не входят в эту цель.
- Собственные завершённые QA fixtures/том/сеть/транспортные файлы убраны
  после сверки; результаты компактны, обычный стенд и чужие ресурсы сохранены.

## 8. Критерий выбора и завершения

Принимаем вариант, если одновременно:

- Выигрыш повторяется при одинаковом объёме, потоке, приложении и учёте ресурсов;
  наблюдаемая разница больше обычного разброса контроля.
- Нет скрытого уменьшения предложенной нагрузки или потери ошибок.
- Не растут возраст/очередь другого этапа; p95 API сам по себе недостаточен.
- Права, exact total, RR, история, идемпотентность, конечные повторы и
  восстановление сохранены либо изменение контракта отдельно принято.
- Обязательные NF08 и regression gates пройдены.
- Нет лишнего процесса, альтернативного legacy-пути или состояния без владельца.

Если 90×4 после простых изменений всё ещё неустойчивы, это фиксируется как
предел данного ресурса/объёма. Тогда выбирать следующую гипотезу из файла
по измеренной цене, а не обещать заранее нужный throughput.
Менять продуктовую точность либо превышать серверные 2CPU/4 ГиБ молча нельзя.

Для неудачного варианта: сохранить результат и причину, удалить его
экспериментальный путь. Для удачного: один актуальный путь, документация
владельца и данные квалификации. Merge и публичный deploy — отдельные действия.

## 9. Ближайший достаточный объём

Сначала архитектурные **S1–S4**, ресурсы оставить прежними.
Самый перспективный измеренный SQL-кандидат — узкий count-индекс
для локального hot-набора. У него есть отрицательный контрпример
с распределённым churn, поэтому нужен macro A/B/A, а не немедленная миграция.

Параллельный по смыслу, но последовательно измеряемый набор малых
изменений — убрать лишние round trips и повторную материализацию
в A2–A5, затем оценить повторные записи A6. Не тратить часы на
оптимизацию редкого operator-запроса, если COUNT всё ещё забирает основную
работу БД. Не обязаны внедрять все кандидаты: каждый должен окупить сложность.

Счётчики O12 — следующая архитектурная ступень, если простое решение
не даёт достаточного результата. Redis, реплика, партиции и новый batch
framework не добавляются заранее. Перераспределение ресурсов — только S7.

### 10.2. Карта транзакций и вывод по изоляции

| Путь | Текущая граница | Вывод |
| --- | --- | --- |
| TaskService.get | readOnly, default RC, один SELECT | RR для этой карточки не нужен. |
| TaskService.list/history | readOnly RR, несколько SELECT | Согласованные rows/total и проверка контекста. Сохраняем. |
| ReviewService.get/list | readOnly RR, issue/task/сверки/total | Составной ответ имеет общий snapshot; N+1 списка уже устранён bulk-чтением. |
| prepareReconciliation → HTTP → saveReconciliation | Две короткие RC-транзакции, HTTP между ними; версия проверяется при сохранении | Сеть не держит соединение или row lock. |
| create/rename/operator-команды | RC + locks/revisions + MANDATORY квитанция/история | Атомарность и сериализация заданной операции; не глобальный SERIALIZABLE. |
| claim → HTTP → finish | Две короткие RC-транзакции и свободный сетевой участок | Lease/fencing сохраняются, не переносить HTTP внутрь Tx. |
| consume страницы | Одна RC-транзакция: cursor lock → task locks по id → эффекты → cursor | Bounded атомарность правильная; цену повторных записей можно уменьшать. |
| emulator accept/executeNext/publish | Отдельные RC-транзакции; bounded batches и cursor lock | Приём не равен исполнению; commit-order cursor не заменяется просто sequence. |

DB default подтверждён как read committed. MANDATORY присоединяется
к транзакции владельца; REQUIRES_NEW и второго пула для этой схемы нет.
readOnly не является проверкой прав.

Контрпример на двух соединениях: первое прочитало 2 строки, второе
изменило строку/добавило третью и закоммитилось. В RC первый reader
увидел count 3 и новую строковую версию; в RR — count 2 и прежнюю версию.
Оба режима позволили writer завершиться, обычный RR SELECT не взял
блокировку строки. Реальный Spring page/count тест тоже прошёл.
SERIALIZABLE в этой пробе сохранил snapshot, но это не повод включать его
везде: дополнительные гарантии и их стоимость нужны для конкретного правила.
Основания: [PG isolation](https://www.postgresql.org/docs/18/transaction-iso.html),
[Spring transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

Механизм стоимости длинного RR отдельно воспроизведён: backend_xmin
удерживался между SELECT; после UPDATE и VACUUM all-visible pages оставались 0.
После закрытия старого snapshot и нового VACUUM стало 1, старая версия
до закрытия читалась. Это доказательство механизма, не найденная утечка
транзакций в приложении: в старом mixed максимальный наблюдаемый возраст
транзакции был≈1,50 с. Выборочные наблюдения не гарантируют отсутствие любого
более длинного хвоста. Сначала измерять lifetime, а не понижать изоляцию.

### 10.3. Сила блокировки — отдельный вопрос

В SQL-пробе FOR UPDATE блокировал FK INSERT в дочернюю таблицу.
FOR NO KEY UPDATE разрешил такой INSERT; конкурирующий UPDATE той же
родительской строки продолжал блокироваться в обоих случаях.
SKIP LOCKED выбрал другую свободную строку, после release обычный UPDATE
занятой строки успешно продолжился.

Следствие: для неизменяемого ключа можно изучить более слабую достаточную
силу lock. Это не способ разрешить два одновременных изменения одного
состояния. Нынешние waits finish/consume на той же задаче от такой замены
могут вообще не исчезнуть. Нужны реальные blockers и regression.
[Матрица row locks](https://www.postgresql.org/docs/18/explicit-locking.html).

### 10.4. Индексы: результат зависит от записи и истории построения

80 тысяч задач, два владельца,40 тысяч совпадающих записей COUNT.
Два прогрева +10 измерений, PostgreSQL executor time. Память/CPU неизменны.

| Состояние данных | Исходный индекс | Узкий owner/status | Свежая копия широкого индекса |
| --- | ---: | ---: | ---: |
| Все страницы all-visible | 3,49 мс; контроль 3,38 | 2,57 мс | 3,33 мс |
| Равномерно изменены 10% строк | 10,23 мс, Seq Scan | 10,23 мс, Seq Scan | 10,19 мс, Seq Scan |
| Диагностический VACUUM после churn | 3,23 мс | 2,59 мс | 3,32 мс |

При распределённом churn visiblePages изменились 3810/3810 →0/4191.
Новый индекс не устранил необходимость видеть версии heap. Ручной VACUUM
не является частью приёмочного прогрева и не заменяет обычный write workload.

Однако этот паттерн не тождественен старому mixed: там rename ограничен
1000 заранее выбранных задач. Поэтому отдельно проверена локальность:
20 commits, каждый обновляет один и тот же набор 1000 задач.

| Индекс существует ещё до вставки fixtures | До churn, мс | После hot 1000, мс | План после churn |
| --- | ---: | ---: | --- |
| Исходный DESC | 3,21 | 9,85 | Seq Scan |
| Широкий ASC | 3,23 | 9,81 | Seq Scan |
| Исходный DESC + узкий owner/status | 2,56 | 2,70 | Index Only Scan, 2370 heap fetches |
| Повтор исходного DESC | 3,26 | 9,73 | Seq Scan |

Так исключён артефакт, при котором новый индекс выигрывает только потому,
что построен после UPDATE. Ранее проверенная свежая копия широкого индекса
тоже помогала, поэтому различать его компактность и узость необходимо.
ASC уменьшил размер широкого индекса≈11,08→8,63 МБ в этом наборе, но count
не ускорил после churn; готовой миграцией его не считаем.

Узкий индекс, сопровождаемый с момента первой вставки, занимал≈0,54 МБ,
после hot 1000≈0,61 МБ. Он остаётся сильным кандидатом для macro-проверки
текущего localized workload, но не универсальным решением любого UPDATE.
Все count всё ещё учитывают 40 тысяч записей. В отдельной одиночной
bulk UPDATE1000-пробе дополнительный индекс увеличил WAL≈9,35%; изменение
времени записи по одному A/B/A не объявляем устойчивым регрессом или выигрышем.
Нужны общий поток, даты/статусы/роли, рост базы, WAL и write latency.

### 10.5. Один SQL вместо RR двух SELECT — не бесплатное ускорение

На тех же 80 тысячах, одинаковых literal predicates и прежних ресурсах:

| Форма | All-visible, мс | Распределённый churn, мс |
| --- | ---: | ---: |
| COUNT + page, сумма двух медиан executor | 3,24 | 10,04 |
| Один CTE: bounded page + total, LEFT JOIN | 3,28 | 10,09 |
| COUNT OVER с полными полями task | 45,37 | 46,78 |

Window вариант записал 1768 temp blocks и прочитал 3054 при work_mem4 МБ.
Он обработал всё множество для окна; на пустой глубокой странице вообще
не вернул строку с total. CTE сохранил exact total 40000 и при 0 items
за счёт null task/sentinel строки, которую пришлось бы явно разбирать.

Один обычный SELECT имеет один statement snapshot при RC. Это допустимая
архитектурная альтернатива RR двух SELECT, если весь согласованный ответ
реально строится этим SELECT. Но CPU COUNT остался прежним; экономия
round trip/transaction overhead и цена mapping здесь не измерены.
Ради такой гипотезы не заменяем Spring Data вслепую и не ослабляем
изоляцию существующих многозапросных ответов.

| --- | --- | --- | --- |
| A1 | SpringDataTaskReadRepository.page всегда вызывает COUNT, даже для неполной первой страницы. | PageableExecutionUtils внутри адаптера; exact total сохраняется. | Полная/неполная/пустая глубокая страницы, обе роли/даты и число реальных SQL. Полные страницы 80k всё ещё требуют count. |

В обычном новом accept ожидается один round trip меньше, не обещание throughput. |

| A5 | ReviewService.loadContext/prepareReconciliation повторно загружают ту же tasks строку как Task и ExchangeState. | Получать один достаточный state при сохранении scope и task-before-issue lock order. | Составной snapshot, reassignment/retry/resolve, актуальные revisions и права. Для A6 нельзя просто выбросить RUNNING и ждать будущий terminal: coalescing
ограничен одной уже полученной страницей, её история и правила проходят
в исходном порядке. Если пришёл только RUNNING, он сохраняется сейчас.
Если корректный простой reducer получается сложнее подтверждённой выгоды,
оставить нынешний цикл и выбрать другое решение.

Если общий COUNT остаётся пределом, развитие O12 может включать
owner/status/day агрегаты: полные UTC-бакеты суммируются, два неполных края
считаются точно из tasks. Это идея, ещё не проверенная реализация.
Выбрать одну минимальную производную модель после анализа фильтров;
не заводить одновременно несколько несогласованных счётчиков и кэшей.

[Spring afterCommit lifecycle](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)
объясняет, почему commit не равен возврату connection. SQL/JSON/history
по-прежнему имеют владельцев в своих слоях; оптимизация не повод переносить
бизнес-правила в контроллер или добавлять universal unit-of-work framework.

### 10.7. Что проверили и не стали объявлять проблемой

- Обычные read SELECT не берут task row locks; RR не является причиной
  любой блокировки. Текущие writes используют RC плюс предметные locks/revisions.
- Один DataSource/transaction manager подтверждён тестом; дробить пулы ради
  формального разделения чтения/записи сейчас оснований нет.
- Сессии — стандартный servlet/Spring Security путь. Spring Session JDBC
  отсутствует в JAR и зависимостях; JdbcUserDetailsService читает users при
  login. Гипотеза о SQL-обновлении сессии на каждый API-запрос не подтверждена.
- Operator list уже использует bulk states/reconciliations, а не SQL на
  каждый элемент. Не добавлять второй batch-слой для уже решённого N+1.
- Advisory lock квитанции привязан к actor/command/key и не является одним
  глобальным mutex всех команд. Удалять его без равноценной атомарности нельзя.
- Cursor lock сериализует commit-order публикации; его нельзя заменять
  несогласованным sequence только ради отсутствия одной блокировки.
- Сеть/задержанный HTTP response находятся вне DB transaction. Интеграционные
  сценарии сохраняют независимость принятия, исполнения и результата.
- Избыточные редкие логи/JSON-мэппинг не объявляются основным SQL CPU без
  JFR/профиля. Не возобновлять отвергнутую перепись JDBC/JPA по вкусу.

Receipts и воспроизводимые SQL-рецепты — в ignored
tests/results/architecture-audit-2026-11-16: focused-java-summary, sql-plans.json.gz,
isolation-proof, count-index-proof, count-hot-locality-proof, index-layout-proof,
page-shape-proof, sql-workflow и library-versions. Все SQL-пробы диагностические;
их числам нельзя присвоить p95 публичного API. Следующий обязательный шаг
для выбранного индекса/изменения кода — macro-тест на прежних квотах,
а не балансирование ресурсов.

### 11.2. Что уже покрыто и почему крупные схемы пока не выбраны

| Семейство | Текущее решение и условие пересмотра |
| --- | --- |
| Слои/DDD/CQRS | Уже разделены command JDBC и read Spring Data; один контекст backend и отдельный эмулятор. Проекции можно улучшать внутри текущего адаптера. JPA-миграция или новые слои сами по себе не уменьшают работу SQL. |
| Outbox/inbox, идемпотентность, retries | Локальная задача+очередь+история+квитанция атомарны; применение feed+cursor атомарно. Это обязательная надёжность, не лишняя запись для удаления. Оптимизируем частоту/группировку, сохраняя конечные попытки и recovery. |
| Конкуренция/обратное давление | Глобальные слоты уже получаются до claim, сеть вне Tx; медленный ответ не держит всю группу. Сначала уменьшить сервисное время; рост in-flight/пула способен лишь переместить очередь в PostgreSQL. |
| Optimistic/pessimistic locking | Revision/fencing и locks защищают разные правила. Условный UPDATE RETURNING может подойти простой команде, но не заменяет получение актуального состояния для сложного перехода. Проверки scope/replay и порядок locks остаются; «убрать все SELECT FOR UPDATE» не план. |
| Батчи/set-based SQL | Сначала O35/A3/A6 внутри текущих Tx; batch size ограничен, без ожидания заполнения. Размер пачки выбирается по throughput, lock hold и задержке отдельных операций, а не только меньшему числу commits. |
| Exact count/read model | Индекс/корректный пропуск count раньше O12. Если он недостаточен — один точный транзакционный агрегат; горячие aggregate rows нельзя скрыть под новым shard framework. |
| Cache/single-flight | O14–O16 требуют контракта свежести. Одинаковый ключ не делает snapshots двух RR-транзакций одинаковыми; общий count нельзя бездумно разделять между ними. Frontend React Query влияет на реальный UI-поток, но отсутствует в direct API NF08. |
| Keyset/Slice/приблизительные данные | Потенциально уменьшают глубокий OFFSET/count, но меняют точное число страниц и адресацию. Нужны отдельное решение о продукте, OpenAPI и callers; текущая цель контракт не меняет. |
| Партиции/BRIN/реплика | Только доказанные pruning/временная локальность/размер или масштабирование. Текущий owner/status count без даты не становится O(1); replica lag противоречит ожиданию текущего снимка. Партиции требуют проверки UNIQUE operation_id/FK и не снимают contention одной строки. |
| Брокер/actor/sharding/event sourcing | Нынешняя надёжная очередь уже в PostgreSQL; COUNT и heap остаются при смене транспорта. Новые процессы/состояния/протоколы и eventual consistency не добавляются ради общего слова «нагрузка». |
| GC/JIT/AOT/native-image | Время старта и RSS отличны от steady-state throughput. Проект уже на JDK 25; смена runtime имеет смысл по CPU/GC-профилю после SQL, а не по новизне технологии. |
| Сеть/UI/static | Один HttpClient уже переиспользуется, response bounded; compression/proxy/UI polling — O17/O18 и отдельный HTTPS/UI-профиль. Их выигрыш не присваивается direct API PostgreSQL-профилю. |

Оценивать не только latency ответа, но и работу на одну принятую операцию:
SQL calls/rows/WAL, commits, connection hold и рост незавершённой работы.
Поиск выигрыша ограничен текущим контрактом и ресурсами. Формулы ёмкости
используются как проверка здравого смысла, не как замена замеру:
в устойчивом потоке среднее число занятых ресурсов связано с частотой и
средним временем владения; из p95 нельзя вычислить нужный размер Hikari.
Ускорение малого участка не даёт такую же кратность всему конвейеру.

### 11.3. Основания исследования

- [PG18 HOT](https://www.postgresql.org/docs/18/storage-hot.html):
  условия HOT; fillfactor помогает только доступному месту и допустимому UPDATE.
- [PG18 multivariate statistics](https://www.postgresql.org/docs/18/multivariate-statistics-examples.html):
  выбор MCV/dependencies по причине ошибки оценки.
- [PG18 EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html):
  SERIALIZE отдельно от сети, profiling overhead и безопасный rollback writes.
- [PG18 cumulative statistics](https://www.postgresql.org/docs/18/monitoring-stats.html):
  HOT/newpage, vacuum, IO/checkpointer/WAL counters и ограничения дельт.
- [PG18 pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html):
  реальная частота/сумма SQL, shared preload и restart только частного QA
  при необходимости. Одного sampled списка активных запросов недостаточно.
- [PG18 vacuum](https://www.postgresql.org/docs/18/routine-vacuuming.html):
  insert/update thresholds, per-table settings, visibility и долгие snapshots.
- [pgJDBC connection options](https://jdbc.postgresql.org/documentation/use/) и
  [server prepare](https://jdbc.postgresql.org/documentation/server-prepare/):
  rewrite/prepare/cache — возможности драйвера; точную совместимость
  выбранного SQL проверяем на установленном 42.7.14, не по обещанию кратности.
- [Spring 7 JDBC batch](https://docs.spring.io/spring-framework/reference/data-access/jdbc/advanced.html):
  штатный batch API без нового framework.
- [Boot 4.1 task execution](https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html),
  [Spring Scheduled](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/annotation/Scheduled.html)
  и [JDK 25 virtual threads](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html):
  существующие managed threads/clients сохраняются; учитывается фактический
  scheduler, не только глобальный virtual flag.
- [PG18 partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html):
  применение зависит от pruning и ограничений схемы, не от наличия блокировки.

### 12.1. Подтверждённые факты и короткий список

- SpringDataTaskReadRepository.page делает page SELECT и отдельный COUNT
  при каждом чтении. TaskService.list объединяет их REPEATABLE READ.
- В mixed-workload список всегда SUCCEEDED/page0, два владельца: для total
  всего два ключа. При 70 list/s это 70 COUNT/s. TTL 2 с с одним загрузчиком
  на ключ даёт примерно 1 COUNT/s: около 70 раз меньше именно подсчётов.
  Listing SELECT суммарно меняются примерно 140→71/s, не 140→2/s.
  Это арифметика вызовов при повторении ключей, не измеренный выигрыш CPU/RPS.
- У K70L1/L2 поздняя фаза использовала PG ≈ 0,777 CPU из 1, backend ≈ 0,33 из 0,6,
  emulator ≈ 0,056 из 0,3. Пока оснований увеличивать Hikari или число отправок нет.
  На 90/больших данных прежние исследования обнаруживали дорогие COUNT;
  время SQL не принимается за точную долю CPU. Исходные результаты — E46–E49
  [журнала](exchange-performance-plan.md).
- Текущие dto/Page.hasNext и OpenAPI TaskPage выводят навигацию из точного total.
  Поэтому кеш одного числа требует изменения контракта и потребителей.
  Правила HistoryPage/IssuePage нельзя незаметно менять вместе с TaskPage.

| Приоритет | Решение | Реальный механизм экономии | Ограничение и проверка |
| --- | --- | --- | --- |
| R1: первый кандидат, O14/O19 | Ограниченный TTL-кеш total в одном backend | Меньше повторных полных COUNT; строки списка и карточки остаются актуальными. | Срок 2 с — стартовая гипотеза. | R4: только при смене UX, O18 | Slice/hasNext без общего итога | COUNT исчезает полностью, читается size+1 строка. Нет кеша и производного состояния. | Нужно отказаться от количества всех страниц; ранее это требование пользователя. Сейчас оно не отменено. | R5: при низком cache hit, O20 | Периодическая сводка owner/status/период | Один пересчёт обслуживает много разных запросов к небольшим агрегатам. | Для нынешних двух ключей может не выиграть у R1. Произвольные временные границы должны поддерживаться явно; REFRESH тоже сканирует исходные данные. |

Чистый VIEW хранит запрос и снова выполняет его при чтении. Полный materialized
реестр не делает COUNT константным; REFRESH заново выполняет определяющий SELECT,
CONCURRENTLY требует подходящий UNIQUE и не означает инкрементального SELECT.
Реплика переносит чтение, но primary продолжает обслуживать свои индексы.
Эти механизмы не являются подтверждённым решением текущего узкого места.

### 12.2. Минимальная реализация выбранного кандидата

Сначала выбрать R1 либо R2; второй кеш поверх первого не нужен.

- Для R1 ключ total: актуальный scope доступа, owner/роль, статус и
  нормализованные UTC-границы. Page/size/sort в ключ COUNT не входят.
  Для R2 они входят в ключ страницы вместе с остальными параметрами ответа.
- Штатный Spring Cache с Caffeine: ограничение числа записей,
  expireAfterWrite и один загрузчик на ключ. Сейчас этих зависимостей
  в backend нет. Не использовать бесконечную Map, expireAfterAccess для
  требования максимального возраста или отдельный Redis без потребности.
  Вызов кешируемого Spring-бина проходит через proxy; self-invocation
  не включает кеширование. Ошибка загрузки не превращается в total=0.
- При R1 строки читаются актуальными, hasNext определяется по size+1,
  total получает время актуальности и явно допускает отставание.
  Старое число не должно обрезать навигацию или скрывать следующую страницу.
  При R2 строки и total относятся к одному сохранённому снимку.
  У обеих схем права проверяются актуально; кеш не продлевает выданный доступ.
- Если продукт допускает задержку, сброс total после каждого create/status
  уничтожает смысл кеша. Правила безопасности рассматриваются отдельно.
  Переименование само по себе не меняет предикаты COUNT.
- Карточки, команды и история остаются актуальными; revision, идемпотентность,
  транзакции записи и атомарность outbox не меняются. Созданную задачу
  можно сразу открыть, даже если реестр ещё показывает предыдущий снимок.

Затронутые границы: contracts/internal-api.openapi.yaml (TaskPage),
TaskService.list, TaskReadRepository, SpringDataTaskReadRepository.page,
потребители task-queries/use-task-list и общей навигации.
dto/Page общий для нескольких сценариев: не менять HistoryPage/IssuePage
как побочный эффект кеширования реестра. Клиент и интерфейсы контроллеров
генерируются при сборке, в исходники сгенерированное не добавляется.

### 12.3. Когда усложнение оправдано

R5 имеет смысл при множестве различных повторяющихся фильтров.
Сводка owner/status не отвечает на произвольный createdAt interval;
группировка по дням требует обработки неполных граничных дней.
Полная materialized view переносит строки, но её COUNT остаётся подсчётом
совпавших строк. Сравнивать нужно всю работу refresh плюс чтения.

R6 нужен только при доказанном превышении цены индексируемой основной таблицы.
Очередь доставки не является журналом всех изменений реестра: rename
пишет task/history, но не enqueue. Поэтому нельзя строить полную UI-проекцию
только по delivery outbox. Потребуются атомарная фиксация всех значимых
изменений, порядок версий, повторяемое применение, восстановление и проверка
отставания. Объединение изменений в пачках полезно, только если оно действительно
уменьшает количество записей. Копирование каждого изменения 1:1 на той же БД
может увеличить нагрузку. Брокер и отдельный процесс заранее не требуются.

Другие варианты остаются условными:

| Вариант | Когда возвращаться | Почему не первым |
| --- | --- | --- |
| Разделить стабильные и часто меняющиеся поля | После кеширования по-прежнему дорого обходить heap из-за churn; это видно в планах/visibility. | Дополнительные таблица, join и правила блокировок; HOT зависит также от индексов и места на странице. |
| Частичные/покрывающие индексы | Есть конкретный дорогой SELECT и подходящая селективность/предикат. | Индексы тоже стоят записей; большинство SUCCEEDED не является автоматически хорошим partial index. |
| Партиции | Подтверждены pruning по периоду или потребность быстро удалять большие периоды истории. | Поиск page0 и COUNT без подходящего partition predicate не исчезают; текущие данные не доказывают потребность. |
| Реплика/Redis | Несколько экземпляров и доказанная выгода общего кеша либо изоляции чтения. | Дополнительные ресурсы, задержка и восстановление; реплика не отменяет обслуживание индексов primary. |
| Большие Hikari/in-flight, иная изоляция, JIT/prepared | Измерены соответствующие ожидания/планирование/конкуренция. | Без причины можно усилить давление на PG или потерять согласованность. READ COMMITTED не устраняет COUNT. |
| Сбалансировать CPU | Отдельный этап S7 после архитектурных экспериментов. | Это смена ресурсных условий, не ускорение алгоритма. |

### 12.4. Порядок проверки и критерий принятия

1. На фиксированных растущих QA-данных отделить цену page SELECT от COUNT:
   планы с реальными типами параметров и EXPLAIN (ANALYZE, BUFFERS).
   Для изменённых записей добавить WAL и безопасный откат только в тестовой БД.
   Одиночный план не объясняет конкурентные ожидания.
2. Выбрать контракт R1/R2, затем реализовать один небольшой эксперимент.
   Две секунды — предложенный срок, не согласованная текущая настройка.
   Не оставлять постоянные параллельные реализации и fallback-цепочки.
3. Сравнить прежний и новый варианты при одинаковых лимитах, данных,
   прогреве и наблюдателе. Сохранить все HTTP-вызовы mixed-профиля;
   начать с 70 циклов/с, затем проверять повышенную ступень при наличии выигрыша.
   Дополнительно проверить множество разных фильтров, холодный кеш и
   одновременное истечение популярных ключей. Старые длинные 90 и новые
   короткие 90 не являются взаимозаменяемыми контрольными результатами.
4. Измерить hit/miss и число реальных SQL, PG CPU, WAL, API p95/p99,
   принятую скорость, очередь и возраст заданий. Включать пересчёт/refresh
   и проверки доступа в общую стоимость. Проверить все принятые задания,
   историю и результаты; ускорение ответа не оправдывает рост очереди.
5. Адресные тесты: изоляция владельцев/ролей, UTC-границы, пустые/глубокие
   страницы, hasNext при старом total, create/status/отзыв доступа,
   истечение и ограничение кеша, один загрузчик для одного ключа,
   независимость разных ключей и явная ошибка при сбое загрузки.
   Время кеша в unit-тестах управляемое, без ожидания реальных секунд.
6. Текущий mixed-тест проверяет total >= 2500; этого недостаточно.
   После истечения кеша и остановки изменений сверить total с точной БД,
   чтобы вечное число 2500 не прошло как оптимизация.
7. Принять вариант только при воспроизводимом выигрыше сверх разброса
   контролей и сохранении корректности. Иначе удалить эксперимент.
   Только затем проверять R3 с полным набором потребителей индекса.
   Полную квалификацию запускать после интегрированного изменения,
   а не после каждого мелкого шага.

Новых нагрузочных/SQL-экспериментов в рамках этого исследования не запускали.
R1–R6 — проверяемые кандидаты, а не измеренное улучшение приложения.

### 12.5. Проверенные первичные источники

- [PostgreSQL VIEW](https://www.postgresql.org/docs/18/sql-createview.html),
  [materialized views](https://www.postgresql.org/docs/18/rules-materializedviews.html)
  и [REFRESH](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html):
  обычный VIEW не хранит результат; materialized требует оплачивать обновление.
- [Spring Boot cache](https://docs.spring.io/spring-boot/reference/io/caching.html),
  [Spring Cache sync](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html),
  [Caffeine eviction](https://github.com/ben-manes/caffeine/wiki/Eviction):
  провайдер, ограничения размера/возраста, синхронизация загрузки и proxy.
- [Spring Data Page/Slice](https://docs.spring.io/spring-data/commons/reference/repositories/query-methods-details.html):
  цена точного итога и вариант size+1 без количества всех страниц.
- [PostgreSQL HOT](https://www.postgresql.org/docs/18/storage-hot.html),
  [index-only scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html),
  [partial indexes](https://www.postgresql.org/docs/18/indexes-partial.html):
  условия уменьшения heap/index работы вместо обещания бесплатных индексов.
- [Hot standby](https://www.postgresql.org/docs/18/hot-standby.html)
  и [EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html):
  задержка реплики и проверка фактических планов.
