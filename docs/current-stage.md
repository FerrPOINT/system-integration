# Текущая стадия

В работе SI-07: правила повторов, SQL списка проблем, диагностика очереди,
демонстрация и повторная квалификация. Публичная версия пока остаётся f0d3be0.
На кандидате 893e55d прошли 57 серверных тестов, 40 UI-сценариев, семь
восстановительных этапов и NF08. В capacity на 80 клиентах обнаружена
необработанная ошибка получения соединения, превращавшаяся в 403.
Адресная регрессия уже подтверждает исправление 503; новые ресурсные настройки,
полный повтор нагрузки, чистый запуск и публикация ещё не квалифицированы.
План — в [декомпозиции](decomposition.md#si-07-доработки-после-архитектурного-ревью).

Кандидат SI-06 f0d3be0 опубликован на
[demo.azhukov-dev.ru](https://demo.azhukov-dev.ru).
SI-00–SI-05 приняты ранее. Проверки SI-06 завершены, включая негативную регрессию полного HTTP deadline.

## Рабочая среда и версия

Исходники, Git, сборки и тесты находятся на Firebat1 в
/opt/dev/system-integration. Все три образа имеют revision f0d3be0.
Ниже приведены результаты этого кандидата от 12 ноября 2026 года.
Классы и ресурсы Java внутри контейнеров совпали с проверенными bootJar;
SHA256 публичного JavaScript совпал с файлом frontend-контейнера.

Публичный путь: Koara TLS gateway → обратный SSH-туннель → frontend Firebat1.
Обычные БД si_app/si_emulator возвращены, туннель работает.
БД, backend, эмулятор и тестовые команды доступны на Firebat1 только через loopback.
Пароли хранятся в приватном .env; в Git и отчётах их нет.

## Внешняя очередь под нагрузкой

API быстро принимает задания, но внешнее исполнение при непрерывной записи
отстаёт. В NF08 из 12141 заданий измерительного окна
при независимой сверке 1251 имели итог,
10890 ожидали исполнения.
p95 от создания до исполнения среди завершённых — 115.3 с;
ошибок сверки нет. Этот показатель отделён от p95 ответа API.

Capacity использует 15 с прогрева и 60 с измерения на ступень:

| Клиентов, смесь | p95 чтения, мс | p95 записи, мс | Запросов/с | Максимум ожидающих |
| --- | ---: | ---: | ---: | ---: |
| 20 | 186 | 108 | 303 | 4719 |
| 40 | 296 | 293 | 316 | 5206 |
| 80 | 611 | 603 | 274 | 5379 |

Для чистого чтения p95 на 20/40/80 клиентах составил 95/171/296 мс,
скорость — около 620 запросов/с. На последней смешанной ступени проверены
5 679 новых внешних операций: все исполнены однократно, история и права сохранены.
Пустая очередь наблюдалась примерно через 48 с после прекращения нагрузки;
проверка результатов завершилась примерно через 57 с.
p95 внешнего исполнения — 73,1 с.

Это измеренные короткие пики двух авторизованных инициаторов на указанном
бюджете. Они не доказывают непрерывную обработку такого потока новых заданий,
массовую авторизацию, суточную устойчивость, миллионы записей или несколько реплик.
Новые клиенты после 80 не измерялись; значение 80 — последняя пройденная ступень,
а не найденный абсолютный предел.

## Принятые настройки

В обоих Java-процессах включены virtual HTTP threads и keep-alive.
Фоновые fixedDelay-задачи используют явный планировщик на два потока.
Hikari ограничен 8/4 соединениями, ожиданием 2 с и validation-timeout 1 с.
Доставка обрабатывает до восьми пачек по четыре; сеть остаётся вне транзакции.
PostgreSQL использует shared_buffers 256 МиБ, effective_cache_size 768 МиБ,
work_mem 4 МиБ при лимите 1472 МиБ.

Индексы очереди, ожидающих операций и списка по владельцу/статусу добавлены
после SQL-измерений отдельными миграциями V5/V6 приложения и V2 эмулятора.
Redis, Caffeine и кэш SQL-ответов не добавлялись.
PostgreSQL владеет данными и квитанциями команд; React Query — запросами вкладки.
Правила и ограничения описаны в [архитектуре](architecture.md).

## Регрессия полного HTTP deadline

Четыре сценария ExchangeClientTest прошли на настоящем временном HTTP-сервере
с привязкой только к 127.0.0.1: задержанные заголовки, зависшее тело после ранних
заголовков, полный JSON и отказ соединения. После тайм-аута тот же клиент
успешно выполняет следующий запрос и закрывается, пока первый обработчик
ещё удерживает ответ. Отказ соединения отличается от неопределённого исхода.

Регрессия проверена на падение: прежняя реализация ExchangeClient из e7b301b
не завершила чтение зависшего тела за 4 с; вариант без cancel не завершил close
за 1 с. После восстановления текущей реализации все модульные тесты прошли.
Тест не использует Spring-контекст, PostgreSQL или публичный стенд.
SI-06.3/06.5/06.6 закрыты.
