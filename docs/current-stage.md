## Архитектура и границы

Два Spring Boot приложения, PostgreSQL и React frontend. Domain остаётся без
Spring/JDBC/generated DTO; service владеет правами и транзакцией, controller/mapper —
HTTP. Spring Data JDBC читает карточки, реестр и историю; JDBC сохраняет команды,
очередь, попытки, квитанции и сложные проекции.

Задание, outbox, история и квитанция атомарны; результат и курсор — тоже.
Сеть выполняется вне транзакции. Сохраняются пять попыток в серии, leases/fencing,
Unicode code points, совместимость сохранённых значений и управляемое восстановление.
Правки Q1–Q7 не добавляли зависимости, процессы, кэши, партиции и миграции.

## Нагрузка

Следующие измерения относятся к отдельному кандидату f638e93.
SQL, алгоритм очереди, пулы и потоки в текущем срезе не менялись; нового
нагрузочного или EXPLAIN-прогона этот срез не заявляет.

| Профиль | Сохранённый результат |
| --- | --- |
| NF08: 5000 записей, 20 клиентов, 30s warm + 120s measure | PASS; 51 700 запросов без ошибок, read/write p95 99,32/99,46 мс. Все 20 058 итоговых записей корректны. |
| Полная смесь 60×4, 3×300s | PASS, sustainable=true; 59 900 записей, худший list/create p95 37,63/34,44 мс. |
| Дополнительный 70×4, 3×300s | Данные и HTTP корректны, sustainable=false: mean pending 30,94→34,42 при допустимом приросте 2. |

60×4 означает по 60 созданий, переименований, списков и карточек в секунду.
Контейнеры суммарно ограничены 2 CPU / 4 ГиБ, включая frontend.
Генератор работал на сервере вне их cgroup через localhost API; публичная сеть
и браузер не измерялись. В интенсивном NF08 первое отправление p95 — 70,73s;
после окна очередь полностью обработана. 70×4 устойчивым не считается.

Для f638e93 также сохранены 69 SQL sites, 542 варианта и 1626 EXPLAIN с
BUFFERS/WAL, проверки V10, 10 recovery и 6 demo. Подробности —
в [журнале оптимизации](exchange-performance-plan.md) и
[истории завершённых этапов](history.md).

## Ограничения

- Принятие HTTP не обещает немедленного внешнего исполнения.
  Точный предел мощности и неограниченный рост базы не установлены; COUNT линейный.
- Idle timeout 60s защищает бездействие внутри транзакции.
  Общего statement/lock/socket timeout и SQL-бюджетов нет.
- Закрытие общей проблемы ленты не исправляет источник и не снимает invalid-page
  pause: источник исправляется отдельно, затем перезапускается worker.
- OS-скан из предыдущего цикла с 30 Medium / 4 Low без исправления на тот момент
  не считается новой проверкой или устранением находок. Зависимости не обновлялись.
- Source, тестовая установка и публичное demo — отдельные версии.
  Тесты не направлялись на публичные данные.
