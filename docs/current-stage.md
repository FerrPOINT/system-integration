## Архитектура и границы

Один backend, отдельный эмулятор, две прикладные БД на одном PostgreSQL.
Domain не зависит от Spring/JDBC/generated DTO; controller/mapper владеют HTTP,
service — сценарием, правами и транзакцией, repository — хранением.
Spring Data JDBC обслуживает обычные чтения; явный JDBC — команды, outbox,
квитанции, блокировки и сложные проекции. Сеть вне транзакции.
Задание/outbox/история/квитанция и применение результата/cursor атомарны.

Доставка имеет пять автоматических вызовов на серию. Дальнейшее продолжение
разрешает оператор после свежей сверки. V11 нормализует прежние открытые
DELIVERY_DELAYED, V12 удаляет неиспользуемый http_status квитанции.
Старый backend, пишущий этот столбец, после V12 несовместим со схемой:
порядок обновления описан в [deploy/README](../deploy/README.md).

PR #18 добавляет привязку команд к поколению сессии, проверку userId при
получении CSRF, фиксацию ключа до первого await и явное восстановление ошибки
подгрузки ленты. Основной API-объём и доменные правила сохраняются.

## Ограничения

- HTTP-принятие не обещает немедленного внешнего исполнения.
  Точный предел мощности для произвольного роста БД не установлен; COUNT линейный.
- Idle timeout 60s защищает бездействие в транзакции. Общего statement/lock/socket
  timeout и SQL-бюджетов нет; активная внешняя блокировка может задержать запрос.
- Закрытие общей проблемы ленты не исправляет источник и не снимает invalid-page
  pause: источник исправляется отдельно, затем перезапускается worker.
- Современный браузер должен поддерживать Web Locks и matchMedia.
  Web Locks требует HTTPS либо loopback; отсутствие API объясняется явно.
- OS-скан предыдущего цикла с 30 Medium / 4 Low не является новым сканом
  текущих образов; устранение этих находок без проверки не заявляется.
- Source, QA и публичное demo — отдельные версии; reset и нагрузка не работают
  с публичными данными.
