# План уменьшения задержек API и фонового обмена

Дата: 15 ноября 2026 года.
Статус: измерения и SQL-планы выполнены. Кандидат ручного SQL отклонён
после одинакового контейнерного A/B/A; сохранён Spring Data. Пул4 отклонён
в пользу8. Удаление повторной очистки и частый autovacuum отклонены;
prepared COUNT отдельной проблемы плана не показал. Проверяется снятие
барьера медленного ответа между проходами с прежним глобальным лимитом;
выбран глобальный механизм ожидания слотов и штатное определение CPU JVM;
конечная квалификация впереди.
Проверенная база: Firebat1 /opt/dev/system-integration/.local/structure,
HEAD c7bdd4c, прикладной код a405814. Разница между ними — документы.
Основание: диагностические профили и receipts в ignored
`tests/results/bottleneck-2026-11-15`; ключевые измерения приведены ниже.
Исходный тег: `baseline/pre-read-path-optimization-2026-11-15` → c7bdd4c.

## Что именно тормозит

Пул Hikari содержит 8 соединений. Это ограничение количества одновременно
выданных соединений, а не количество заданий, которое система вообще умеет
обработать. Ожидание свободного соединения и ожидание блокировки строки —
разные события.

В полной смеси API и worker делят backend с лимитом 0,6 CPU и общий пул;
PostgreSQL ограничен одним CPU. Дополнительные чтения занимают CPU и
соединения дольше, а фоновые claim/finish ждут вместе с остальными операциями.
Увеличение числа соединений не добавляет процессорной мощности.

| Вопрос | Подтверждённый ответ |
| --- | --- |
| Пул точно слишком маленький? | Нет. Ожидания есть, оптимальный размер ещё не сравнивали. |
| БД массово блокирует строки? | Такой механизм не подтверждён: в 900 частых снимках полного контроля нет блокирующих сессий. |
| CPU ограничивает работу? | Да: под чтениями backend 0,580 из 0,6 ядра, PG 0,930 из одного, наблюдается throttling. |
| Где дорогой сценарий? | Реестр: Spring Data mapping, обработка результата и точный COUNT внутри транзакции. |
| Нужны партиции? | Сейчас оснований нет: не доказаны ни полезное отсечение больших частей данных, ни горячая блокировка очереди. |

Одинаковые 90 созданий + 90 изменений/с, только средняя фаза добавляет
90 списков + 90 карточек/с: p95 исполнения 3,985 с при чтениях и 0,340 с
после их отключения. Claim/finish p95 — 106/188 против 6/6 мс.
Это локализация механизма, а не измеренный выигрыш будущей правки.
Первое окно контроля включало дополнительный прогрев; общий коэффициент
ускорения по одному ABA не считается универсальной оценкой.

COUNT в одном живом EXPLAIN прошёл всю tasks за 4,607 мс,
выбор задания очереди — за 0,276 мс. В отдельном коротком смешанном
профиле COUNT составил 41,9% накопленного времени первых 40 SQL.
Это доля времени SQL, не доля CPU и не все расходы приложения.

В коде уже есть плоская проекция TaskReadRow и индекс
tasks_owner_status_created(owner_id,business_status,created_at DESC,id DESC).
Их повторное «внедрение» не входит в план. Контракт списка требует result
для завершённых записей: просто выкинуть JSON результата тоже нельзя.

## Выбранный подход

Сначала уменьшаем работу в существующих service/repository, затем подбираем
параллелизм под реальную мощность БД. Один механизм чтения, один владелец
преобразования результата, прежние права и внешние контракты.

Основная последовательность: шаг 1 → шаги 2–3 → адресное сравнение →
шаг 4 при оставшейся проблеме → шаг 5 при подтверждённой необходимости →
итоговая проверка. Варианты не накапливаются в production-коде:
остаётся один измеренно полезный путь.

Разделение на дополнительные сервисы/пулы, Redis, партиции и увеличение
ресурсов не являются исходным решением. Они требуют отдельного доказательства
после простых изменений; в текущую реализацию автоматически не добавляются.

## 1. Зафиксировать сравнение и разделить время

Владельцы: tests/load, существующие SqlWorkflowProfileTest и ReadSqlCapture.
Начать с текущих default: 2 CPU / 4 ГиБ, пул backend 8, доставка 32,
эмулятор execution batch 5. Снять SHA образов/JAR и настройки.

В одном наборе измерений отделить:

- ожидание выдачи соединения Hikari;
- длительность владения соединением;
- выполнение SQL, Java mapping/JSON и завершение транзакции;
- HTTP и последующий finish;
- ожидание задания до первой попытки и применения результата.

Использовать штатные Hikari/Micrometer, JFR и pg_stat_statements.
Оставшиеся пробелы закрыть узким тестовым измерителем, без нового публичного
endpoint, framework или постоянных per-task таймеров. Нынешний
SqlWorkflowProfileTest не измеряет acquisition/commit — явно учесть это.
Суммы параллельных ожиданий не складывать в wall time.

Нагрузку воспроизводить с одинаковыми arrivals и бизнес-операциями.
Отдельно разогреть сценарии чтения/изменения, учитывать операции разогрева
в сверке данных. Повторить исходный контроль, чтобы знать разброс.
Не требовать повторяемости единичного значения 3985 мс до миллисекунды.

Результат шага: понятно, сколько занимает SQL, mapping и удержание соединения.
До этого не выбирать новый размер пула или широкую перепись адаптера.

## 2. Уменьшить Java-расходы реестра

Места: SpringDataTaskReadRepository.page, TaskReadRow,
TaskResultReader.outcome, TaskApiMapper; проверки SpringDataReadsTest,
ReadBoundaryTest, SqlWorkflowProfileTest.

Проверить раздельно стоимость построения динамического запроса, materialization
20 строк, разбора accepted_result и формирования ответа. Убирать только
подтверждённые повторные вычисления/преобразования.

Первый вариант — оптимизация текущего Spring Data пути с прежней проекцией.
TaskResultReader остаётся единственным владельцем трактовки результата;
не вводить второй SQL/Java parser с другими правилами и не скрывать ошибочные данные.

Если основная цена остаётся внутри framework mapping/query generation и
штатное средство её не снимает, сделать небольшой тестовый сравнительный
эксперимент с явным SQL и существующим RowMapper для того же read-контракта.
Это не заранее принятое решение заменить Spring Data.

Выбирать явный SQL только при воспроизводимом выигрыше и сохранении
простоты: точечный горячий метод, параметры привязаны, фильтры не дублируются,
старый путь удаляется. Если не требуется — оставить Spring Data.
Обоснование исключения и Javadoc обновить в docs/spring-data-read-plan.md.
Не создавать универсальный query builder или дополнительный слой ради одного метода.

Сохранить состав TaskPage, terminal result, owner scope, сортировку,
полуоткрытые границы UTC и точные totalItems/totalPages.

## 3. Проверить и уменьшить стоимость COUNT

Места: SpringDataTaskReadRepository.page, миграция V6 как существующая база,
tests/sql/plans.py, тесты counted-пагинации.

Для реальных owner/status/date-фильтров и ролей снять
EXPLAIN (ANALYZE, BUFFERS), включая пустую и глубокую страницу.
Сравнить 5000, 20000 и 50000 записей, разные доли статусов и распределения
владельцев. Фиксировать rows/loops, heap fetches, чтения, planning/execution,
статистику таблиц, dead tuples, видимость страниц и работу autovacuum.

Порядок решений:

1. Проверить корректность условий, типов параметров и статистики планировщика.
2. Если доказано влияние обслуживания таблицы — проверить адресную штатную
   настройку autovacuum/ANALYZE на продолжительном потоке, включая её CPU/WAL.
3. Новый индекс рассматривать только при недостаточности существующего.
   Сравнивать также цену INSERT/UPDATE, WAL и размер индекса.
4. Если точный COUNT уже выполняется рационально — не добавлять бесполезную
   миграцию. Продолжить уменьшение суммарной стоимости read/транзакций.

Seq Scan не считается ошибкой сам по себе. Не заставлять PostgreSQL использовать
индекс глобальным enable_seqscan=off и не делать ручной VACUUM перед каждым тестом,
чтобы получить красивый отчёт.

Два запроса страницы и COUNT сохраняют общий снимок REPEATABLE_READ.
Не заменять его READ_COMMITTED, приблизительным счётчиком или Slice.
COUNT OVER не принимать только ради «одного запроса»: учитывать пустые
глубокие страницы и стоимость обработки всего набора.

Схема по умолчанию не меняется. Если новая миграция действительно нужна —
добавить следующую Flyway-миграцию, не переписывать V1–V7.

## 4. Сократить время владения соединением

Места: TaskService, ExchangeService, IdempotencyService,
JdbcTaskRepository.history/auditAfterCommit и связанные адаптеры.

После шагов 2–3 повторить профиль. Сначала убирать лишнюю работу внутри
существующих границ, не переносить транзакции в контроллеры.

Проверить стоимость преобразований, журналирования после commit до возврата
соединения, повторных JDBC round trips. Сохранять аудит и смысл момента
«операция зафиксирована»; не вводить для него асинхронную недолговечную очередь.

Если finish/consume остаются дорогими из-за поштучных JDBC-вызовов,
сравнить штатный JDBC batch для однородных записей в пределах прежней
ограниченной транзакции. Не менять порядок событий, cursor, fencing,
атомарность или размер пачки без отдельного измерения.
Spring Batch и новый writer/framework не требуются.

Не выносить ленивые persistence-объекты за транзакцию. Изменение границ
допустимо только при явном сохранении согласованного снимка и модели слоёв.
При отсутствии измеренного выигрыша текущую границу оставить.

## 5. Подобрать пул и параллелизм — только после устранения лишней работы

Если проблема исчезла — конфигурацию оставить. Если сохраняются существенные
ожидания выдачи соединения — сначала сравнить backend Hikari 4 / 8.
Вариант 12 проверять только при занятых 8 соединениях и измеренном запасе CPU
backend/БД, по одному изменению за раз. Исходная память, суммарные 2 CPU
и одинаковый поток неизменны.

Сравнивать одновременно API, скорость исполнения, возраст/размер очереди,
Hikari active/pending/acquire/usage, SQL и CPU throttling.
Вариант, ускоривший API ценой ухудшения фоновой доставки, не принимать.

Цель — минимальная достаточная конкуренция, а не максимальное число соединений.
Не вычислять пул по 16 ядрам физического Firebat1, игнорируя лимит PG в одно ядро.
Если 12 соединений не дали повторяемого выигрыша — не увеличивать default.
Если меньший пул лучше — это допустимый результат.

Число virtual threads не добавляет CPU. Отдельные datasource/transaction managers,
разделение пулов API/worker и новые ограничения запросов не являются частью
этого шага. Вернуться к ним можно только при доказанном starvation с запасом
CPU и отдельным сравнением более простых решений.

## 6. Итоговая проверка и критерий принятия

В ходе изменений — адресные unit/PostgreSQL-тесты и короткие сравнения.
Один полный согласованный gate после выбранного интегрированного результата.

Проверки корректности:

- Оба владельца и оператор; изоляция чужих записей.
- Пустая, обычная и глубокая страницы; все фильтры/UTC/статусы.
- Точный COUNT и единый снимок при конкурентном создании/завершении.
- Тот же terminal result и явная ошибка повреждённых данных.
- Конкурентные claim/finish, истёкший lease и поздний ответ.
- Идемпотентность, конечные повторы, cursor, история и восстановление.
- При изменении batch — rollback всей группы и независимая соседняя группа.

Проверки производительности:

1. Повтор фиксированной полной смеси: 90 созданий + 90 изменений/с;
   чтения включаются/выключаются независимо. База → кандидат → контроль,
   с одинаковым прогревом и учётом размера данных. Не путать рост количества
   запросов closed-loop с ростом мощности доставки.
2. Для выбранного кандидата — длительная проверка полной смеси,
   чтобы короткий удачный интервал не скрывал рост/возраст очереди.
   Если эта ступень неустойчива, явно так и записать; не заявлять 90/с
   поддерживаемой мощностью. Не обещать заранее p95 340 мс под полной смесью.
3. Исходный NF08: 5000 записей, 20 клиентов, 30/120 с, равная смесь операций,
   2 CPU / 4 ГиБ; p95 чтения ≤2 с, изменения ≤3 с, без маскировки ошибок.
4. Прежний настоящий непрерывный steady 50/с × 3×300 с:
   прежние критерии устойчивости, все arrivals, полная сверка.
5. Текущие Java/архитектура/OpenAPI/build/style, SQL-планы, UI,
   recovery и demo — на конечном кандидате; актуальные количества тестов,
   а не требование навсегда сохранить старое число 250.

Правка принимается, если на одинаковой нагрузке снижение задержки/CPU/времени
владения соединением повторяется за пределами разброса, очередь и API не
ухудшились, обязательные проверки пройдены. Если выигрыш не подтверждён,
экспериментальный путь удалить, а не накапливать «оптимизации».
Новые SQL-бюджеты, отказы по сложности запроса и тайм-ауты ради зелёного теста
не вводятся. Критерии теста не превращаются в ограничения приложения.

## Когда понадобятся партиции

Партиционирование tasks имеет смысл возвращать в обсуждение, если рост объёма
подтвердит дорогой доступ к большим данным и конкретный ключ позволит
отсекать значительную часть таблицы. Нужно показать выигрыш EXPLAIN и учесть
уникальность operation_id, внешние ключи, миграцию и обслуживание.

Разделение очереди между worker-ами — другой механизм. Оно требует доказанного
горячего участка/конкуренции за блокировки или потребности в горизонтальном
масштабировании. Текущие измерения этого не подтвердили.
Ни один вид партиций не добавляет CPU текущим контейнерам.

## Завершение реализации

Обновить существующие docs/exchange-performance-plan.md,
docs/current-stage.md, docs/architecture.md и docs/spring-data-read-plan.md

Сохранить компактные исходные отчёты, причины отклонения вариантов и границы
результата. Закрыть свои QA-контейнеры/том/сеть и проверить соседние приложения.

Подготовка к слиянию, merge и публичный deploy — отдельные действия.
Текущий цикл охватывает исполнение плана, проверку и подготовку к слиянию.
Merge и публичный deploy в него не входят.

## Официальные основания

- [HikariCP: About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing):
  большой пул не равен высокой пропускной способности.
- [Spring Data Relational 4.1.2: projections](https://docs.spring.io/spring-data/relational/reference/repositories/projections.html):
  использовать реальные возможности уже существующей плоской модели.
- [PostgreSQL 18: partitioning](https://www.postgresql.org/docs/18/ddl-partitioning.html):
  партиционирование оценивается по доступу к данным и partition pruning.
