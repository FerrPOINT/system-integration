# Аналитика

## Задание и роли

В качестве демонстрационной операции исполнитель проверяет вымышленную заявку.
Запрос состоит из `reference` (номер вида `REQ-123456`) и `quantity` (целое число
от 1 до 1000). До 100 единиц включительно заявка проходит проверку. При большем
количестве исполнитель возвращает `QUANTITY_LIMIT_EXCEEDED`. Это бизнес-отказ,
при котором обмен завершился корректно. Название задания относится к реестру
и может меняться независимо от зафиксированного внешнего запроса.

| Действие | Инициатор | Оператор |
| --- | --- | --- |
| Создать задание | От своего имени | — |
| Список, карточка, история | Свои задания | Все задания |
| Изменить название | Своё задание | — |
| Посмотреть проблемы, взять разбор на себя, сверить состояние, повторить, принять решение | — | Для доступных оператору заданий |

Сервер берёт владельца из сессии. Чтение чужого задания, его истории и попытка
изменить название для инициатора возвращают `404 NOT_FOUND`, как для
отсутствующей записи. Для защищённого запроса порядок проверок — сессия
(`401 SESSION_REQUIRED`), CSRF для записи (`403 CSRF_INVALID`), роль
(`403 ACCESS_DENIED`), затем объект и допустимость операции. Неверный вход
возвращает `401 INVALID_CREDENTIALS` без уточнения, существует ли логин.

Пользователь входит по логину и паролю. Браузер передаёт сессионную cookie
на тот же origin. Для команды, меняющей состояние, frontend передаёт
CSRF-токен. После входа и выхода клиент запрашивает свежий токен. Форматы
запросов, заголовки и ошибки описаны во [внутреннем API](../contracts/internal-api.openapi.yaml).

Владелец задания — создавший его инициатор. У открытой проблемы по заданию
отдельный ответственный оператор. Сразу после появления проблемы это поле
пустое. Действие «Взять разбор» записывает текущего оператора. Если разбор
уже ведёт другой оператор, действие передаёт ответственность. Сервер
сохраняет ID прежнего и нового ответственных, автора и время одним событием.
Назначение служит для координации разбора. Доступ по-прежнему определяется
ролью оператора и владельцем задания. Авторство существующих событий сохраняется.

## Состояния

| Измерение | Состояния и переходы |
| --- | --- |
| Доставка | `QUEUED` после локальной записи → `ACKNOWLEDGED` после подтверждения. Временная ошибка до отправки даёт `RETRY_WAIT`, неопределённый исход — `UNKNOWN`. Ошибка протокола или исчерпание серии приостанавливает отправку в `NEEDS_REVIEW`. Явное решение оператора прекратить её даёт `STOPPED`. |
| Исполнение | `PENDING` после создания → `RUNNING` по снимку версии 1 → `SUCCEEDED` или `REJECTED` по версии 2. Если итог пришёл раньше промежуточного снимка, допустим прямой переход из `PENDING` в итог. |
| Проблема | Открывается по причине обмена или сверки. Оператор видит причину, снимки, допустимые команды и записанное решение. Проблема результата после доставки не меняет `ACKNOWLEDGED`. |

Подтверждение, GET состояния и каждое событие содержат неизменные ID и запрос
операции. Приложение сравнивает их с сохранённым заданием до изменения
доставки или исполнения. Несовпадение в событии сохраняется как конфликт
и оставляет оба состояния прежними. Для ответа на PUT или уточняющий GET
несовпадение считается ошибкой подтверждения по таблице доставки.

При корректной позиции ленты обработка снимка выполняется в следующем порядке.

1. Проверить схему, ID операции и равенство `reference` и `quantity`
   сохранённому запросу. Для GET дополнительно проверить согласованность
   ID и запроса внешней записи с вложенным результатом.
2. Повтор уже принятой версии с тем же содержимым пропустить.
   Более старую версию отметить в истории без изменения состояния.
3. В `NEEDS_REVIEW` новый снимок сохранить как наблюдение текущей проблемы.
   В `STOPPED` открыть проблему расхождения. Это правило действует и для
   `RUNNING`, и для конечного результата. Их принятие ожидает решения
   оператора по свежей сверке.
4. Проверить версию и допустимость перехода. Изменённое содержимое той же
   версии либо недопустимый переход открывают конфликт.
5. Применить допустимую новую версию, подтвердить доставку и сохранить
   историю вместе с позицией ленты в одной транзакции.

Допустимый снимок может подтвердить доставку раньше ответа на PUT.
Поздний ответ сохраняет уже записанное подтверждение. Его ID и запрос
проходят ту же проверку идентичности.
У проблемы сохраняются причина и допустимые поля входящего результата.
Для известного задания также сохраняется локальный снимок на момент ошибки.
Исходный ошибочный пакет в API не выдаётся.
Для сообщения, которое невозможно разобрать по контракту, сохраняются причина,
его отпечаток и позиция. Валидный конфликтный снимок доступен оператору целиком.

Для ошибочного входящего события причина и содержимое в области операции
задают один отпечаток. При его расчёте исключаются курсор и время получения.
Повтор того же события продвигает курсор и использует прежнюю проблему,
включая закрытую. Иное ошибочное содержимое создаёт отдельную проблему.

## Доставка и повтор

У операции одна запись очереди, сквозной номер попытки и отдельный счётчик
текущей серии. Серия содержит максимум пять автоматических вызовов: PUT и
уточняющий GET расходуют один и тот же лимит, включая тайм-аут и прерванный
захват. Между вызовами — 2, 5, 15 и 60 с. Перед HTTP атомарно сохраняются
номер, вид попытки и расход счётчика серии. Тайм-аут подключения — 1 с, ожидания ответа — 2 с.

| Событие | Статус доставки и следующий шаг |
| --- | --- |
| Первое локальное сохранение | `QUEUED`. Начать с PUT по ID операции. |
| PUT вернул валидное подтверждение `200` или `202` | `ACKNOWLEDGED`. Цикл отправки закрывается. Итог приходит через ленту. |
| Соединение с эмулятором заведомо не установилось при PUT | `RETRY_WAIT`. Следующий шаг — PUT с тем же ID. |
| Ответ PUT потерян, истёк тайм-аут ответа, получен `503` или другой временный `5xx` | `UNKNOWN`. Записать неопределённость и открыть `DELIVERY_UNCERTAIN`, если доставка ещё не подтверждена. Следующий шаг — GET по тому же ID. |
| Уточняющий GET вернул валидное состояние | `ACKNOWLEDGED`. Записать исход уточнения. Фоновый GET подтверждает приём, а нормальный результат приходит через ленту. |
| Уточняющий GET вернул `404 OPERATION_NOT_FOUND` | `RETRY_WAIT`. Следующий шаг — PUT с прежним ID. |
| Уточняющий GET временно недоступен | `UNKNOWN`. Следующий шаг — повтор GET. |
| `400`, `409 OPERATION_CONFLICT`, неожиданный постоянный ответ или неверное тело подтверждения | `NEEDS_REVIEW` с причиной `PROTOCOL_ERROR`. Автоматический повтор прекращается. |
| Четвёртая попытка завершилась временной ошибкой | Сохранить `RETRY_WAIT` или `UNKNOWN`, назначить пятый вызов через 60 с. |
| Пятая попытка завершилась временной ошибкой | `NEEDS_REVIEW`, проблема `DELIVERY_DELAYED`. Сохранить очередь и историю остановки, очистить захват. Автоматического шестого вызова нет. Успех на пятой принимается штатно. |
| Процесс перезапущен после захвата попытки без записанного исхода | После истечения захвата отметить её как прерванную. При остатке лимита продолжить с GET по тому же ID; при исчерпании приостановить доставку. Уже сохранённая попытка учитывается один раз. |

Время следующего шага хранится в БД. После перезапуска обработчик использует
этот срок. После прерванного захвата интервал считается от его истечения.
До исчерпания лимита восстановление доступности позволяет продолжить автоматически.
После остановки нужна явная команда оператора со свежей сверкой, причиной,
актуальной версией проблемы и свободным захватом. Она начинает новую серию
с уточняющего GET, сохраняя ID, исходный запрос и общий номер попытки.
Replay сохранённой команды возвращает прежнюю квитанцию без сброса счётчика.
Готовый внешний итог принимается отдельным решением; несовпадающий запрос
или недоступная сверка запрещают продолжение. Оператор может окончательно
остановить доставку, сохранив бизнес-статус без вымышленного успеха.

Лимит D-NF03 равен пяти вызовам на серию; исходное ТЗ не задаёт число,
это решение проекта. Одновременно работают не более четырёх отправителей.
Чтение ленты и ручная сверка не расходуют лимит конкретной доставки.
При миграции старое число попыток переносится в счётчик серии без обнуления.
Очередь с числом пять и более останавливается до следующего сетевого вызова.
Поздний ответ старого захвата не меняет новое состояние. Позднее событие
ленты в NEEDS_REVIEW сохраняется как наблюдение для разбора, без применения
бизнес-результата; курсор продолжает двигаться.

Валидное событие ленты может подтвердить доставку раньше ответа на PUT.
Если подтверждение уже записано, поздняя ошибка или тайм-аут остаются в
истории и сохраняют `ACKNOWLEDGED`. Подтверждение закрывает открытую проблему
доставки `DELIVERY_UNCERTAIN` или `DELIVERY_DELAYED` системным событием с
причиной. До подтверждения доставки ошибка протокола переводит открытую
проблему доставки в `PROTOCOL_ERROR`, сохраняя её историю.

Чтение ленты работает независимо от состояния отдельных заданий. После пустого
ответа ждать 1 с.
При временной недоступности ждать 2, 5, затем 15 с до восстановления.
Этот интервал сбрасывается после успешного чтения и не расходует попытки
заданий. Для известной позиции некорректное событие или неизвестная операция
дают проблему с привязкой к курсору и обработка продолжается. При неверной
структуре страницы или позиции чтение останавливается на сохранённом курсоре
до исправления источника и перезапуска обработчика. Такая проблема видна
оператору как общая проблема ленты.

## Сверка и действия оператора

Оператор может сверить любое задание. Команда сохраняет локальный снимок,
ответ внешнего GET, автора и вывод. Каждый сохранённый снимок можно прочитать
по ID сверки из истории, включая снимок, на который ссылается решение.
Если обмен изменил локальное состояние во время
GET, команда возвращает `409 SNAPSHOT_STALE`. Внешняя недоступность даёт
сохранённый исход `UNAVAILABLE` без изменения результата. Ошибка схемы
дополнительно сохраняет проблему `PROTOCOL_ERROR` с безопасной диагностикой.
Сама сверка не приостанавливает очередь. Авторитетное
отсутствие операции совпадает с локальным неподтверждённым заданием без
результата. При наличии операции сравниваем подтверждение доставки, версию,
статус, содержание результата и неизменный запрос операции. Любое отличие, включая внешний итог,
которого ещё нет локально, даёт `DIFFERENCE` и сохраняет оба снимка. Штатное
событие ленты может принести следующий допустимый результат. Снимки сверки
и открытое расхождение остаются доступны оператору, а устаревшее решение
требует свежей сверки.

| Действие | Когда доступно и что меняет |
| --- | --- |
| Взять разбор | Открытая проблема по заданию, текущий оператор ещё не ответственный. Проверяет ожидаемую версию проблемы и ключ команды. В одной транзакции меняет ответственного, увеличивает версию и добавляет событие истории. |
| `RETRY` | Требует актуальную сверку: операция отсутствует снаружи либо имеет тот же запрос и незавершённое состояние. Команда оператора с причиной и версией проблемы сбрасывает только счётчик серии и назначает GET. Готовый итог принимается через APPLY_EXTERNAL_RESULT. ID, тело и сквозной номер попытки сохраняются. Replay не начинает вторую серию. |
| `RECONCILE` | Операторская команда для задания. При открытой проблеме карточка показывает последнюю связанную сверку. |
| `APPLY_EXTERNAL_RESULT` | Открытая проблема результата, расхождения или приостановленной доставки. Актуальная сверка обнаружила допустимый внешний снимок с тем же запросом и более новой версией. Сервер применяет его по общим правилам результата и записывает решение с причиной. |
| `ACKNOWLEDGE_DIFFERENCE` | Открытая проблема результата, расхождения или приостановленной доставки. Есть актуальная сверка с `DIFFERENCE` либо `MATCH`. Закрывает разбор с причиной, сохраняя бизнес-результат. Для `PROTOCOL_ERROR` или `DELIVERY_DELAYED` в `NEEDS_REVIEW` завершает отправку в `STOPPED`. |

Для решения проверяются ожидаемая версия проблемы, ID последней сверки и
версия локального обмена, записанная в снимке. Устаревшая версия даёт
`409 ISSUE_REVISION_CONFLICT` или `409 SNAPSHOT_STALE`, недопустимая команда
— `409 ACTION_NOT_ALLOWED`. Для общей проблемы ленты список действий пуст.
Команда повтора проверяет свободный захват очереди атомарно с изменением
расписания. Для любой новой команды проверяются ID последней сверки,
версия обмена и допустимость продолжения. Возобновление переводит
проблему в `DELIVERY_UNCERTAIN` и доставку в `UNKNOWN`. История сохраняет
причину и ссылку на сверку, диагностика остаётся доступной. Подтверждение
закрывает эту проблему обычным правилом доставки.
В `STOPPED` сетевые попытки завершены. Поздние события сохраняются в
истории как наблюдения, применение возможно только отдельным решением
по новой проблеме и свежей сверке.

Повтор успешной команды с прежним ключом и теми же значимыми полями
возвращает исходный ответ после проверки прав. Ключ привязан к пользователю
и виду команды. Идентификатор цели, ожидаемая версия и входные поля входят
в сравнение. Тот же ключ с отличием даёт `409 IDEMPOTENCY_CONFLICT`.
Проверка версии названия не зависит от получения результата исполнения.

Время в интерфейсе, API и фильтрах — UTC. Граница периода задаётся как
`[from, to)`. В модели нет дедлайна. URL-фильтры проверяют календарную дату и
диапазон лет 0001–9999; известное смещение нормализуется в UTC перед запросом.
Неизвестное `-00:00` и невозможные даты не отправляются. Сравнение границ
сохраняет точность до наносекунд; поля ввода редактируют UTC с точностью до минуты.
PostgreSQL хранит время создания с микросекундами. Адаптер чтения округляет
обе границы вверх до микросекунды: это сохраняет `[from, to)` для хранимых
моментов и не отдаёт решение округлению JDBC-драйвера.

## Экраны

| Экран | Действие и обратная связь |
| --- | --- |
| Вход | Логин и пароль. Неверные данные дают общее сообщение, потеря сессии возвращает на вход. |
| Реестр | Инициатор видит свои задания, оператор — общий список. Есть фильтры по состоянию исполнения и периоду. На узком экране строки становятся карточками. |
| Создание и карточка | Инициатор создаёт задание и редактирует своё название. Карточка отдельно показывает доставку и исполнение, время завершения и причину отказа. Конфликт версии предлагает обновить данные. |
| История | Видна в карточке при доступе к заданию. События упорядочены, автор и время различимы. |
| Проблемы и сверка | Оператор открывает проблему, видит ответственного, снимки и исход сверки. Доступные действия берутся из API. После передачи разбора новый ответственный виден в карточке. |

После команды изменения frontend запрашивает актуальную карточку и
затронутый список. Повтор с прежним ключом может вернуть сохранённый ответ
первого вызова. До обновления данных форма показывает выполнение операции.
При ошибке чтения интерфейс сохраняет введённые данные и предлагает повторить
обновление.

В списке разборов показываются название задания и номер заявки; общая проблема
ленты помечается отдельно. История показывает логин автора, а UUID остаётся
технической ссылкой. У событий протокола есть понятный заголовок и раскрываемое
исходное содержание без подмены сохранённых данных. После закрытия переименования
фокус возвращается на кнопку открытия формы.

На экранах видны состояния загрузки, пустого результата и ошибки. Поля имеют
подписи, а основной сценарий выполняется с клавиатуры на ширинах 390–1440 px.

## Демонстрация

Демо включает двух инициаторов и оператора. В минимальном наборе задания
двух владельцев покрывают ожидающую отправку, подтверждённую доставку, успех,
бизнес-отказ, неопределённый исход и открытую проблему.

Для воспроизводимого сбоя сначала выбираем свободный номер заявки `reference`
и задаём режим через `PUT /test/faults/{reference}` эмулятора. Затем создаём
задание с этим номером. Первый PUT доставки связывает режим с ID операции.
Режимы хранятся в БД эмулятора и доступны только в тестовом профиле и его
закрытой сети.

| Режим | Наблюдаемый эффект |
| --- | --- |
| `UNAVAILABLE` | PUT для выбранной заявки отвечает `503` до записи операции, пока режим не снят. GET фактического состояния возвращает `404`, если операции нет. |
| `DROP_RESPONSE_AFTER_EXECUTION` | Один раз фиксирует итог и счётчик, затем задерживает первый ответ PUT на 5 с. Клиент ждёт до 2 с. Независимый GET сразу показывает исполнение, повторный PUT подтверждает прежнюю запись. События операции удерживаются до снятия режима, включая перезапуск эмулятора. |
| `DUPLICATE_RESULT` | Публикует один итог дважды с разными курсорами и одинаковым содержимым. Счётчик исполнений остаётся равен одному. |
| `DELAY_RESULT` | Удерживает снимок `RUNNING` версии 1 до публикации итога версии 2. Запоздалый снимок получает больший курсор и не откатывает итог. |

`DELETE /test/faults/{reference}` снимает режим и выпускает удержанный итог
`DROP_RESPONSE_AFTER_EXECUTION` в ленту. Фактическое состояние и число
исполнений проверяются запросом `GET /operations/{operationId}` напрямую к
эмулятору. Контракт служебных запросов находится в [OpenAPI эмулятора](../contracts/external-exchange.openapi.yaml).

## Недоступность хранилища

Истечение ожидания соединения с БД или недоступность ресурса возвращает
503 SERVICE_UNAVAILABLE с общим сообщением без SQL и параметров подключения.
Это не 401/403: сессия и права не меняются. Клиент сохраняет форму и ключ
неизменённой команды для явного повтора. Если команда успела зафиксироваться,
квитанция возвращает прежний результат; отказ до начала транзакции не создаёт запись.
Ошибки прав и CSRF сохраняют свои ответы. В техническом журнале остаются
метод, путь и тип ошибки без содержимого запроса и секретов.
