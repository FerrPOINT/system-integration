# Роадмап

Этапы описывают последовательность поставки. Фактические результаты
фиксируются в [текущей стадии](current-stage.md).

| Этап | Зависит от | Критерий готовности |
| --- | --- | --- |
| [SI-00. База проекта](decomposition.md#si-00-база-проекта) | — | В чистой копии по README запускаются PostgreSQL и каркас, проходят HTTP smoke и TC-15. |
| [SI-01. Вход и реестр](decomposition.md#si-01-вход-и-реестр) | SI-00 | Три пользователя входят. Права на чтение, список, фильтры и карточка проверены по TC-08, TC-09 и TC-12 в объёме этапа. |
| [SI-02. Сохранение задания](decomposition.md#si-02-сохранение-задания) | SI-01 | Локальное принятие, повтор и конкурентное редактирование проверены по TC-01, TC-02 и TC-11. |
| [SI-03. Доставка и внешний результат](decomposition.md#si-03-доставка-и-внешний-результат) | SI-02 | Штатный результат сверяется с API эмулятора по TC-01. Серверные проверки TC-03–TC-06 подтверждают однократность после перезапуска и автоматическое продолжение после короткого и длительного простоя. |
| [SI-04. Разбор проблем](decomposition.md#si-04-разбор-проблем) | SI-03 | Проверены история, передача разбора, сверка, повтор и решение по TC-07–TC-09 и TC-14. |
| [SI-05. Приёмка и сдача](decomposition.md#si-05-приёмка-и-сдача) | SI-04 | Для одной версии выполнены TC-01–TC-16, включая чистый запуск, NF08 и публичную публикацию; собран комплект сдачи. |

Ориентир исходного ТЗ — одна рабочая неделя. Переход между этапами определяется
критериями приёмки.

Этапы SI-00–SI-05 описывают объём поставки. Для работы над задачами
используем цикл Base от Драфта и Бэклога через Анализ, Архитектуру,
Разработку, Ревью и Тестирование до Деплоя. На Ревью проверяем границы, права, контракты и
транзакции. На Тестировании сверяем [критерии ТЗ](requirements.md) с
[результатами сценариев](test-cases.md). При дефекте задача идёт на
Доработку и повторяет затронутые проверки.

[SI-07](decomposition.md#si-07-доработки-после-архитектурного-ревью) завершён на 343d873.

Результаты находятся в [статусе](current-stage.md).

## Итоговый аудит поставки

[SI-08](decomposition.md#si-08-итоговый-аудит-исходного-тз) связывает исходное

## Архитектура и оптимизация

[SI-09](decomposition.md#si-09-архитектура-и-оптимизация) завершён на db56b91; проверенные образы опубликованы.
Текущие подтверждения — в current-stage.md. Сначала SQL-профиль и модель, затем вертикальные срезы
задания, обмена/review и эмулятора с четырьмя слоями.
Рубеж A подтверждает сохранение поведения до изменения алгоритмов.
После него — пустая лента, replay, polling/gzip и измеренные оптимизации
публикации, отправителей и чтения страницы. Рубеж B объединяет серверные,
клиентские, UI/recovery/build и сравнимые нагрузочные проверки.

JDBC остаётся; DDD не требует замены на JPA. Размеры батчей выбираются по
замерам, новые SQL-таймауты и увеличение пулов исключены.
Локальный NF08, внешний генератор через закрытый канал и публичный HTTPS
проверяются раздельно. Поставка завершается сверкой исходного ТЗ,
документами и проверенным доменом; внешняя машина не нужна для начала работы.

## Эксплуатация и сдача

- Параметры и команды PostgreSQL находятся в README.
  При подключении БД проверяем отдельно запуск процесса и готовность
  приложения обслуживать запросы к БД после миграций. Недоступность
  эмулятора допускает локальное принятие задания по D01.
- README описывает запуск, остановку, миграции и загрузку демоданных.
  Обычная остановка сохраняет том. Для диагностики проверяем
  готовность БД, статус доставки, позицию ленты и журнал по ID задания,
  операции и попытки. При неверном курсоре после исправления источника
  возобновляем чтение с последней сохранённой позиции. Команды проверки
  эмулятора выполняем из тестовой сети. Секреты исключаем из журналов и отчётов.
- При сдаче передаём исходники frontend, backend и эмулятора, схемы,
  миграции, демоданные и инструкцию. Проверяющий воспроизводит
  [демо TC-10](test-cases.md#демо-и-проверка-эмулятора) из чистой копии.
  Возможности, ограничения и подтверждения для кандидата перечисляем в
  README и текущей стадии.

Результаты приёмки фиксируем для одной версии Git с окружением, командами
и ссылками на отчёты. В отчёте указываем отдельные результаты для исходников
и контрактов, API с БД и эмулятором, браузера, восстановления и нагрузки.
Каждой проверке присваиваем фактический статус «прошла», «не прошла»
или «не выполнялась». Текущий статус хранится в
[current-stage.md](current-stage.md), результаты прогона — в `tests/results/`.
