# Роадмап

## Текущая итерация: подготовка к приёмке

Обязательный объём задаёт [исходное ТЗ 2.1](original-specification.md).
Реализованные функции и критерии связаны в [матрице требований](requirements.md).
Фактический кандидат, результаты и публичная версия имеют одного владельца —
[current-stage.md](current-stage.md). Этот файл задаёт порядок завершения,
а не заменяет результаты проверок.

| Этап | Зависит от | Результат |
| --- | --- | --- |
| A1. Согласовать документы | Актуальный main после PR #18 | README, аналитика, архитектура, требования, тесты и эксплуатация описывают действующие правила; прежние результаты помечены своими версиями. |
| A2. Квалифицировать кандидат | A1, зафиксированный commit | Сборка/генерация, Java и PostgreSQL, frontend unit/component/UI/CSP, smoke, recovery, чистый запуск и демо на отдельном QA. |
| A3. Проверить NF08 | A2 | 5000 исходных записей, 20 клиентов, 30 с прогрева и 120 с измерения, бюджет исходного ТЗ, итоговая целостность и отдельное время внешнего исполнения. |
| A4. Проверить поставку | A2, A3 | Итоговое ревью, ссылки, версии схем и артефактов, известные ограничения и инструкция проверяющему. |
| A5. Обновить публичную демонстрацию | A4, поручение на публикацию | Только квалифицированные образы, сохранённые данные, порядок V11/V12, проверка фактических ассетов и TC-16 через HTTPS. |

При дефекте исправляется его владелец и повторяются затронутые проверки.
Тесты не направляются на публичные данные. QA используется одним владельцем;
обычный стенд и соседние приложения сохраняются. Исследовательский capacity,
перебалансировка ресурсов и новые архитектурные эксперименты не являются
предварительным условием выполнения исходного NF08.

автоматически прошёл полную квалификацию или опубликован на домене.

## Завершённые дополнительные этапы

Детальная декомпозиция сохраняет критерии этапов, а
[история](history.md) ведёт к неизменяемым результатам их кандидатов.

| Этап | Что входит в действующую реализацию |
| --- | --- |
| [SI-06](decomposition.md#si-06-настройки-производительности-и-актуализация-стека) | Virtual HTTP threads, отдельные fixedDelay-триггеры, ограниченные пулы, HTTP deadline, закреплённые SDK. |
| [SI-07](decomposition.md#si-07-доработки-после-архитектурного-ревью) | Политика повторов и пакетное обогащение списка проблем без N+1. |
| [SI-08](decomposition.md#si-08-итоговый-аудит-исходного-тз) | Матрица ТЗ, негативные сценарии, целостность и границы приёмки. |
| [SI-09](decomposition.md#si-09-архитектура-и-оптимизация) | Явные слои, SQL-планы, ограниченные батчи, независимая доставка, gzip ассетов. |
| [SI-10](decomposition.md#si-10-конечный-лимит-автоматических-попыток) | Пять вызовов на серию, постоянный счётчик, остановка и управляемое продолжение. |
| [R01–R09](decomposition.md#структура-проекта-r01r09) | Независимые build targets, общий init БД, структура тестов и навигация. |
| [Spring-слои](decomposition.md#переход-на-spring-слои) | Controller/service/repository/domain/mapper и архитектурные ограничения. |
| [Spring Data JDBC](decomposition.md#чтение-через-spring-data-jdbc) | Обычные чтения через узкие репозитории, явный JDBC для команд/очереди. |
| PR #16–#18 | Типизация runner, очистка неиспользуемых путей, V11/V12, сессии и восстановление UI. |

Публичные проверки прежних этапов относятся только к их образам.
Они не означают публикацию последующего main. Текущая граница всегда указана
в [статусе](current-stage.md).

Пароли передаются отдельно от Git и отчётов; названия трёх демонстрационных
пользователей и способ задания пароля находятся в README.
Приёмка использует одну зафиксированную версию. Проверяющий проходит
[демо TC-10](test-cases.md#демо-и-проверка-эмулятора), сверяет результат через
эмулятор и проверяет разделение прав. Нагрузочная проверка запускается
отдельно от демонстрации и искусственных сбоев.
