## Архитектура после исправлений

Сохраняется один прикладной backend и отдельный обязательный эмулятор.
Frontend обращается к generated OpenAPI-клиенту; controller/MapStruct
преобразуют HTTP, service владеет сценарием и транзакцией, domain —
инвариантами, repository — хранением, client/http — внешним протоколом.

Чтения заданий используют Spring Data JDBC. HistoryRows содержит явный
bounded JOIN для автора, с Javadoc и SQL-планами. Команды, outbox, lease,
конкурентные изменения и публикация сохраняют явный JDBC SQL. Это одна БД
и один transaction manager, без JPA, второго пути чтения или отдельного
кэша. Исключение архитектурного теста касается только mapping-интерфейсов
метаданных Spring Data @Query; отрицательная fixture по-прежнему запрещает
JdbcTemplate в read-адаптере.

Создание, outbox, история и квитанция атомарны. HTTP выполняется между
короткими транзакциями. Применение ленты и её курсор фиксируются вместе.
Порядок блокировок сохранён. Пять автоматических вызовов серии, постоянный
счётчик и свежая операторская сверка обеспечивают управляемый повтор.

IssueView — только read-проекция: доменная Issue, сохранённые квитанции,
fingerprints и схема БД не менялись. Проверка строки команды имеет одного
владельца TaskTitle. Новых процессов, брокеров, кэшей, ORM и CI нет.

## Нагрузка: API и фактическое исполнение

На конечном кандидате: 5000 завершённых исходных записей, 20 параллельных
клиентов, 30 с прогрева и 120 с измерения. Общий лимит четырёх контейнеров
backend/PostgreSQL/emulator/frontend — 2 CPU / 4 ГиБ. Node-генератор работал
на том же Firebat1 вне этих лимитов; Windows отправлял SSH-команду запуска.
Запросы шли прямо на loopback API. Это не тест публичной сети и не
изолированная оценка пропускной способности всего физического хоста.

| Метрика | Результат |
| --- | --- |
| HTTP | 56 228 запросов, ошибок 0; чтение p95 98,23 мс, изменение p95 96,72 мс. |
| Смесь измерения | Список 14 058, карточка 14 054, создание 14 058, переименование 14 058. |
| Идемпотентность | 20 конкурентных одинаковых запросов создали одну запись; replay вернул её, другой допустимый payload получил конфликт. |
| Конечная целостность | 21 494 записи в обеих БД; все 16 494 новые операции завершены, наборы ID/заявок/результатов совпали. |
| Очередь и повторы | Queue/pending/open issues/unpublished = 0, повторных исполнений 0; два запоздавших ответа корректно проигнорированы. |
| Внешнее исполнение | p95 всех новых операций 125,912 с, отдельно от HTTP p95. |
| Ожидание drain | 50,477 с — длительность отдельного этапа ожидания очереди. |
| От конца HTTP-окна до подтверждения пустой очереди | 109,024 с, включая первую сверку и replay перед drain. |

Первая последовательная сверка после измерения проверила 14 058 созданий:
4477 уже завершены, 9581 (68,15%) ещё ожидали. Она сама заняла 54,62 с;
это не атомарный снимок очереди в момент окончания HTTP-окна.
Затем выполнялись replay и ожидание drain, после них — конечная сверка.

HTTP принимает задания быстрее, чем весь асинхронный конвейер их завершает.
В этом профиле очередь росла, затем опустела. p95 ожидания до первой
попытки — 125,30 с, внутреннего исполнения эмулятора — 9,32 с, применения
результата — 1,08 с. Эти p95 относятся к разным распределениям и не
складываются. Замер не доказывает SLA непрерывного потока с такой скоростью
созданий и не задаёт срок внешнего исполнения по задержке API. Приёмочный NF08 API
пройден; подбор устойчивого потока требует отдельного capacity-профиля.

## Безопасность и границы вывода

[OSV API](https://google.github.io/osv.dev/api/) проверил 70 фактических
Maven-модулей из runtime JAR обоих приложений: совпадений нет.
JAR сопоставлены с разрешёнными зависимостями по байтам; embedded jarmode
дополнительно проверен по POM/SHA-256 Maven Central. Пустые Boot starters
не считаются runtime JAR. Проверка npm production advisories: совпадений нет.

OS scan: frontend/PostgreSQL — известных совпадений нет; каждый Java-образ —
30 Medium и 4 Low, без vendor fix; High/Critical и fixable — 0.
Это не полный пентест и не независимый аудит всех native-бинарников JRE.
Наличие advisory без исправления поставщика отражено как остаточный риск.

доступны в диагностике. Некорректная структура всей внешней ленты требует
исправления источника и перезапуска backend по README. Смена этой
документированной модели эксплуатации не добавлялась как новая функция.
