c83b4ca03149e6c4da1fe7b9932a89a60ea4435f после PR #19.

## Заключение

Новых подтверждённых блокирующих дефектов D01–D07, NF01–NF10 и D-NF01–D-NF03
в проверенных сценариях не найдено. Система соответствует объёму тестового
задания и имеет квалификацию точного работающего кандидата.
Это не утверждение об отсутствии любых дефектов или промышленной готовности
для произвольной нагрузки и нескольких реплик.

Широкая смена архитектуры, ORM, брокера, кэша или партиционирования не обоснована.
На снимке аудита оставались два небольших замечания и долг базового образа.

## Замечания

### G01 · P3 · Лишняя утилита с advisory в Java runtime

[PR #24](https://github.com/FerrPOINT/system-integration/pull/24) удалил
`pebble` из файловой системы новых контейнеров. Исходный бинарник остаётся
в базовом слое OCI, а приведённый ниже скан относится к исходному кандидату.

[Dockerfile, строка 22](../Dockerfile#L22) использует JRE-образ, содержащий
/usr/bin/pebble, около 10,6 МБ. Trivy обнаруживает в ней Go stdlib v1.27.3
с CVE-2026-97054, severity UNKNOWN; исправленные ветки в отчёте —
1.26.11 и 1.27.4. Это не уязвимость Spring или JAR приложения.

По [первичному advisory Go](https://pkg.go.dev/vuln/GO-2026-6859),
проблема относится к определённому конкурентному использованию HTTP/1
MaxBytesReader/MaxBytesHandler. В контейнере запущен только процесс Java,
ENTRYPOINT переопределён, обращений проекта к pebble нет. Достижимость
проблемного пути через API System Integration не подтверждена.
Наличие пакета не выдаётся за доказанный удалённый exploit.

Минимальная последующая правка: удалить неиспользуемую утилиту из финальной
стадии после проверки потребителей базового образа либо выбрать исправленный
эквивалентный digest. Не менять Java/Spring ради Go-утилиты.
Проверка: отсутствие файла/advisory, те же JAR, запуск обоих приложений,
healthcheck и повторный image scan. В этом аудите образ не менялся.

### G02 · P3 · Неиспользуемый FormField.error

[PR #24](https://github.com/FerrPOINT/system-integration/pull/24) удалил
`error` из FormField. На [снимке аудита](https://github.com/FerrPOINT/system-integration/blob/c83b4ca03149e6c4da1fe7b9932a89a60ea4435f/frontend/src/shared/ui/form-field.tsx#L10)
компонент сохранял error props, aria-invalid и Notice-ветку без потребителя.
У 12 JSX-вызовов FormField нет error и нет spread props, скрывающих его передачу.
Ветка не нужна текущим формам; required-ошибка Select имеет отдельного
действующего владельца.

Минимальная правка: убрать error и связанную ветку/импорт, сохранив
label/id/required/hint и связь подсказки с контролом. Проверить типы и формы.
Новая система полевой валидации для удаления этого остатка не нужна.

### Базовый образ: известный security-долг

В каждом Java-образе OS-скан выявил 30 MEDIUM и 4 LOW, без доступной
FixedVersion в обновлённой базе Trivy. Это не 68 уникальных advisory:
образы имеют общие OS-слои. HIGH/CRITICAL нет.
Удаление этих находок или их эксплуатационная неприменимость не доказаны.
Менять дистрибутив и стек ради нулевой суммы сканера без оценки последствий
не предлагается; нужны сопровождение исправлений vendor и повторная проверка.

## Архитектура и Spring Boot

| Область | Проверенный вывод |
| --- | --- |
| Состав | Один backend, отдельный эмулятор, один PostgreSQL с разными БД/ролями. Отдельных брокера, Redis и синхронизируемой read-БД нет. |
| Слои | Controller принимает generated API и делегирует service; service владеет сценарием/правами/транзакцией; JDBC/Spring Data и HTTP находятся в адаптерах. Domain не зависит от Spring, JSON и persistence. |
| Репозитории | Spring Data JDBC обслуживает обычные чтения. Явный JDBC оправдан для команд, leases, квитанций, конфликтов, batch и сложных проекций. Оба используют один DataSource и транзакционный менеджер. |
| Lombok/MapStruct | Lombok — простой DI/log; явные конструкторы проверяют настройки и lifecycle. MapStruct — HTTP DTO с ошибкой при непокрытом поле. Ручной ResultSet parsing не дублирует HTTP mapping. |
| Бины и lifecycle | Общий Spring-managed HttpClient, проверяемые settings, закрываемый executor, отдельные fixedDelay-триггеры; нет клиента на каждый запрос. |
| Минимальность | Нет интерфейса для каждого service, универсальной шины/саги или двух текущих реализаций контракта. Бounded helpers имеют реальные обязанности. |
| Генерация | OpenAPI, MapStruct и Lombok генерируют в build; outputs не коммитятся. |

Штатный механизм предпочтительнее новой обёртки. Архитектурные тесты
проверяют направления зависимостей и негативные fixtures.
Размер useCollection сам по себе не признан дефектом: он обслуживает
bounded mobile window, Back/GC, ошибки и восстановление позиции с реальными тестами.

## Данные, конкуренция и обмен

- Создание задания, outbox, история и квитанция выполняются в одной транзакции.
  Команда распознаётся по actor/type/key и отпечатку значимых полей.
- Advisory lock сериализует и первый запрос. Replay не повторяет эффекты,
  несовпадающее тело отклоняется. Для переименования проверяются доступ и revision.
- Сеть находится между транзакциями claim/finish. Задержанный ответ не владеет
  чужим или истёкшим claim. Task→queue/issue — согласованный порядок блокировок.
- Подтверждение получения не подменяет исполнение. Operation ID неизменяем,
  запрос проверяется в подтверждении/снимке/событии. Дубликат не создаёт эффект,
  запоздалый результат не откатывает новый.
- Пять автоматических вызовов на серию сохраняются в БД; исчерпание переводит
  доставку в разбор, а не в бесконечный цикл. Оператор продолжает после свежей сверки.
- Применение страницы результатов и cursor атомарно. Эмулятор фиксирует
  результат/события вместе, назначает курсоры в порядке commit.
- Сверка сохраняет оба снимка; операторская команда проверяет версии проблемы
  и локального обмена. Ошибка/расхождение не затираются скрыто.
- Миграции V1–V12 сохранены; V12 несовместима со старым writer http_status.
  Публикация использует квалифицированные образы и совместимый recovery-набор.

## Безопасность и API

Проверены security rules, текущий actor, область owner, операторские методы,
CSRF, idempotency, валидация и контракт ошибок. Прикладные права действуют
на сервере и в предикатах чтения; UI не является security boundary.

HTTP-сессия — Spring Security, пароль хранится как BCrypt hash.
CSRF имеет владельца, frontend-команда привязана к поколению сессии,
login/logout сериализуются Web Locks между вкладками.
После смены identity приватный Query cache очищается.
Прямые чужие ID не расширяют доступ. Эмулятор и БД опубликованы только на loopback;
служебный Actuator не проксируется frontend.

В просмотренных tracked-файлах нет реальных env, private keys или совпадений
проверенных шаблонов токенов. Это поиск известных форматов, а не доказательство
отсутствия секрета любой формы и не скан всей истории Git.
CSP nonce, no-store приватного API и HTML, hashed assets и gzip имеют
согласованные владельцы. SQL использует параметры; динамические фрагменты
собираются из внутренних условий/placeholder, а не ввода пользователя.

## Интерфейс

Реестр, создание, карточка, история, проблемы и сверка используют API.
Допустимые операторские действия определяются сервером.
Фильтры принадлежат URL и применяются без дополнительной кнопки.
Query хранит DTO, форма — черновик; refresh после принятой команды повторяет GET.
Неопределённый исход сохраняет исходный ключ и предупреждение при выходе.
Тема по умолчанию тёмная, выбор сохраняется; мобильные списки — карточки.
Mobile cache/DOM ограничены пятью страницами/100 записями.
Состояния загрузки, ошибки, пустого результата и клавиатура покрыты
предыдущей полной квалификацией этого же прикладного кода.

Новый ручной браузерный прогон и визуальные скриншоты в этом аудите не выполнялись.
Свежий runtime readback — HTTP/артефакты и TC-16, а не повтор всех UI-сценариев.

## Производительность: что доказано и что нет

Предыдущая полная квалификация d747511 на Firebat1:
53 804 запросов без ошибок, read/write p95 97,79/98,35 мс,
20 клиентов, 5000 исходных записей, 30 с прогрева + 120 с измерения,
2 CPU / 4 ГиБ для четырёх контейнеров. Все 20 691 итоговые записи сверены.

При этом ожидание первой отправки p95 — 74,95 с. После окна очередь обработана.
Это предел интенсивного сценария доставки, а не нарушение числового SLA API
из NF08. Нет оснований обещать такую скорость бесконечного исполнения.
Точный COUNT остаётся линейным; общий короткий SQL timeout не введён намеренно.
EXPLAIN не заменяет анализ конкурентных ожиданий.

В этом аудите нагрузка и EXPLAIN заново не запускались:
прикладные входы не изменились с квалификации. Сохранённые 1626 планов,
recovery и NF08 проверены как evidence того кандидата.
[Исследование вариантов](performance-options.md#12-приоритеты-после-обсуждения-допустимого-отставания-ui)
опубликовано как исследование, без включения серверного кеша, изменения total
или ресурсного баланса. Эти решения не считаются внедрёнными.
