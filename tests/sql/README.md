# SQL-планы

Из корня проекта на Firebat1:

~~~sh
python3 tests/sql/plans.py
~~~

Скрипт использует Python standard library, Docker CLI и psql действующего
контейнера system-integration-load-postgres-1. Не запускайте его параллельно с
интеграционными тестами, recovery или нагрузкой.

Проверяет JDBC-вызовы исходников приложения/эмулятора и явно заданные варианты
SQL. Вызов идентифицируется классом, методом/числом аргументов и номером
внутри метода; перемещение других методов не сдвигает его параметры.
При добавлении вызова без соответствующего случая проверка падает.
Перегрузки одинаковой арности и неподдержанные формы Java не угадываются:
инструмент требует явного уточнения. Сканер проверяется через
python3 -m unittest discover -s tests/sql -p '*_test.py'.
Параметры и данные синтетические; это проверка планов, не замена API-тестам.

Доступ к изменению ограничен si_test/si_emulator_test: обе БД должны быть пустыми
и не иметь подключений. Не выполняется reset. Fixtures создаются внутри BEGIN,
каждая проба — под SAVEPOINT, в конце ROLLBACK; psql ON_ERROR_STOP и закрытие
соединения откатывают данные при ошибке. Остаток проверяется после прогона.
Обычные si_app/si_emulator никогда не являются целью SQL этого инструмента.
Проверка подключений — защита от ошибки запуска, не распределённая блокировка:
единый владелец тестовой среды обязателен.

Набор: 10 000 заданий с распределением владельцев 90/10, 5 000 очередей,
21 000 событий истории, 1 000 проблем/сверок; у эмулятора 10 000 операций
и 20 000 событий. Дополнительный временной набор содержит 5 000 старых
SUCCEEDED и 15 000 новых PENDING: сравниваются параметр и enum-литерал статуса
на одной физической выборке с существующим индексом V6. Это сравнительные
пробы, а не новый SQL приложения; новые индексы не создаются.
Набор нужен для планов отдельных запросов, не представляет
согласованную функциональную модель обмена. EXPLAIN ANALYZE/BUFFERS/WAL
проверяет inline, prepared custom и generic планы, включая узкие/пустые окна,
редкого/отсутствующего владельца и глубокую историю.
Типы prepared-параметров выводит PostgreSQL; арифметические выражения
могут отличаться от точных типов JDBC binding.

Результаты — в игнорируемом tests/results/sql-plans/report.json и сырых
psql-ответах. Для baseline SI-09 до рефакторинга сохранён отдельный receipt
tests/results/sql-baseline/report.json. Одиночный замер — не p95; он не
объясняет конкурентное ожидание и не доказывает причину насыщения CPU.
Под нагрузкой отдельно нужны частота SQL и время транзакций/блокировок.

## Профиль JDBC по сценарию

С загруженным окружением тестовой БД и GRADLE_USER_HOME, из корня репозитория:

~~~sh
sh ./gradlew --no-daemon --max-workers=2 :backend:integrationTest --tests '*SqlWorkflowProfileTest'
~~~

Профиль проходит настоящий API/транзакции PostgreSQL и прикладные обработчики:
создание/повтор, переименование/повтор, чтение, claim/ack, два результата и
история. Тестовый Spring AOP перехватывает внешние вызовы JdbcTemplate,
включая JDBC и mapping, без значений параметров. Сохраняет общее число/время
по SQL и число вызовов по шагу в tests/results/sql-workflow.json.
Время не является серверным SQL-таймером или нагрузочным p95.
Это test-only наблюдение, производственный код не инструментируется.
SI-09 дополнительно проверяет одно чтение заблокированного задания при claim
и одно чтение состояний на страницу из 100 событий. Это проверки отсутствия
N+1, не лимит числа запросов в рабочем API. Состояния страницы загружаются
под блокировками в порядке task id и живут только в транзакции применения;
после каждого результата локальное состояние обновляется. Порядок событий,
история и атомарный курсор сохраняются. Общая нагрузка должна подтвердить,
что более ранний захват строк страницы не ухудшил конкуренцию.

## Профиль пакетной публикации

С окружением тестовых БД и GRADLE_USER_HOME, из корня репозитория:

~~~sh
sh ./gradlew --no-daemon --max-workers=2 :emulator:backend:integrationTest --tests '*PublisherProfileTest'
~~~

Настоящий Spring proxy и PostgreSQL публикуют один и тот же набор из 2 000
событий. Размеры 1/10/25/50 проверяются в трёх порядках; измеряются число
транзакций, общее время и p95 транзакции. Проверяются уникальность и непрерывность
курсоров. Fixtures только si_emulator_test, очищаются перед и в finally.
Результат tests/results/publisher-profile.json. JVM работает вне контейнерного
лимита: это адресное сравнение алгоритма, не NF08 или ёмкость системы.
EXPLAIN batchUpdate проверяет отдельный SQL с представительным bind;
сетевой пакет и транзакцию целиком проверяют этот профиль и нагрузка.

Публикация по умолчанию использует 25 событий в транзакции
(si.emulator.publication-batch-size, SI_EMULATOR_PUBLICATION_BATCH_SIZE, диапазон 1–100).
Сначала фиксируется набор подходящих событий, затем строки блокируются
в общем со снятием сбоя порядке operation_id/version/copy_number.
Присвоение курсоров и счётчик атомарны; вновь подходящий поздний RUNNING
попадает в следующую транзакцию. Лимит цикла остаётся 100 событий.
Размер 50 быстрее в адресном профиле, но удерживает вдвое больше строк:
default 25 выбран для последующей общей проверки, а не как универсальный оптимум.

## Проверка наблюдателя блокировок

Из корня с проектным Node:

~~~sh
node --test tests/sql/metrics.test.mjs
~~~

При свободных тестовых БД тест удерживает строку incoming_position в si_test,
создаёт второе ожидающее чтение FOR UPDATE и проверяет, что наблюдатель видит
реальные блокирующие PID, SQL и тип Lock.
Наблюдатель сохраняет запросы активных/ожидающих сессий только выделенных
si_test/si_emulator_test с синтетическими данными. Это выборка активности,
не число исполнений SQL и не рейтинг суммарной стоимости.
Текст ограничен серверным track_activity_query_size; обычные БД не включены.
[Семантика pg_stat_activity](https://www.postgresql.org/docs/18/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY). Обе транзакции откатываются.
Приложения не перезапускаются; обычные данные не меняются.
Отчёт — tests/results/metrics-lock-observation.json.
Это проверка инструмента, не доказательство причины задержек обмена.
