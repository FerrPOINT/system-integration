# Проверки сервиса

## Порядок приёмки одного кандидата

Зафиксируйте Git commit, отдельные QA-пароли и единого владельца стенда.
Не используйте пароль публичной демонстрации. Кандидат, точное дерево источников и фактические результаты
записываются в [текущую стадию](../docs/current-stage.md).
Для проверки уже опубликованной версии используйте кандидата, указанного там
в строке публичного демо.

1. Выполните сборку/генерацию, Java check/bootJar, frontend build/unit/assets,
   TypeScript runner и unit тестовых инструментов по корневому README.
2. Поднимите только PostgreSQL отдельного load-проекта и выполните оба
   integrationTest. После них остановленные backend/emulator остаются остановленными.
3. Очистите только собственные QA-данные штатным reset, выполните
   [SQL-проверки](sql/README.md) на пустых si_test/si_emulator_test.
4. Соберите три образа последовательно с revision кандидата. Поднимите QA,
   сверьте revision, JAR и обслуживаемые frontend-ассеты с проверенной сборкой.
5. Выполните component, production Nginx/CSP, HTTP smoke и
   [полный e2e двух размеров экрана](#автоматический-браузерный-сценарий).
   Для полного e2e сначала загрузите showcase в этот же QA. Затем отдельно
   выполните recovery и шесть демосценариев.
6. После сброса только собственных fixtures выполните [NF08](load/README.md#запуск).
   Не смешивайте в его окне сбои, recovery, UI и SQL-измерения.
7. Проверьте целостность, сохранность обычного стенда и итоговый diff.
   Удалите созданные QA-контейнеры/сеть/том; сохраните компактные результаты.

Публичный TC-16 выполняется отдельно после разрешённой публикации.
Он не заменяет нагрузку, браузерный сценарий или проверку артефакта.

| Где | Что проверяем |
| --- | --- |
| `tests/e2e/` | HTTP smoke, браузерные сценарии обеих ролей и аварийные перезапуски процессов. |
| [tests/sql/](sql/README.md) | Реестр JDBC и EXPLAIN на откатываемых тестовых fixtures. |
| `tests/load/` | Генерация 5 000 записей и [профиль NF08](load/README.md). |
| backend/src/test/, emulator/src/test/ | Контракты, предметные правила, архитектура, HTTP-доступ и PostgreSQL. integrationTest использует si_test/si_emulator_test. |
| `frontend/tests/` | Unit клиента, URL/polling, projections/positions, lint guardrails; component fixtures и round-trip production JS/CSS. |

Сценарии и ожидаемые результаты связаны с требованиями в
[плане приёмки](../docs/test-cases.md).

## Проверка TypeScript

Из корня: corepack pnpm --dir tests typecheck. Проверяются конфигурации, support
и все TypeScript-сценарии runner с Node/DOM types. Команды test:e2e,
test:components и test:production выполняют эту проверку перед Playwright.
Для test:components дополнительно выполняется frontend typecheck: браузерные
fixtures входят в frontend/tsconfig.json, но не в production bundle.
JavaScript load/recovery scripts остаются вне строгой проверки TypeScript.

## Демосценарии на QA

`tests/demo.mjs` по умолчанию обращается к локальному load-проекту на 19680/19681.
Команда scenarios проверяет принадлежность контейнеров и БД перед записью:

```sh
node --input-type=module -e "import {loadEnvironment} from './tests/load/environment.mjs'; loadEnvironment();"
SI_BACKEND_URL=http://127.0.0.1:19680 SI_EMULATOR_URL=http://127.0.0.1:19681 node --env-file=.env tests/demo.mjs scenarios
```

Проверьте origin/external, новые ID и observedStates в `tests/results/demo.json`.
Каждый вызов scenarios создаёт шесть новых операций и проверяет свежий обмен.

Большой исторический набор и его проверка принадлежат [seed/](../seed/README.md).
Команды `node --env-file=.env tests/demo.mjs seed` и `verify-seed` используют
по умолчанию локальный load-проект на 196xx. Явный `SI_SEED_TARGET=demo`
переключает только большой набор и его проверку на обычную демонстрацию;
живые сценарии и автотесты остаются изолированными. `corepack pnpm --dir tests test:seed`
проверяет детерминированность, распределение, связи и допустимые результаты
каталога без записи в БД.
## Production frontend без API/БД

После `frontend: pnpm build` из `tests/` выполните
`corepack pnpm test:production`.
Runner поднимает временный контейнер на 127.0.0.1:19778 из Nginx image,
закреплённого в frontend/Dockerfile, с настоящим nginx.conf и read-only dist.
Он использует отдельную временную сеть; API перехватывается тестами, доступа
к Compose/БД нет. Container/network удаляются в global teardown.

Проверяются переходы из открытой вкладки после смены ассетов, nonce CSP
и условный HTTP-запрос, Dialog/Select/вложенный discard,
видимость точных границ периода и desktop scroll cold/warm/POP после Query GC.
Эта проверка не заменяет сквозные сценарии отдельного test Compose.

## HTTP smoke

Запустите отдельный тестовый Compose по [инструкции](load/README.md#запуск).
После готовности сервисов запустите тесты из корня репозитория.

```sh
node --test tests/e2e/smoke.test.mjs
```

По умолчанию тест проверяет backend на `http://127.0.0.1:19680` и frontend
на `http://127.0.0.1:19673`. Для другого тестового стенда задайте
`SI_BACKEND_URL` и `SI_FRONTEND_URL`. HTTP smoke проверяет доступность
API, выдачу собранного JavaScript и проксирование защищённого API через frontend.
Дополнительно проверяет сырые gzip/identity-ответы JS/CSS, Vary, запрет gzip;q=0,
совпадение распакованных байтов и отсутствие изменения private API.

Пишите локальные отчёты в `tests/results/`. Снимки, логи и результаты нагрузки
в этом каталоге игнорируются Git.

## Автоматический браузерный сценарий

Поднимите отдельный Compose-проект system-integration-load с
compose.load.yml по [инструкции запуска](load/README.md#запуск) до шагов
reset и подготовки 5 000 записей. Загрузите QA-пароли из .env в окружение
по [корневому README](../README.md#сборка-и-проверки). Из корня проекта:

~~~sh
corepack pnpm --dir frontend install --frozen-lockfile
corepack pnpm --dir frontend generate:api
corepack pnpm --dir tests install --frozen-lockfile
corepack pnpm --dir tests exec playwright install chromium
SI_SEED_TARGET=load node --env-file=.env tests/demo.mjs seed
corepack pnpm --dir tests test:e2e
~~~

Генерация OpenAPI создаёт типы в этом checkout для TypeScript-проверки
runner. Загрузка сида создаёт tests/results/showcase/load/showcase.json и данные для трёх
showcase-сценариев на двух ширинах. Для приёмки используйте свежую QA-базу:
повторная загрузка сохраняет уже внесённые изменения, а сценарии проверяют
исходное состояние примеров.

Для UI поверх native Vite на 19673 явно задайте
`SI_UI_FRONTEND_RUNTIME=vite`. Проверка окружения продолжает требовать backend,
эмулятор и PostgreSQL из изолированного Docker-проекта и сверяет их БД/порты.
Без этой настройки требуется и frontend-контейнер. Load/recovery используют
полный Compose; native Vite не заменяет их проверку контейнеров или бюджета.
Полные тяжёлые прогоны соблюдают общий host execution slot из инструкций workspace.

Runner использует `http://127.0.0.1:19673`, экраны 390 и 1440 px,
учётки `initiator.one`, `initiator.two` и `operator`. `SI_FRONTEND_URL` переопределяет
адрес тестового стенда. Тесты создают собственные задания с префиксом E2E.
Не направляйте их на окружение с реальными данными. Краткий отчёт выводится
в терминал; снимки ошибочных сценариев — в `tests/results/playwright/`.
Трассы и HTML-отчёт по умолчанию отключены: они сохраняют введённые значения
и сессионные данные. Для изолированного стенда используйте отдельный тестовый
SI_DEMO_PASSWORD, отличный от публичной демонстрации. Сбор списка тестов не подтверждает прохождение
пользовательского сценария.

themes.spec.ts проверяет три палитры, тёмную по умолчанию, контраст текста,
сохранение выбора, синхронизацию вкладок, сохранение черновика формы,
мобильные фильтры, общий логотип, поля с подсказками и карточки, оформление меню и отступ стрелки, клавиатуру и явное сообщение при недоступном или неверном сохранённом выборе.
spacing.spec.ts дополнительно измеряет интервалы при удержанном HTTP-ответе, ошибке, пустом и заполненном реестре, в карточках, форме, истории и сверке.
Основной прогон выполняется в двух профилях экрана. Component specs
находятся в `components/`, прикладные — в `e2e/`: runner разделены каталогами.
Component discovery проверяет Select, отложенное измерение,
идентичность/guard форм, исходы команд и follow-up GET, operator draft basis,
восстановление маршрута после ошибки отрисовки и mobile window. Они используют production components/Query
под StrictMode и перехватывают все API-запросы. Проверяются тёплый/холодный кэш,
равные revisions, history jump, refetch без потери draft, native reload, focus
и отсутствие повторной записи после receipt. `mobile/collection-window.spec.ts`
проверяет cache/DOM/refetch/polling на 20/100/1000/5000, полный проход 5000 записей,
оба направления, Back после GC, изменение данных и видимые ошибки восстановления.
Этот профиль ограничен mobile project; остальные checks выполняются в двух.
Discovery не является результатом прогона; свежие результаты см. в текущей стадии.
UI-17 проверяет мобильное окно фильтров, короткий экран, сохранение условий
и возврат фокуса; на desktop — раскрытие и пересчёт вместимости списка.
UI-18 проверяет клики по краям ячеек разных строк в обоих реестрах,
Ctrl-клик, среднюю кнопку мыши и Enter; заголовок таблицы не открывает запись.
UI-13 проверяет число запросов NEEDS_REVIEW/STOPPED по управляемым часам;
UI-14 — реальную запись сверки оператором и обновление истории уже завершённого
задания в открытой вкладке инициатора. Состояние фактических прогонов — в
[текущей стадии](../docs/current-stage.md).
Основной сценарий реестра дополнительно проходит ширины
390/480/481/759/760/761/767/768/1024/1150/1151/1440 px:
карточки до 760 px включительно, затем таблица без внутреннего горизонтального скролла.

HttpErrorRoutingTest проверяет настоящий HTTP-сервер: 404/405/500 сохраняют
свой смысл, 500 не раскрывает SQL и откатывает task/queue/history/receipt;
повтор с тем же ключом после восстановления создаёт одну запись.
Прямой /error закрыт, 401/403 для сессии и роли сохраняются.
Серверные тесты также проверяют все допустимые варианты внешнего результата,
равные UTC-метки, запрет всех операторских маршрутов для обоих инициаторов,
конкурентную передачу разбора и повтор сверки одним/разными авторами.

Автоматическое обновление истории проверяется с временной недоступностью
эмулятора для ID созданной операции. Режим снимается в `finally`.

Операторские сценарии управляют сбоями через `SI_EMULATOR_URL`
(по умолчанию `http://127.0.0.1:19681`). Фикстура `held-delivery` на
выделенном QA временно откладывает первую отправку новых задач, созданных
обычным API. Перед снятием удержания тест настраивает сбой для конкретного ID.
Проверяются независимый счётчик исполнения, сохранённая сверка и явная
остановка при несовпадении количества.

## Перезапуски и границы коммита

На выделенных тестовых БД с Compose-файлами compose.yml, compose.public.yml
и compose.load.yml, с загруженным `.env`, из корня:

```sh
node tests/e2e/recovery.mjs
```

Runner проверяет подключение к si_test/si_emulator_test и перезапускает только
API, PostgreSQL и эмулятор этого проекта. Обычные БД стенда не используются.
Не запускайте другие тесты на этом стенде одновременно.
Recovery отправляет Connection: close: при намеренном убийстве/пересоздании
процессов клиент не сохраняет старые TCP-соединения. NF08/capacity используют
обычный keep-alive. Все Compose-вызовы recovery, включая отключение worker,
сохраняют один список файлов с compose.load.yml; после override БД перепроверяются. Контрольные точки
используют блокировки строк PostgreSQL: после сохранения захвата, до
применения ленты и до назначения курсора эмулятором. Для проверки принятой,
но ещё не исполненной операции временно отключается существующий worker
эмулятора. В конце восстанавливается обычная конфигурация.

Проверяются сохранение курсора, история, неизменный результат и одно
исполнение. Седьмой этап останавливает Java-процессы с восемью сохранёнными
ожидающими заданиями, проверяет завершение HTTP и закрытие пула БД, отсутствие OOM/SIGKILL и однократное исполнение после старта. Пересоздание backend с другим IP проверяет обновление адреса
во frontend без перезапуска Nginx. Временный контейнер занимает прежний IP
только на время проверки и удаляется в `finally`. Сбои адресуются к созданным проверкой ID операций.
Восьмой этап удерживает тестовую таблицу, исчерпывает пул параллельными HTTP-чтениями,
проверяет 503 SERVICE_UNAVAILABLE вместо ошибки прав и восстановление той же сессии
после освобождения блокировки. Подключения и блокировки освобождаются в finally.
Отчёт находится в `tests/results/recovery.json`. Это проверка рабочего
процесса и БД; она не подменяет браузерный сценарий.

## Публичная публикация TC-16

После включения публичного Compose и туннеля дождитесь HTTP 200 на корне
публичного HTTPS. Systemd active сам по себе не подтверждает готовность
обратного порта. Затем, с загруженным `.env`, из корня:

```sh
node --test tests/e2e/public.test.mjs
```

Проверяются HTTPS, Secure/HttpOnly/SameSite cookie, права трёх пользователей,
выход, отсутствие публичного маршрута к эмулятору и хеш JavaScript.
Тест пишет `tests/results/public.json` без сессионных данных и паролей.
Основные автотесты запускайте через локальные порты; нагрузочный профиль
использует отдельный Compose-проект и не прерывает публичное приложение.

pagination.spec.ts проверяет общее число страниц, автоматические фильтры, отказ неверных URL до запроса, допустимый соседний фильтр и потерянный ответ создания: повтор сохраняет ключ и не создаёт второе задание, а кэш реестра обновляется.


UI-12 проверяет корректный 503 при создании: форма и сессия остаются доступны,
повтор использует прежний ключ и создаёт одно задание. DatabaseAvailabilityTest
проверяет то же правило с настоящим исчерпанием Hikari и PostgreSQL, включая
соседний случай запрещённой роли.

Native PostgreSQL-тесты, UI, recovery и нагрузка используют один выделенный
PostgreSQL проекта system-integration-load на 19632 с БД si_test/si_emulator_test.
Native-тесты требуют остановленных backend и emulator; их команды есть в корневом README.
Тяжёлые проверки выполняются последовательно; данные обычных si_app/si_emulator
не являются тестовыми fixtures.

SI-10 проверяет UI остановки и продолжения на обоих размерах. Перед
адресным переносом срока он проверяет принадлежность
всех контейнеров отдельному проекту и выбирает только созданный им UUID.
В recovery проверяются два перезапуска вокруг лимита и продолжение оператором
с повтором сохранённой команды.
Демо ожидает до 120 с: четыре задержки суммарно 82 с плюс HTTP-дедлайны.

## Проверка Docker context

Из корня с Docker и проектным Node выполните:

~~~sh
node --test tests/build/context.test.mjs
~~~

Проверка использует scratch/COPY без сети, синтетические env-файлы и временный
каталог внутри .local. Не читает приватные env и удаляет созданные fixtures.

Проверка графов и владения codegen использует JDK из `JAVA_HOME`
или ищет Java в `PATH`, если переменная не задана. Бизнес-исходники
при этом не компилируются.

~~~sh
node --test tests/build/gradle.test.mjs
~~~

Она создаёт временные build metadata, генерирует обе схемы, проверяет
UP-TO-DATE и инвалидацию потребителей внешнего контракта. Все fixtures удаляются.
Общий прогон этих проверок: node --test --test-concurrency=1 tests/build/*.test.mjs.

## Нативное поведение Select

Из tests с проектным Node/Corepack и установленными браузерами:

~~~sh
corepack pnpm test:components
~~~

Тестовая страница frontend/tests/choice-form.html доступна только через Vite
на собственном loopback-порту 19774, который runner запускает и останавливает.
Она проверяется TypeScript, не входит в production bundle и не обращается к API/БД.
Шесть desktop/mobile-проверок покрывают required, controlled/uncontrolled reset,
однократный FormData, disabled/fieldset, клавиатуру и недоступное значение.
Основной playwright.config.ts эту fixture не запускает.

Production UI tests (`production.config.ts`) запускают временный Nginx на
loopback 19778 в отдельной сети 10.252.97.0/28. Сеть и контейнер удаляются
global teardown; перед запуском проверьте отсутствие пересечений Docker/host/VPN.
API перехватывается тестами, доступ к БД не требуется.

## Измерение пагинации и навигация

Из tests/: corepack pnpm test:components.
Десять проверок: шесть Select и четыре route/filter-сценария на 390/1440 px.
Отдельный fixture использует настоящий usePagination и такой же RouterProvider, как приложение,
контролируя только доставку ResizeObserver/requestAnimationFrame. Измерение,
уже поставленное в очередь, не должно возвращать старую страницу или стирать
новый фильтр. Без проверки актуального адреса все четыре сценария падают;
с ней проходят. Fixture не входит в production assets.

## Независимость доставки от медленного ответа

`node tests/e2e/delivery-isolation.mjs` запускается на пустых тестовых БД
system-integration-load с теми же 2 CPU / 4 ГиБ. Пять обычных заданий разогревают
путь; затем пять пар: эмулятор задерживает ответ первой операции после commit,
следующая нормальная должна быть принята менее чем за 1 с. Это fault-регрессия,
не NF08 и не оценка обычной пропускной способности. После каждой пары ждём
завершения работ; задержка между пробами не входит в измерение. Сверяются
все 15 заданий, запросы, история и одно внешнее исполнение, сбои снимаются
в finally. Отчёт — tests/results/delivery-isolation.json.
Для отрицательного контроля можно явно выбрать immutable application SHA
через SI_TAIL_APP_COMMIT; все три образа должны ему соответствовать.
