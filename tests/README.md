# Проверки сервиса

| Где | Что проверяем |
| --- | --- |
| `tests/e2e/` | HTTP smoke, браузерные сценарии обеих ролей и аварийные перезапуски процессов. |
| [tests/sql/](sql/README.md) | Реестр JDBC и EXPLAIN на откатываемых тестовых fixtures. |
| `tests/load/` | Генерация 5 000 записей и [профиль NF08](load/README.md). |
| backend/src/test/, emulator/src/test/ | Контракты, предметные правила, архитектура, HTTP-доступ и PostgreSQL. integrationTest использует si_test/si_emulator_test. |
| `frontend/tests/` | Контрактные тесты клиента, polling и round-trip production JS/CSS. |

Сценарии и ожидаемые результаты связаны с требованиями в
[плане приёмки](../docs/test-cases.md).

## HTTP smoke

Запустите отдельный тестовый Compose по [инструкции](load/README.md#запуск).
После готовности сервисов запустите тесты из корня репозитория.

```sh
node --test tests/e2e/smoke.test.mjs
```

По умолчанию тест проверяет backend на `http://127.0.0.1:19680` и frontend
на `http://127.0.0.1:19673`. Для другого тестового стенда задайте
`SI_BACKEND_URL` и `SI_FRONTEND_URL`. HTTP smoke проверяет доступность
API, выдачу собранного JavaScript и проксирование защищённого API через frontend.
Дополнительно проверяет сырые gzip/identity-ответы JS/CSS, Vary, запрет gzip;q=0,
совпадение распакованных байтов и отсутствие изменения private API.

Пишите локальные отчёты в `tests/results/`. Снимки, логи и результаты нагрузки
в этом каталоге игнорируются Git.

## Автоматический браузерный сценарий

Для запущенного локального приложения загрузите `.env` по инструкции
из корневого README, чтобы передать `SI_DEMO_PASSWORD`. Из `tests/`:

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm exec playwright install chromium
corepack pnpm test:e2e
```

На Firebat1 поднимите отдельный проект system-integration-load
с compose.load.yml, как для восстановления и нагрузки.
Его PostgreSQL и том отделены от демо. Прогон против обычных
si_app/si_emulator не выполняется; публичный туннель продолжает работать.

Runner использует `http://127.0.0.1:19673`, экраны 390 и 1440 px,
учётки `initiator.one`, `initiator.two` и `operator`. `SI_FRONTEND_URL` переопределяет
адрес тестового стенда. Тесты создают собственные задания с префиксом E2E.
Не направляйте их на окружение с реальными данными. HTML-отчёт находится
в `tests/results/report/`; снимки ошибочных сценариев — в
`tests/results/playwright/`. Трассы отключены: они сохраняют пароль входа и
сессионные заголовки. Сбор списка тестов не подтверждает прохождение
пользовательского сценария.

themes.spec.ts проверяет три палитры, тёмную по умолчанию, контраст текста,
сохранение выбора, синхронизацию вкладок, сохранение черновика формы,
мобильные фильтры, общий логотип, поля с подсказками и карточки, оформление меню и отступ стрелки, клавиатуру и явное сообщение при недоступном или неверном сохранённом выборе.
spacing.spec.ts дополнительно измеряет интервалы при удержанном HTTP-ответе, ошибке, пустом и заполненном реестре, в карточках, форме, истории и сверке.
Вместе с основными сценариями и refresh.spec.ts это 48 проверок на двух размерах экрана.
UI-13 проверяет число запросов NEEDS_REVIEW/STOPPED по управляемым часам;
UI-14 — реальную запись сверки оператором и обновление истории уже завершённого
задания в открытой вкладке инициатора. Состояние фактических прогонов — в
[текущей стадии](../docs/current-stage.md).
Основной сценарий реестра дополнительно проходит ширины
390/480/481/759/760/761/767/768/1024/1150/1151/1440 px:
карточки до 760 px включительно, затем таблица без внутреннего горизонтального скролла.

HttpErrorRoutingTest проверяет настоящий HTTP-сервер: 404/405/500 сохраняют
свой смысл, 500 не раскрывает SQL и откатывает task/queue/history/receipt;
повтор с тем же ключом после восстановления создаёт одну запись.
Прямой /error закрыт, 401/403 для сессии и роли сохраняются.
Серверные тесты также проверяют все допустимые варианты внешнего результата,
равные UTC-метки, запрет всех операторских маршрутов для обоих инициаторов,
конкурентную передачу разбора и повтор сверки одним/разными авторами.

Автоматическое обновление истории проверяется с временной недоступностью
эмулятора для `REQ-800006` и `REQ-800007`. Режим снимается в `finally`.

Операторские сценарии управляют сбоями через `SI_EMULATOR_URL`
(по умолчанию `http://127.0.0.1:19681`) и используют тестовые номера
`REQ-810001`, `REQ-810002`, `REQ-820001`, `REQ-820002`, `REQ-829999`.
Они проверяют независимый счётчик исполнения, сохранённую сверку и явную
остановку при несовпадении запроса.

## Перезапуски и границы коммита

На выделенных тестовых БД с Compose-файлами compose.yml, compose.public.yml
и compose.load.yml, с загруженным `.env`, из корня:

```sh
node tests/e2e/recovery.mjs
```

Runner проверяет подключение к si_test/si_emulator_test и перезапускает только
API, PostgreSQL и эмулятор этого проекта. Обычные БД стенда не используются.
Не запускайте другие тесты на этом стенде одновременно.
Recovery отправляет Connection: close: при намеренном убийстве/пересоздании
процессов клиент не сохраняет старые TCP-соединения. NF08/capacity используют
обычный keep-alive. Все Compose-вызовы recovery, включая отключение worker,
сохраняют один список файлов с compose.load.yml; после override БД перепроверяются. Контрольные точки
используют блокировки строк PostgreSQL: после сохранения захвата, до
применения ленты и до назначения курсора эмулятором. Для проверки принятой,
но ещё не исполненной операции временно отключается существующий worker
эмулятора. В конце восстанавливается обычная конфигурация.

Проверяются сохранение курсора, история, неизменный результат и одно
исполнение. Седьмой этап останавливает Java-процессы с восемью сохранёнными
ожидающими заданиями, проверяет завершение HTTP и закрытие пула БД, отсутствие OOM/SIGKILL и однократное исполнение после старта. Пересоздание backend с другим IP проверяет обновление адреса
во frontend без перезапуска Nginx. Временный контейнер занимает прежний IP
только на время проверки и удаляется в `finally`. Тестовые номера — `REQ-830001`–`REQ-830004`.
Восьмой этап удерживает тестовую таблицу, исчерпывает пул параллельными HTTP-чтениями,
проверяет 503 SERVICE_UNAVAILABLE вместо ошибки прав и восстановление той же сессии
после освобождения блокировки. Подключения и блокировки освобождаются в finally.
Отчёт находится в `tests/results/recovery.json`. Это проверка рабочего
процесса и БД; она не подменяет браузерный сценарий.

## Публичная публикация TC-16

После включения публичного Compose и туннеля дождитесь HTTP 200 на корне
публичного HTTPS. Systemd active сам по себе не подтверждает готовность
обратного порта. Затем, с загруженным `.env`, из корня:

```sh
node --test tests/e2e/public.test.mjs
```

Проверяются HTTPS, Secure/HttpOnly/SameSite cookie, права трёх пользователей,
выход, отсутствие публичного маршрута к эмулятору и хеш JavaScript.
Тест пишет `tests/results/public.json` без сессионных данных и паролей.
Основные автотесты запускайте через локальные порты; нагрузочный профиль
использует отдельный Compose-проект и не прерывает публичное приложение.

pagination.spec.ts проверяет общее число страниц, автоматические фильтры, отказ неверных URL до запроса, допустимый соседний фильтр и потерянный ответ создания: повтор сохраняет ключ и не создаёт второе задание, а кэш реестра обновляется.


UI-12 проверяет корректный 503 при создании: форма и сессия остаются доступны,
повтор использует прежний ключ и создаёт одно задание. DatabaseAvailabilityTest
проверяет то же правило с настоящим исчерпанием Hikari и PostgreSQL, включая
соседний случай запрещённой роли.

Native PostgreSQL-тесты, UI, recovery и нагрузка используют один выделенный
PostgreSQL проекта system-integration-load на 19632 с БД si_test/si_emulator_test.
Native-тесты требуют остановленных backend и emulator; их команды есть в корневом README.
Тяжёлые проверки выполняются последовательно; данные обычных si_app/si_emulator
не являются тестовыми fixtures.

SI-10 добавляет UI остановки/продолжения на обоих размерах, номера
REQ-850001/REQ-850002. Перед адресным переносом срока он проверяет принадлежность
всех контейнеров отдельному проекту и выбирает только созданный им UUID.
Recovery добавляет REQ-830020/REQ-830021: два перезапуска вокруг лимита и
продолжение оператором с повтором сохранённой команды.
Демо ожидает до 120 с: четыре задержки суммарно 82 с плюс HTTP-дедлайны.

## Проверка Docker context

Из корня с Docker и проектным Node выполните:

~~~sh
node --test tests/build/context.test.mjs
~~~

Проверка использует scratch/COPY без сети, синтетические env-файлы и временный
каталог внутри .local. Не читает приватные env и удаляет созданные fixtures.

Проверка графов и владения codegen не компилирует бизнес-исходники:

~~~sh
node --test tests/build/gradle.test.mjs
~~~

Она создаёт временные build metadata, генерирует обе схемы, проверяет
UP-TO-DATE и инвалидацию потребителей внешнего контракта. Все fixtures удаляются.
Общий прогон этих проверок: node --test --test-concurrency=1 tests/build/*.test.mjs.

## Нативное поведение Select

Из tests с проектным Node/Corepack и установленными браузерами:

~~~sh
corepack pnpm exec playwright test --config choice.config.ts
~~~

Тестовая страница frontend/tests/choice-form.html доступна только через Vite
на собственном loopback-порту 19774, который runner запускает и останавливает.
Она не входит в production build и не обращается к API/БД.
Шесть desktop/mobile-проверок покрывают required, controlled/uncontrolled reset,
однократный FormData, disabled/fieldset, клавиатуру и недоступное значение.
Основной playwright.config.ts эту fixture не запускает.
