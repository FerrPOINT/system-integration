# Нагрузочная проверка NF08

[Исходное ТЗ](../../docs/original-specification.md) задаёт профиль нагрузки.
Подготовка и runner находятся в этой папке. Результат прогона фиксируется
в [текущей стадии](../../docs/current-stage.md). Профиль измеряется
после появления рабочих API и отдельного эмулятора, на выделенной тестовой БД.

- Отдельная команда готовит 5 000 записей и связанные данные. Для обычной
  демонстрации применяется отдельный набор. Подготовка использует штатный
  вход и создание задания. До прогрева для каждой учётки есть не менее 20
  успешных записей для фильтра. У клиентов непересекающиеся наборы задач
  для редактирования.
- 20 клиентов отправляют следующий запрос после ответа. После 30 с прогрева
  измерение длится 120 с. Каждый клиент циклически выполняет четыре операции,
  начиная с одной из них. На каждую стартовую операцию приходится пять
  клиентов. Для окна измерения считаем запросы по моменту их старта и ждём
  исхода запросов, начатых до конца окна. Публикуем число и долю каждой
  операции. Разница между любыми двумя счётчиками — максимум 20 из-за
  неполного последнего цикла у каждого клиента.
- Чтение использует `GET /api/tasks?businessStatus=SUCCEEDED&page=0` (20 строк)
  и `GET /api/tasks/{taskId}`. Запись использует `POST /api/tasks` и
  `PATCH /api/tasks/{taskId}` с актуальной версией и отдельным ключом команды.
  Генератор использует штатную авторизацию и распределяет доступные записи
  между клиентами.
- Эмулятор работает в обычном режиме. Браузер и генератор нагрузки
  работают вне лимитов сервисов.
- Перед измерением фиксируем число исходных записей, успешную авторизацию,
  по 20 записей в отфильтрованной странице для каждой учётки и доступ к
  выбранным карточкам. В отчёте отмечаем отказы из-за неверных тестовых
  прав, данных или ревизий отдельно. Если генератор создал такие отказы,
  сохраняем отчёт, исправляем подготовку и повторяем замер.
- В отчёте указываются версия, команды, параметры стенда, ограничения
  ресурсов, число успешных запросов и ошибок по причинам. p95 рассчитывается
  отдельно для чтения (≤ 2 с) и записи (≤ 3 с). Измеряем время монотонными
  часами от начала запроса до чтения тела ответа либо ошибки. Предельное
  время одного запроса генератора — 10 с, включая соединение и тело.
  При его истечении записываем фактическую длительность и ошибку тайм-аута.
  В каждой группе сортируем все длительности запросов измерительного окна
  по возрастанию и берём элемент с номером `ceil(0,95 × N)`, считая с 1.
  Ошибочные ответы и тайм-ауты входят в выборку. Пустая выборка означает
  несостоявшийся замер. Ошибки классифицируются по операции и причине.
- Время от локального принятия до исполнения равно `completedAt - createdAt`.
  `createdAt` читаем из сохранённого задания, `completedAt` — из фактического
  состояния эмулятора по тому же ID операции. После замера проверяем
  задания, успешно созданные в измерительном окне, и указываем время сверки.
  Перед сверкой ждём завершения первого такого задания до 120 с: принятые
  операции могут оставаться в очереди после окончания нагрузки. Ожидание
  фиксируется отдельно и не входит в p95 API. Это предел времени проверки,
  а не срок исполнения задания. Ненаблюдаемый прогресс означает ошибку проверки.
  Отдельно указываем число и долю операций без итога на момент запроса:
  ещё не полученных эмулятором и принятых, но не завершённых. Корректный
  `404 OPERATION_NOT_FOUND` допустим только для локально неподтверждённой
  доставки; противоречие с подтверждением или итогом считается ошибкой.
  Ошибки проверки эмулятора указываем отдельно от операций без итога.
  Публикация события не участвует в расчёте.

## Кэш, повторы и границы результата

NF08 обращается к API напрямую, без React Query и браузерного кэша.
API возвращает no-store; серверного кэша нет. 30 секунд прогрева не являются
замером холодного старта процесса или БД. Смена кэша, потоков или пула БД
требует нового сравнимого прогона с версией и фактическими настройками.
Поведенческие проверки и TC-17 — в [сценариях](../../docs/test-cases.md#проверка-кэша-при-нагрузке).

После измерительного окна runner отдельно запускает 20 конкурентных команд
с одним actor/ключом/телом, затем replay и конфликт тела.
Успех: один taskId, увеличение списка на одну запись, тот же результат replay,
409 для иного тела; блок не смешивается с p95 основных операций.
Он не заменяет проверку однократного внешнего исполнения по TC-03–TC-05.

После измерения NF08 ждёт полного завершения очереди до 300 с; capacity —
до 180 с на ступень. Затем общий integrity.mjs сверяет созданные задания
с исходными title/reference/quantity/owner, внешним ID, одним исполнением,
результатом и историей. NF08 включает также задания прогрева и probe повтора.
Глобальная сверка двух тестовых БД проверяет точное число операций, пустую очередь,
отсутствие открытых проблем и неопубликованных событий, совпадение курсоров,
ID, запросов и полных JSONB-результатов. Время результата не переводится
в SQL timestamp для сравнения: JDBC и текстовый cast могут по-разному округлить
половину микросекунды. Исходная точность JSON сохраняется.

Начальный снимок незавершённых операций остаётся отдельной метрикой.
Наличие pending в нём допустимо, но итоговый passed требует завершения
всего проверяемого набора. Каждая ступень capacity учитывает свой replay probe
в ожидаемом количестве записей.

Проверку валидатора можно повторить без запущенного приложения:

~~~sh
node --test tests/load/integrity.test.mjs
~~~

Пять тестов включают неверный исходный запрос при согласии двух серверов,
чужого владельца, дубли исполнения, неверные итоги/время/историю и расхождение БД.
Перед запуском профиля run.mjs заменяет прошлый отчёт на passed:false/status:running;
ранняя ошибка оставляет status:failed, а не прежний PASS.

Пройденный NF08 подтверждает 20 клиентов и заданный набор данных/операций.
Для большей нагрузки нужен отдельный профиль с целями по приёму и исполнению.
Учитывать рост/возраст очереди, незавершённые задания и скорость восстановления
после прекращения записи. Кэш чтений и virtual threads сами по себе не ускоряют
исполнителя. Последний прогон и ограничения —
в [текущей стадии](../../docs/current-stage.md#внешняя-очередь-под-нагрузкой).

## Лимиты стенда

| Компонент | Логические ядра | Оперативная память |
| --- | ---: | ---: |
| API | 0,6 | 1 536 МиБ |
| PostgreSQL | 1,0 | 1 472 МиБ |
| Эмулятор | 0,3 | 1 024 МиБ |
| Статический веб-сервер | 0,1 | 64 МиБ |
| Всего | 2,0 | 4 096 МиБ |

Перед прогоном считываем фактически применённые лимиты CPU и памяти
всех четырёх запущенных контейнеров и прикладываем их к отчёту вместе с суммой.
В общий бюджет включён также статический веб-сервер frontend.
Адрес стенда и тестовые
учётки передаются из окружения. Отчёт пишется в `tests/results/` без секретов.

## Запуск

Команды выполняются из корня репозитория после обычной приёмки приложения.
Загрузите `.env` в окружение терминала по README. Тест использует отдельные
БД `si_test` и `si_emulator_test` с разными ролями и паролями.
Не запускайте серверные интеграционные тесты одновременно с нагрузочным стендом.

Перед сборкой кандидат должен быть закоммичен. В PowerShell:

```powershell
$env:SI_SOURCE_REF = git rev-parse HEAD
```

В POSIX shell: `export SI_SOURCE_REF=$(git rev-parse HEAD)`.
Соберите три образа обычными командами корневого README с этим окружением.
Метка образов API и эмулятора должна совпадать с коммитом кандидата.

```sh
docker compose -f compose.yml -f compose.public.yml -f compose.load.yml --profile app up -d --wait
docker compose -f compose.yml -f compose.public.yml -f compose.load.yml --profile app stop backend emulator
node tests/load/reset.mjs
docker compose -f compose.yml -f compose.public.yml -f compose.load.yml --profile app up -d --wait
node tests/load/prepare.mjs
node tests/load/run.mjs
```

Первый запуск применяет миграции к тестовым БД. Reset разрешён только
при остановленных API и эмуляторе и очищает только эти две БД. Подготовка
использует штатный API и ждёт исполнения всех 5 000 исходных записей.
Runner проверяет фактические подключения, число записей, ресурсы, метки
образов и чистое состояние Git до и после измерения. Результат —
`tests/results/nf08.json`; ненулевой exit code означает несостоявшуюся
либо не прошедшую квалификацию. Сам отчёт содержит причины ошибок.

После прогона верните обычные БД демонстрационного стенда:

```sh
docker compose -f compose.yml -f compose.public.yml --profile app up -d --wait
```

Данные `si_app` и `si_emulator` reset нагрузки не изменяет.

## Подсчёт и идемпотентность

Запросы реестра в NF08 проверяют totalItems/totalPages с теми же фильтрами,
что и записи. Замер p95 включает стоимость точного COUNT.
После измерительного окна генератор отправляет 20 одновременных повторов
одной команды с одним ключом, затем повторяет её последовательно и проверяет
409 для другого тела. Итог: один taskId и увеличение числа заданий на 1.
Эта проверка записывается в idempotency и не смешивается с задержками окна NF08.
Исполнение внешней операции проверяют также серверные тесты и восстановительный
сценарий; рост внешней очереди под нагрузкой фиксируется отдельно.

## Расширенный профиль capacity

Точка входа одна: run.mjs явно выбирает nf08 (по умолчанию) или capacity.
Неизвестное значение SI_LOAD_PROFILE отклоняется до запросов.
nf08.mjs сохраняет штатную смесь и длительность NF08;
capacity.mjs реализует TC-18. Общие проверки окружения и метрики принадлежат
environment.mjs и metrics.mjs. Это тестовые модули, не новые сервисы.

Авторизация клиентов выполняется до прогрева с параллелизмом не больше четырёх;
профиль измеряет API уже вошедших пользователей, а не массовый вход с BCrypt.
Время опустошения очереди определяется по последней выборке drain.samples;
drain.finishedAt фиксирует конец ожидания очереди; независимая сверка
и проверка replay выполняются затем.

После NF08 остановите backend/эмулятор, выполните reset выделенных БД и снова
поднимите нагрузочный Compose. Обычные демонстрационные БД не очищаются.
Из корня с проектным Node 26 и загруженным .env:

~~~sh
SI_LOAD_PROFILE=capacity node tests/load/prepare.mjs
SI_LOAD_PROFILE=capacity SI_CAPACITY_MODE=read SI_CAPACITY_CLIENTS=20 node tests/load/run.mjs
~~~

Один запуск измеряет одну ступень: read или mixed, 20/40/80 клиентов,
15 с прогрева и 60 с измерения. Default — read/20; неизвестные значения
отклоняются. Подготовка ждёт завершения ровно 10 000 записей, runner повторно
проверяет их количество и отсутствие очереди до запуска.

После каждой ступени сначала дождитесь drain и полной сверки созданных данных
(до 180 с), сохраните capacity.json под именем режима/числа клиентов в results.
Затем остановите API/эмулятор, выполните штатный reset, поднимите тестовый
Compose и снова prepare с SI_LOAD_PROFILE=capacity. Повторите для read/40,
read/80, mixed/20, mixed/40 и mixed/80. Нельзя использовать изменённый предыдущей
ступенью набор: каждая начинает с тех же 10 000 завершённых заданий и владельцев.
Если drain или целостность не подтверждены, reset не является способом скрыть
результат: сначала диагностируйте и сохраните неуспех.

При ранней остановке отчёт указывает фактически измеренное время.
Порог p95 обозначает пройденную ступень, а не доказательство абсолютного предела.
Предыдущий накопительный capacity сохранён как историческое исследование;
его нельзя напрямую сравнивать с этими независимыми ступенями.
Пределы и проверки — в [TC-18](../../docs/test-cases.md#tc-18-расширенная-нагрузка-и-восстановление-после-пика).

Метрики каждые 5 с: настройки БД, число/возраст ожидающих операций,
захваты, исполнения/публикации, статистика БД и ожиданий, CPU/память и состояние
контейнеров. Сбор асинхронный, Docker/psql читают только выделенные тестовые БД.
Наблюдение добавляет небольшую нагрузку; новые отчёты NF08 включают её,
прежний baseline её не содержал. Кэш ОС не сбрасывается.

capacity.json хранит каждую ступень, причину остановки, независимую сверку,
историю/права/повтор команды и maximumPassedClients по чтению и смеси.
passed означает корректный эксперимент без нарушений данных/прав, с пройденной
ступенью 20 в обоих режимах. Более высокая ступень может выявить предел;
это не означает поддержку 80 клиентов. Неожиданные ошибки, OOM/перезапуск
и ошибки наблюдения не считаются успешным результатом.

### Разделение задержки конвейера

В периодических снимках отдельно фиксируются число/возраст очереди приложения,
число/возраст принятых, но ещё не исполненных операций эмулятора и оба курсора.
Снимки двух БД снимаются независимо и не считаются атомарной сверкой.

После окончания измерения и ожидания очереди capacity добавляет pipeline:
p95 от создания до первой попытки, от начала до завершения попытки,
от приёма эмулятором до исполнения и от исполнения до применения итога.
Агрегаты выбирают записи начиная с начала соответствующей ступени, включая
прогрев. NULL означает отсутствие завершённых наблюдений, а не нулевую задержку.
Агрегация выполняется вне измерительного окна. Эти показатели дополняют
штатный p95 API и позволяют проверить причину отставания без нового сервиса мониторинга.

### Наблюдение SI-09

Снимки дополнены блокирующими PID, типом ожидания и возрастом транзакции,
числом активных/idle-in-transaction транзакций. runnerProcess содержит
host/PID, накопленное CPU-время и RSS самого Node-процесса; host — память
и load average общего физического хоста. CPU дочерних Docker/psql-процессов
в CPU Node не включён. В локальном NF08 генератор и наблюдатель работают
в одном процессе; при внешнем генераторе его метрики собираются отдельно.

Корректность обнаружения известной блокировки проверяет
[SQL-наблюдатель](../sql/README.md#проверка-наблюдателя-блокировок).
Наличие или отсутствие ожидания в редком снимке не определяет всю долю
блокировок за период. Сравнение до/после использует одинаковый сбор метрик;
старый отчёт без новых полей не объявляется новым сопоставимым baseline.

## NF08 с независимым генератором

Профиль nf08-external выполняет тот же цикл из nf08-workload.mjs:
20 клиентов, 30/120 с, те же проверки ответов и полный учёт созданных заданий.
БД, resource observer, проверка идемпотентности и итоговая сверка остаются
на Firebat1. Подготовка клиентов и вход выполняются до измерения.
Сервер передаёт сигнал начала по stdin/stdout SSH-процесса и принимает
отчёт генератора; незавершённый канал, иная версия и неполные метрики дают отказ
квалификации. Локальный NF08 сохраняет отдельный отчёт.

Сначала на Firebat1 отключите публичный туннель, поднимите точные образы кандидата
с compose.load.yml, выполните штатный reset при остановленных API/эмуляторе,
затем up и подготовку:

~~~sh
SI_LOAD_PROFILE=nf08-external node tests/load/prepare.mjs
~~~

На другой машине используйте ту же версию Node, что на Firebat1.
Скопируйте из этого коммита три файла с сохранением каталогов:
tests/load/external.mjs, tests/load/nf08-workload.mjs, tests/support/http.mjs.
Зависимости npm для них не нужны. Генератор сверяет SHA-256 всех трёх файлов
с квалифицированным source. Запуск из внешней копии, например в PowerShell:

~~~powershell
$env:SI_EXTERNAL_SSH_HOST = 'firebat1'
$env:SI_EXTERNAL_REMOTE_ROOT = '/opt/dev/system-integration'
$env:SI_EXTERNAL_LOCAL_PORT = '19680'
node tests/load/external.mjs
~~~

Драйвер сам создаёт только loopback SSH-forward к API, проверяет тестовую БД
и образы до входа, запускает серверный контроллер, затем закрывает оба своих
SSH-процесса. Тестовый пароль получает через приватный pipe; он не записывается
в файлы, аргументы, отчёты или диагностический вывод.
Эмулятор и PostgreSQL не публикуются. Прямой запуск серверного режима
nf08-external без клиента не является полноценным прогоном.

У SSH заданы connection/keepalive и ожидания протокола. Серверный процесс
NF08 ограничен 15 минутами (подготовка, 150 с нагрузки, drain и сверка),
preflight — 55 с; это ограничения тестовых процессов, не SQL или рабочего API.
Контроллер завершает работу при обрыве входного канала до результата.
Соединения не используют общий SSH ControlMaster.
Названия/ревизии проверяются в PATCH-ответе и повторным чтением изменявшихся
карточек после окна; число и авторы rename-аудита сверяются в БД.

На Firebat1 результат — tests/results/nf08-external.json.
На машине генератора — tests/results/external-driver.json и
nf08-external-server.json; контрольная сумма серверного отчёта проверяется.
Node CPU/RSS и средняя занятость/память хоста генератора указаны отдельно.
Node CPU не включает дочерние SSH-процессы; hostResources включает их и другие
приложения, RSS — два снимка, не пик. Времена pipeline выбираются по серверной
границе окна, а p95 API — по монотонным часам генератора: синхронизация часов
двух компьютеров для этих вычислений не требуется.

Это проверка отдельного генератора и SSH/сети, она не измеряет публичный HTTPS,
браузер или frontend-прокси. После прогона оператор возвращает обычный Compose,
проверяет сохранность/образы и запускает публичный туннель с TC-16.

## Равномерное поступление заданий

steady — отдельный create-only профиль: arrivals планируются по монотонным
часам независимо от времени ответа. Это не смесь NF08 и не замена capacity.
Размер исходного набора — 5 000 завершённых заданий. До запуска сохраняются
выбранные частоты и длительность, используется тот же бюджет контейнеров.

После reset/up тестовых БД выполните:

~~~sh
SI_LOAD_PROFILE=steady node tests/load/prepare.mjs
SI_LOAD_PROFILE=steady SI_STEADY_RATES=50,100,150,200,250 SI_STEADY_PHASE_SECONDS=30 node tests/load/run.mjs
~~~

Это пример короткой калибровки, не обещание такой пропускной способности.
Для основного окна выберите по её результатам частоты ниже/около/выше
наблюдаемой устойчивой скорости: три фазы по 300 с, всего 15 минут поступления.
Каждый новый прогон начинает с заново подготовленных 5 000 записей.
Внутри одного прогона очередь между фазами не сбрасывается и не опустошается.

Не более 64 незавершённых HTTP-запросов генератора. Не вместившиеся arrivals,
выход за временное окно, ошибки и фактический jitter сохраняются явно:
успешная фаза требует всех запланированных запросов без пропусков и p95
создания ≤ 3 с. Ограничения 20 000 ожидающих / 180 с возраста и состояние
контейнеров останавливают только тестовый генератор, не запросы приложения.
Они не являются SQL-таймаутами или новым ограничением рабочего API.

После фаз ждём drain до 300 с и полностью сверяем все созданные операции,
владельцев, неизменный запрос, результат, историю и однократное исполнение
через общий integrity-модуль и обе тестовые БД.
Рост очереди по фазам, pipeline, CPU/память и отсроченные ответы учитываются
отдельно. passed означает выполнение заявленного окна с целостностью;
растущая очередь при верхней частоте не объявляется устойчивой работой.
Отчёт tests/results/steady.json и логи сохраняются до следующего reset.
