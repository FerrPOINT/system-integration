# System Integration

Сервис принимает задания, отправляет их отдельному эмулятору и показывает
оператору доставку, результат и историю. Объём работ задаёт
[исходное ТЗ](docs/original-specification.md), текущий этап — [статус](docs/current-stage.md).

| Каталог | Ответственность |
| --- | --- |
| [backend/](backend/AGENTS.md) | Java, HTTP API, бизнес-правила, БД и доставка. |
| [emulator/](emulator/AGENTS.md) | Отдельное исполнение, БД, события и режимы сбоев. |
| [frontend/](frontend/AGENTS.md) | React, экраны и вызовы API. |
| [contracts/](contracts/AGENTS.md) | OpenAPI внутреннего приложения и эмулятора. |
| [tests/](tests/AGENTS.md) | Проверки запущенного сервиса и нагрузка. |
| [docs/](docs/requirements.md) | ТЗ, требования, архитектура, план работ и приёмка. |

Перед изменением сценария проверьте его правило в [аналитике](docs/analysis.md)
и критерий в [декомпозиции](docs/decomposition.md). За границы модулей и
хранение отвечает [архитектура](docs/architecture.md).

## Рабочая среда

Рабочую среду выбирает пользователь для конкретной задачи. Выбор другой
задачи и наличие preview не переключают текущий workspace. Перед изменениями
проверяйте host, путь, HEAD и dirty state.

Для явно выбранного Firebat1 исходники и Git находятся в /opt/dev/system-integration;
из Windows-чата работа выполняется через SSH. Для явно выбранной локальной
среды используется C:/git/azhukov/mini-crm/system-integration и Docker context
desktop-linux. У каждой изменяемой ветки и тестовой среды один владелец.
Публичный demo.azhukov-dev.ru меняется только в порученном объёме.
Сохраняйте соседние приложения и их данные.
Mini-CRM на Firebat1 выведен из эксплуатации; его исходники сохранены в GitHub.
Сохраняйте действующие TLS-материалы общего gateway и работающий Xray.
Нагрузочные, UI и recovery-проверки запускайте через compose.load.yml:
это отдельный проект system-integration-load со своей БД/томом, сетью
10.252.96.0/24 и loopback-портами 19632/19680/19681/19673.
Обычный Compose и публичный туннель при проверках продолжают работать.
Не направляйте тестовые команды на демонстрационные контейнеры.
Перед изменением тестового стенда проверяйте живые процессы тестов/сборок
и фактические подключения к БД; одновременно окружением управляет один прогон.
Открытый preview и оставленные контейнеры сами по себе не означают активный
прогон. Штатный reset тестовых БД разрешён при остановленных backend/emulator.
Команды и завершение тестового стенда описаны в tests/load/README.md.
Эмулятор и БД остаются доступны только на loopback.

При работе на Firebat1 используйте существующие Linux toolchains в
/opt/dev/system-integration/.local/toolchains и кэши выбранного workspace;
системные SDK соседей не обновляйте. На Firebat1 сборки и тяжёлые проверки
идут последовательно. Команды Windows ниже применимы только к локальной среде.

Для команд Node используйте проектный Windows Node 26 из
`.local/toolchains/node-v26.13.1-win-x64` и Corepack из
`.local/toolchains/corepack/node_modules/.bin`. Системные toolchain соседних
приложений не обновляйте. Тяжёлые сборки выполняйте последовательно через общий
host execution slot, соблюдая ограничения из пользовательского AGENTS.md.
Для интерактивного локального preview поднимайте `postgres backend emulator`
проекта `system-integration-load` и Vite на `127.0.0.1:19673`; `/api`
проксируется на локальный `127.0.0.1:19680`. Для полного Compose/UI/recovery
прогона Vite освобождает порт frontend-контейнеру той же группы.

Из корня проекта:

```powershell
$env:PATH="$PWD/.local/toolchains/node-v26.13.1-win-x64;$PWD/.local/toolchains/corepack/node_modules/.bin;$env:PATH"
$env:COREPACK_HOME="$PWD/.local/toolchains/corepack-cache"
$env:GRADLE_USER_HOME="$PWD/.local/gradle"
$env:PLAYWRIGHT_BROWSERS_PATH="$PWD/.local/browsers"
```

Приватный `.env` при переносе на Linux использует LF и права `600`.

## Общие правила

- У каждого состояния и бизнес-правила один владелец. Начинайте с простого
  решения на текущем стеке. Добавляйте зависимости, слои и каталоги, когда
  у них появился потребитель.
- REST меняется через OpenAPI. Сгенерированные файлы и отчёты остаются
  в игнорируемых каталогах. Секреты передаются через окружение.
- Меняйте правило, контракт и проверку согласованно. Запускайте
  проверки затронутого сценария в рабочей среде. Статус сборки, работу сервиса и приёмку
  фиксируйте отдельно в [текущей стадии](docs/current-stage.md).

## Архитектурные принципы

Перед переводом backend/emulator на явные controller/service/repository/mapper
прочитайте [план Spring-слоёв](docs/spring-boot-refactoring-plan.md). Он задаёт
целевые владельцы и проверки; текущие пакеты меняются только вместе с их
реальными потребителями и архитектурными тестами.

Текущая структура и правила описаны в [архитектуре](docs/architecture.md#границы-кода).
Рефакторинг сохраняет runtime-контракты; это не заменяет квалификацию и проверку
публичной версии по [текущей стадии](docs/current-stage.md).

- Основное приложение — один контекст интеграции; эмулятор — отдельный контекст
  и процесс. Разделяем domain, application, infrastructure и web без новых сервисов.
- Domain владеет состоянием и допустимыми переходами; application — сценарием,
  правами и транзакцией; infrastructure — SQL/HTTP/планировщиками; web — API.
  Бизнес-модель не зависит от Spring, JDBC, Jackson и сгенерированных HTTP DTO.
- Используем DDD для языка, границ и инвариантов. SOLID означает ясную
  ответственность и направление зависимостей; DRY — одного владельца правила,
  а не объединение внешне похожих сценариев. KISS/YAGNI исключают
  generic CRUD, интерфейс каждому сервису и абстракции без потребителя.
- Сначала сохраняем поведение и существующие форматы, затем меняем алгоритм.
  Заменённый путь удаляется в том же срезе; параллельные legacy/fallback реализации
  не остаются. OpenAPI и сохранённые квитанции не меняются из-за перемещения классов.
- Сеть выполняется вне транзакции БД. Задание, outbox и история фиксируются
  атомарно; результат и курсор ленты — тоже. Это не заменяется событием после коммита.
- Производительность подтверждается SQL-планами и сравнением одинаковых данных.
  Батч имеет ограниченный размер, явную атомарность и порядок блокировок.
  Увеличение пулов, таймауты и новые кэши не заменяют устранение причины.
