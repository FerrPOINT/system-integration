# System Integration

Сервис принимает задания, надёжно передаёт их эмулятору и показывает доставку,
результат и историю. Объём — [исходное ТЗ](docs/original-specification.md),
выполненные проверки и граница публикации — [текущая стадия](docs/current-stage.md).

| Каталог | Что прочитать при изменении |
| --- | --- |
| backend | [AGENTS](backend/AGENTS.md): серверные сценарии, права, транзакции и хранение. |
| emulator | [AGENTS](emulator/AGENTS.md): внешнее исполнение, события и режимы сбоев. |
| frontend | [AGENTS](frontend/AGENTS.md): экраны, API, кэш и общие компоненты. |
| contracts | [AGENTS](contracts/AGENTS.md): OpenAPI и build-time генерация. |
| tests | [AGENTS](tests/AGENTS.md): API/UI, восстановление, SQL и нагрузка. |

Перед изменением поведения проверьте правило в [аналитике](docs/analysis.md)
и критерий в [декомпозиции](docs/decomposition.md). Границы кода и владельцы
состояния описаны в [архитектуре](docs/architecture.md).
Завершённые планы и исследования доступны через [историю](docs/history.md).

## Рабочая среда

Рабочую среду определяет поручение. Перед изменениями проверьте host, checkout,
HEAD и dirty state. В удалённой среде исходники, Git, зависимости, сборки и тесты
остаются в выбранном SSH workspace. Не переносите работу на другой компьютер
только из-за наличия второго checkout. Сохраняйте несвязанные изменения.

У тестовой установки один активный владелец. UI, integration, recovery и нагрузка
используют compose.load.yml: проект system-integration-load, отдельный том/БД,
сеть 10.252.96.0/24 и loopback-порты 19632/19680/19681/19673.
Обычный проект использует сеть 10.252.95.0/24 и порты 195xx.
Проверяйте процессы тестов и подключения к БД перед reset. При PostgreSQL-тестах
backend/emulator тестового стенда остановлены. Завершённые тестовые ресурсы
очищаются по [инструкции](tests/load/README.md).
Обычная установка, её данные и публичный туннель при тестах сохраняются.

Используйте закреплённые версии SDK из README и существующие кэши выбранной среды.
Не обновляйте общие SDK и сервисы других проектов. Тяжёлые проверки выполняйте
последовательно; промежуточные проверки ограничивайте изменённым модулем.
Приватный .env исключён из Git и журналов.

## Архитектура

- У каждого правила и состояния один владелец. Используйте штатный механизм
  или небольшой предметный helper; слои и интерфейсы нужны при реальной границе.
- Domain — чистая Java без Spring, JDBC, Jackson и generated DTO.
- Controller/mapper владеют HTTP. Service владеет сценарием, правами и транзакцией.
  Repository определяет хранение, client/http — внешнее общение, scheduler — триггеры.
- Spring Data JDBC обслуживает обычные чтения. Ручной JDBC остаётся для команд,
  блокировок, outbox, квитанций и сложных проекций.
- Сеть выполняется вне транзакции. Задание/outbox/история/квитанция фиксируются
  атомарно; применение результата и курсора ленты — тоже.
- Бизнес-правила не дублируются в mapper или UI. URL владеет фильтрами;
  сервер — доступом и допустимыми действиями; Query — клиентским кэшем.
- REST меняется через OpenAPI. Outputs и annotation processors пишут в build,
  сгенерированный код не редактируется и не коммитится.
- Lombok убирает простой DI/log; конструкторы с проверками и lifecycle остаются
  явными. MapStruct проверяет HTTP DTO; ручной ResultSet parsing его не заменяет.
- Замена механизма включает обновление вызовов и удаление заменённого кода.
  Параллельные legacy/fallback пути и абстракции без потребителя не добавляются.
- Flyway сохраняет применённую историю. Миграция нужна для изменения схемы,
  а не для перестановки классов.
- SQL оптимизируется по планам на подходящих данных; батчи ограничены,
  порядок блокировок явен. Пулы, кэши и таймауты не заменяют устранение причины.

## Проверки и доставка

Java build/check проверяет Spotless; frontend build — Prettier, ESLint и TypeScript.
Проверка стиля не переписывает файлы; применение запускается явно.
Чистые правила проверяются unit-тестами, SQL и конкурентность — на PostgreSQL,
права/контракт — через API, интерфейс — существующими UI/component тестами.

После интегрированного среза выполните подходящие [проверки](README.md#сборка-и-проверки).
Source, сборка, runtime и публичная приёмка — разные подтверждения.
Публикуйте только свои изменения. Merge-ready не означает merge/deploy;
публичная установка меняется в порученном объёме с сохранением её данных.
