# Демонстрационный набор

`seed/` владеет большим набором вымышленных данных для просмотра интерфейса.
Это исторические демонстрационные снимки в настоящих БД backend и эмулятора,
а не подменённые ответы frontend. Они не являются доказательством исполнения
бизнес-сценария: для этого отдельно запускаются живые сценарии и автотесты.

## Загрузка и проверка

Нужны Node 26, запущенный локальный `system-integration-load` из
compose.yml + compose.load.yml, текущие миграции и три демоучётки.
По умолчанию используются loopback-порты 19680/19681/19673 и отдельные БД
si_test/si_emulator_test. Целевая установка проверяется до записи.
Пароль передаётся через существующий приватный `.env`; в отчёт не записывается.

Из корня репозитория:

```sh
node --env-file=.env tests/demo.mjs seed
node --env-file=.env tests/demo.mjs verify-seed
node --env-file=.env tests/demo.mjs verify-seed --pristine
node --test seed/dataset.test.mjs
node --env-file=.env seed/check-import.mjs
```

Для обычной демонстрационной установки `system-integration` на 195xx
нужен явный выбор целевой среды:

```sh
SI_SEED_TARGET=demo node --env-file=.env tests/demo.mjs seed
SI_SEED_TARGET=demo node --env-file=.env tests/demo.mjs verify-seed --pristine
```

Этот режим проверяет принадлежность четырёх контейнеров проекту, loopback-порты
и подключения backend/emulator к si_app/si_emulator. Адреса API берутся из
проверенных контейнеров. Неподдерживаемая цель или чужие БД останавливают
команду до записи. Без SI_SEED_TARGET команда по-прежнему выбирает только load.
`scenarios`, `check-import` и изменяющие автотесты остаются на отдельном load-стенде;
SI_SEED_TARGET не переключает их в демонстрационную установку.

Загрузка добавляет записи, затем проверяет их через настоящий API.
Отчёт, ссылки на примеры и контрольные суммы сохраняются в
`tests/results/showcase/load/` или `tests/results/showcase/demo/` в зависимости
от выбранной установки. UI-тесты читают только отчёт `load/showcase.json`.
`check-import` отдельно проверяет окончательный SQL во временных таблицах
с реальными типами и CHECK/UNIQUE-ограничениями; транзакции откатываются.
Внешние ключи и связи дополнительно проверяются каталогом и чтениями API.
При повторе новые экземпляры не создаются; изменения, внесённые в UI, сохраняются.
`--pristine` дополнительно проверяет исходные статусы и доступные действия:
используйте его до ручного изменения демонстрационных примеров.
Состояния и история не «восстанавливаются» поверх пользовательских действий.
При совпадении ID с другим запросом или владельцем загрузка прекращается.
Reset, TRUNCATE, удаление прежних данных, изменение миграций и перезапуск
контейнеров не выполняются. Автоматического destructive reset у набора нет.

В каждой БД импорт выполняется отдельной транзакцией. Сначала импортируется
внешнее состояние, затем внутреннее; общей распределённой транзакции нет.
При ошибке команда завершается неуспешно. Повтор завершает недостающий этап,
не переписывая уже созданные объекты. Контрольные суммы посторонних таблиц
сверяются до и после импорта; во время загрузки не запускайте другие writers
и изменяющие автотесты на том же стенде.

## Состав

| Объекты       | Количество / разнообразие                                                                                            |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| Задания       | 1200, по 600 у каждого инициатора; 31 группа товаров, 13 городов, 6 рабочих операций                                 |
| Даты и объёмы | Около трёх месяцев, более 100 значений количества, обычные объёмы и превышение лимита                                |
| Исходы        | Успех, бизнес-отказ, ожидаемый результат, выполнение, приостановка для разбора и остановленная отправка              |
| Разборы       | 150: все пять видов, открытые/завершённые, назначенные/неназначенные, 30 общих проблем ленты                         |
| Сверки        | 1320: MATCH/DIFFERENCE/UNAVAILABLE; PRESENT/NOT_FOUND/UNAVAILABLE; свежее и устаревшее основание решения             |
| История       | 6610 событий всех 12 типов; 10 заданий с более чем 120 событиями, ссылки на сохранённые сверки и разборы             |
| Исполнитель   | 1160 согласованных внешних операций с одним исполнением; отсутствующие операции подготовлены отдельно                |
| Решения       | Принятие внешнего результата, явное завершение разбора, закрытие общей проблемы, восстановление доставки с тем же ID |

Основные 1000 записей дают заполненный правдоподобный реестр. Ещё 200 —
по десять примеров каждого из 20 сценариев; каждый сценарий есть у обоих
инициаторов. Названия описывают комплектацию, резервирование, перемещение,
отгрузку, пополнение и выдачу материалов. Номера нового набора занимают
REQ-600001–REQ-601200; конфликтующие внешние заявки используют отдельные
REQ-651009–REQ-651189. Существующие REQ-900001–REQ-900006 не затрагиваются.

Исторические даты задаются относительно дня первой загрузки; повтор получает
исходную точку из первого задания. ID детерминированы версией каталога.
Прежние квитанции команд, курсоры ленты и учётки не меняются.

## Что открыть

В `showcase.json` выбранной установки примеры имеют поле `scenario`:

| Сценарий              | Что видно / доступно                                                                     |
| --------------------- | ---------------------------------------------------------------------------------------- |
| success / rejected    | Обычное завершение и бизнес-отказ из-за количества выше 100                              |
| duplicate / late      | Повторная публикация результата у эмулятора; устаревший снимок в истории                 |
| waiting / running     | Подтверждённая доставка отдельно от ожидаемого или промежуточного бизнес-результата      |
| unavailable           | Приостановленная доставка и сохранённая недоступность при сверке                         |
| retry                 | Свежая сверка отсутствия операции; доступен разрешённый повтор                           |
| protocol              | Внешний ID занят другим запросом; чужой результат нельзя принять                         |
| difference / assigned | Расхождение, которое можно разобрать и принять; вариант с ответственным                  |
| conflict              | Противоречащее сообщение сохранено как evidence, действительный результат не перезаписан |
| applied / stopped     | Завершённое решение с автором, временем, причиной и сохранённым основанием               |
| retried / uncertain   | История восстановления либо подтверждения после неоднозначного ответа                    |
| matched / missing     | Совпадение с внешним состоянием либо отсутствие внешней операции                         |
| stale                 | Сохранённая сверка устарела; решение требует новой сверки                                |
| long                  | Более 120 событий: desktop-пагинация и ограниченная мобильная лента                      |

Сверка `UNAVAILABLE` — исторический снимок. При новом запросе работающий сейчас
эмулятор может дать другой результат; это нормальная смена состояния.
Общие проблемы ленты тоже исторические: они не останавливают текущий worker.

Для подготовленных примеров с удержанными уведомлениями result_events остаются
без cursor/publish_after: импорт не публикует старую ленту заново и не двигает
глобальный курсор. Для примеров зарегистрирован штатный режим удержания ответа;
`clear` выпускает их события. У завершённых массовых записей сохранены состояние
эмулятора и внутренняя история, без повторного импорта внешней ленты.

## Живые сценарии обмена

Шесть минимальных сценариев исходного ТЗ запускаются отдельно:

```sh
node --env-file=.env tests/demo.mjs scenarios
```

Команда использует тот же локальный load-проект на 19680/19681 и проверяет
его принадлежность перед записью. Каждый прогон создаёт шесть новых заданий
в свободном диапазоне REQ-700000–REQ-789999 обычными командами API.
Прогон включает четыре штатных сбоя, независимо проверяет единственное
исполнение и ожидаемый результат, две публикации дубликата и игнорирование
выпущенного запоздалого снимка. Отчёт — `tests/results/demo.json`.
В отчёте сохраняются новые ID и реально наблюдавшиеся состояния. Старые
квитанции не заменяют свежий прогон. Идемпотентная загрузка большого набора
по-прежнему принадлежит только команде seed.

QUEUED, RETRY_WAIT и UNKNOWN — кратковременные состояния действующего обмена,
а не постоянные архивные исходы. Они наблюдаются при новом создании, отказе
связи и уточнении после потери ответа. Сид не подменяет их бессрочно зависшей
очередью и не выключает общие workers. RUNNING и ожидание результата доступны
также в историческом наборе с удержанным окончательным уведомлением.

Нагрузочные 5000 записей остаются отдельным профилем
[tests/load/prepare.mjs](../tests/load/prepare.mjs) и не заменяют демонстрацию.
